## §3. Найденные дефекты и что исправлено

### P0 — ломали функцию (1)

**P0-1. Датированный тейпер (per-event cessation + Winwood) был МЁРТВ для последней недели.**
`strength-sport-builder.engine.ts:781–805`: per-event cessation считал `finalSets/finalWeight/
finalRir` внутри `if (compDateAny && startDateAny …)`, но затем цепочка
`else if (taper && !deload)` (которая идёт ПОСЛЕ `if (winwoodTaper)`) затирала результат
внешним `taperWeeks`-тейпером. Доказано пробой: при дате старта и `taperWeeks=2` последняя
неделя выдавала `rir=1, вес=100` (внешнее ×0.92) вместо обещанного cessation `rir=3, вес=55`
(×0.50) и Winwood `×0.75/int 0.75`. Для `forge` с датой старта это означало, что «план
под соревнование» не таптовался вообще — обещание интерфейса («Тапер: Winwood step 8.6д,
vol -45%») не исполнялось.

*Фикс:* введён флаг `dateTapered`; ветка `else if (dateTapered) {}` встала **перед**
`else if (taper && !deload)` — данные тейпера больше не затираются. Тест с проверкой
`rir≥2` у всех рабочих последней недели + веса Winwood-недели > cessation-недели.

### P1 — неправильные цифры / вранье интерфейса (5)

**P1-1. Дни/нед 5 и 6 молча схлопывались в 4 сессии.** `strength-sport-split-patterns.ts`
содержал `sm_2/sm_3/sm_4`, `wl_3…wl_6`, `hyb_3/hyb_4` — но у стронга и гибрида не было
паттернов на 5 и 6 дней. `recommendStrengthSportPattern` возвращал `sm_4`, и UI врал
«5×/нед», выдавая 4 сессии. Для соревновательного стронгмена с 2 overhead-днями в неделю
это блокировало главную потребность (Amdi 2026: плечо 2.48×/нед).

*Фикс:* новые `sm_5` (overhead ×2 + тяга + присед + ивенты), `sm_6` (6-дневка для
enhanced), `hyb_5`, `hyb_6`. Тест: 5→5 сессий, 6→6, все паттерны консистентны
(schedule/rotationDays/sessionsPerRotation).

**P1-2. Warning «🦾 добавлен hammer curl 3×12» печатался ВСЕГДА**, даже если hammer уже
есть в плане (тогда инъекция пропускалась) — подпись обещала то, чего в плане нет.
*Фикс:* подпись печатается только при фактической инъекции; при нехватке бюджета —
честная «не влез в лимиты сессии».

**P1-3. Warning «QL — добавлен suitcase carry 2×20м + side plank 2×30с» обещал side plank,
который не добавлялся никогда** (в коде только `sandbag_carry`).
*Фикс:* подпись = факту («вставлен suitcase … + **совет**: side plank …»), либо
честное «не влез».

**P1-4. `enforceCategory` для камней не был подключен** — warning «камни N подъёмов > MRV»
печатался каждую неделю, но объём никто не резал (перебор оставался в плане).
*Фикс:* enforce подключён (`enforceCategory(stoneIds, …)`).

**P1-5. Несоответствие единиц и списков в enforce, из-за которого enforce не работал:**
- измерение `stoneLifts` включало `tire_flip`, а список enforce — нет → перебор не резался;
- `carry` сравнивал МЕТРЫ с MRV, но резал по СЕТАМ (`carrySets` против `mrv/25`) →
  при переборе метров резал не то и не до конца;
- `circus_db_medley` (**overhead-ивент**, «гантели-лестница») шёл в `stoneIds` → двойной
  счёт с `liftsOverhead` давал ~16 фантомных «камней» и ложный перебор каждую неделю
  (замер: «камни 42 подъёмов > MRV 22» при факте 24).

*Фикс:* `tire_flip` в списке enforce; carry-ветка режет метры (сначала длину подхода,
потом сеты); `circus_db_medley` убран из камней (он в `press_db`). Тест «circus_db_medley
не считается камнем».

### P1 — честность подписей и метрик (3)

**P1-6. Warnings объёма печатались на значениях ДО резки.** Метрики считались один раз
до `enforceCategory`, поэтому подпись «переноски 385м > MRV 380» появлялась при уже
разрезанном плане (факт 400 м) — цифры описывали план, которого больше нет.
*Фикс:* `measureWeek(wk)` вызывается повторно после резки; warnings печатаются по
фактическому плану (`m1`).

**P1-7. `reps` у переносокок врал:** подпись была «6-10» (lifts-диапазон), хотя реальные
подходы — «1 повтор × N метров». После MRV-enforce расхождение усиливалось («3×20м»
при 2 сетах).
*Фикс:* подпись строится из факта (`${finalSets}×${distanceM}м`); в finalize добавлен
`syncRepLabels()`, который синхронизирует `reps` после любой резки sets/distance/reps.

**P1-8. Кондиция дублировалась и была бессмысленной:**
- `aerobic` (Zone2 30′) шёл в `cond_day` как `sled_push_sprint` с `вес=0, reps=1,
  restSeconds=0` — «подход» из ничего;
- finalize добавлял свой tire/sled в ту же неделю **даже если билдер уже сделал cond_day**.
*Фикс:* aerobic остаётся **рекомендацией** (rationale, не «подход с весом 0»); для
alactic/lactic cond_day строится с реальными 3 подходами и отдыхом из протокол;
finalize проверяет `sessionTag === 'cond_day'` и не дублирует.

### P2 — гигиена/каноны (3)

**P2-1. Два разных `cessationDaysFor` с одной сигнатурой-ловушкой** (табличный
`(eventId, sex)` в taper.engine и числовой `(baseDays, sex)` в planner-pro) +
дубль `OPENER_SINGLE_NOTE` в двух файлах. Импорт из «не того» файла давал молча
неверное поведение. *Фикс:* числовой переименован в `cessationDaysForBase` (с
DOC-комментарием о ловушке), `OPENER_SINGLE_NOTE` остался в taper.engine как канон
(re-export из planner-pro).

**P2-2. Гэпы в таблице cessation:** `squat`/classics не были прописаны и получали
дефолт 5 (замер Winwood: squat 6.6±3.2 д). Добавлены `back_squat/front_squat/squat/
hack_squat=6`, `bench_bar=5`, `snatch/clean_and_jerk/push_jerk/split_jerk/pause_jerk/
push_press=5`.

**P2-3. Нет sex-aware длины тейпера.** Замер Winwood 2018: **стройные женщины таперят
ДОЛЬШЕ (9.5±5.5 д vs 8.3±4.8)**, а в ТА — **КОРОЧЕ (5.3±1.8 vs 8.6±4.6)**; старый
`cessationDaysFor(sex)` давал «женщине всегда меньше» — верно только для ТА.
*Фикс:* NEW `taperLengthDaysFor(mode, sex)` (8/5 для ТА М/Ж, 8/10 для стронга).

## §6. Границы (честно — что осталось и почему)

1. **Живой тест на устройстве недоступен** — только юниты/пробные дампы.
2. **Per-event cessation** — из одного self-report survey (Winwood n=454), хотя его
   порядок воспроизведён независимым SR 2026. В UI подписано «practice», не «RCT».
3. **Йок — наименее изученное событие** (Hindle 2019): переносы других событий на йок
   остаются экспертной экстраполяцией; в приложении это видно как `STRONG_FALLBACK_COEFF`
   с бейджем «замена без снаряда ×коэффициент».
4. **Deload-каденция** 4/7/11 — внутри observed диапазона Rogerson (1–12, ср 5.6),
   но для стронга в survey было всего 9 атлетов; не выдаётся за канон.
5. **Плотность 5/6-дневных стронг-сплитов** — новая потребность (Amdi 2026), паттерны
   спроектированы под `overhead×2`; калибровка по реальному восстановлению — за
   пользователем (нет данных обратной связи в зоне).
6. **Болгарский daily-max** остаётся согласием пользователя (`cycleConsent`) — гейт
   fail-closed в билдере, раннер — UX-фильтр (проверено, AGENTS-история).
7. **Коммита/пуша нет** (в worktree чужие WIP: arm, cardio, nutrition).
8. **Файлы других агентов не тронуты** — `git status` подтверждает scope.

## §8. Найдено и исправлено (раунд 2)

### P1 — UI врал цифрами (4)

**R2-1. Cessation в плане ≠ cessation в UI.** PlanView печатал сырое
`TAPER_CESSATION_DAYS[e.id]` («cess 7д» для йока), а билдер считает через
`cessationDaysFor(id, sex)` = **8 дней для мужчин** (таблица +1 по полу).
Подпись обещала на день меньше, чем реально применялось. Доказано пробой:
`raw 7 vs male 8`, `raw 5 vs male 6` (лог). *Фикс:* UI зовёт ту же функцию,
что и билдер.

**R2-2. Стратегия попыток в UI — хардкод «85/92/98 vs 90/97/102%».**
Фактическая таблица `SM_STRATEGY_PCT`: conservative 85/92/98,
balanced **88/95/100**, aggressive 90/97/102. Подпись показывала несуществующую
пару цифр и не соответствовала выбранной стратегии. *Фикс:* проценты берутся
из `SM_STRATEGY_PCT[strategy]`.

**R2-3. «taper Winwood 8.6д» — хардкод в подписи контеста.** Для ТА измерено
**8.0±4.4 д** (Pritchard), для женщин — другие значения (см. P2-3 раунда 1).
*Фикс:* `taperLengthDaysFor(plan.mode, sex)`.

**R2-4. Gantt-нота описывала несуществующую математику:** «объём ×0.45/0.65».
Факт: внешний тапер ×0.55→×0.45, toro4 ×0.65, Winwood W-1 ×0.45/int ×0.50,
W-2 ×0.55/int ×0.75. *Фикс:* нота приведена к реальным числам.

### P1 — данные циклов (2, настоящие дефекты контента)

**R2-5. `ss-sm-base-12` недели 3/7/11: ДВА `ohp` в одной сессии.**
«Жим стоя со стоек x5» и «Жим сидя с пола (Z-press)` имели один id → второй
слот затирался (вес/роль/подпись), сессия теряла упражнение, а план выдавал
7 записей при 6 уникальных. *Фикс:* Z-press → `ohp_seated` («Армейский жим
сидя» — реальная запись каталога).

**R2-6. `ss-sm-cube-12` недели 2,3,5,6,8,9: ДУБЛЬ ивента в event_day.**
Третий ивент был хардкодом `atlas_stone_load`, а ротация `EVENTS[(w-1)%3]` /
`EVENTS[w%3]` уже могла выдать камень → дубль id (слот затирался). Замер
пробой: 6 недель с дублем. *Фикс:* третий ивент = оставшийся из ротации
(`EVENTS.find(e => e.id !== ev.id && e.id !== ev2.id)`).

### P1 — проводка wizard (2)

**R2-7. Согласие на daily-max (`cycleConsent`) утекало при перезагрузке.**
UI прятал гейт только до ремонта — после F5 пользователь снова упирался в
заблокированный болгарский цикл, хотя уже соглашался. *Фикс:* персист
`he_ss_cycle_consent_v1`.

**R2-8. Окно ACWR считалось по порядку ВСТАВКИ ключей, не по дате.**
`Object.values(daily).slice(-28)` — при записях дневника не по порядку
(ручной ввод/импорт) «последние 28 дней» брали произвольный срез: ACWR мог
