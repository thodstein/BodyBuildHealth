# План доработки планировщика питания — «профессиональный диетолог бодибилдера» (Aug 31 2026)

Полный аудит текущего состояния и план работ. База: `IndividualPlanContext.tsx` (~3.4k строк),
`meal-plan-engine.ts` (проверяемое ядро, `@ts-nocheck` снят), полная карта настроек в
`IndividualPlanSettings.tsx` (~2.7k строк). Область IndividualPlan: 527/527 тестов зелёные, tsc 0.

---

## Часть 0. Текущее состояние (что уже «профессионально»)

Уже сделано и не трогаем (зафиксировано тестами): единая целевая арифметика `buildDayTargets`
(наука → ккал, белок-пресет → оверрайд, угли → остаток в диетпотолке, Atwater); квоты реализма
(гарниры ≤3/день, орехи/масла/яйца/фрукты, порошок ≤2); MPS-физиология (лейцин ≥2.5 г, pre-sleep
28 г, пери-бюджет по LBM); recipe-mode двухпроходный ±15% гейт; разнообразие между неделями месяца;
брифинг; экспорт тренеру; распознавание продуктов сетей (retail-search).

**Проблема не в движке — в слое настроек и в разрозненности «профессиональных» функций V2 вокруг ядра.**
527 тестов покрывают генерацию, но не семантику настроек.

## Часть 1. Аудит настроек — что избыточно / противоречит принципам

Проанализирована каждая карточка настроек против фактической генерации (`Context` + `meal-plan-engine`).

### 1.1. Четыре параллельных механизма «периодизации углеводов» (P0 — главное противоречие)

В коде одновременно живы:
- `cyclingMode` (`CycleType`: macro/butch/cheatmeal/carbload) — **живой**, читается генерацией
  (`Context:2657–2684`) и отображается (`Settings:1177`, `2556+`);
- `dietPauseMode` (`refeed/flex_80_20/periodization_2_1/diet_5_2`) — **живой** (`Context:617`,
  `2670–2684`);
- `periodizationEnabled` (волна 2+1) — **живой** (`Context:350`, `2723`);
- `carbPeriodization` (v6: none/refeed/carb_cycle/butch/flex_80_20/two_one/five_two/wave) — **новый
  единый селектор**, но в генерацию доезжает лишь частично (`Context:2822` `carbAutoCycle` только
  для `carb_cycle`/`butch`).

UI уже показывает новый селектор «Периодизация углеводов» (8 опций), но параллельно отображает
старые `cyclingMode` и `dietPauseMode`, а ядро по-прежнему ветвится по старым полям. Пользователь
выбирает «БУЧ» в одной карточке — генерация читает другую переменную. Классика «кнопка есть —
эффекта нет или не тот».

### 1.2. `nutrLevel` мёртв, но отображается как живой

v6 (`types.ts:53-56`) заменил `nutrLevel` на `proteinPreset`, но:
- `Settings:1173–1176` всё ещё рендерит «Уровень +15%/+30%/+50%» (умножая `effective*` **только
  в подсказке**);
- `NUTRITION_LEVELS` (mult 1.0/1.15/1.3/1.5) остаётся в импортах и рендере.

Подпись «план будет на 30% больше» — ложь; реальный белок задаёт `proteinPreset`, ккал — surplus.

### 1.3. Два переключателя «рецепты»: `useRecipesInPlan` vs `generationMode`

- `generationMode: 'products' | 'recipes'` — два больших селектора в шапке (авторитетный путь);
- `useRecipesInPlan` — отдельный тумблер «🍲 Рецепты в рационе» (`Context:345`, `2908` — всё ещё
  читается как `useRecipesInPlan || _genRecipes`).

Два источника истины для одного решения.

### 1.4. `goal` и `phase` дублируют друг друга на 5 из 9 значений

`GOALS` и `PHASES` пересекаются по cutting/maintenance/recomp/fat_loss/post_cut. `autoGoal`
выводится из `phase`, но обе карточки показываются рядом. Пользователь ставит `goal=mass` +
`phase=pct` → противоречащие фарма-правила.

**Принцип проф. планировщика**: цель (масса/сушка/поддержка/рекомп) — намерение атлета; фаза
(курс/ПКТ/мост) — фарма-контекст, который **только уточняет** цель. Сегодня они конкурируют.

### 1.5. `histamineSensitive` и `intolerances.lowHistamine` — два тумблера одной вещи

- `histamineSensitive` в карточке «v2 Скоринг» (`Settings:681`);
- `lowHistamine` в «Подбор продуктов» → «Непереносимость» (`Settings:1657`).

Разные карточки, разные ключи, разные ветки чтения.

### 1.6. Peak-week: легаси-селектор конфликтует с единым prep-планом

`peakWeekEnabled` + `peakWeekShowDay` (select «Show: день 0–6», `Settings:524-528`) — остаток
легаси пик-недели. Единый `bbPrepConfig` (contest-prep) живёт отдельно. Два пути «подготовки к шоу».

### 1.7. `planType` пересекает 3 других параметра

- «Кето» ↔ карб-потолок (+ `carbCapGPerKg=0` + carb-periodization) — три механизма управления углеводами;
- «Вегетарианский» ↔ `dietPrefs.vegetarian` ↔ аллергены — три механизма животного белка;
- `pMult/fMult/cMult` в `PLAN_TYPES` — «декоративны» (применяются только к карб-флору, не к целям).

### 1.8. Три «уровня качества»: `budget` + `proteinPreset` + `nutrLevel`

`BudgetLevel` (low/medium/max/enhanced) фильтрует по `bb_quality_score`; `proteinPreset`
(base/…/max) задаёт г/кг; `NUTRITION_LEVELS` (ещё «max/enhanced») мёртв. Семантическая каша «уровней».

## Часть 2. Что МЕШАЕТ статусу «профессиональный диетолог» помимо настроек

### 2.1. V2-скоринг существует отдельно от генерации
`product-usefulness-v2` (DIAAS, фазы, фарма, лабы, микро) — большой движок, но в выбор продуктов
входит только как мягкий bbScore-сигнал (эпик E1). Профильные микро-таргеты, DIAAS-цепочки приёма,
PRAL считаются **после**, не управляют составом дня.

### 2.2. Две системы «полезности» дают разные числа
`planner-reports` (tier-скоринг) vs `product-usefulness-v2` — два «health-score» дня (E3). Для
проф-уровня критично: одна цифра качества дня.

### 2.3. Микронутриенты — «текст, не действие»
Покрытие цинка/магния/калия/D3 считается, но «закрыть дефицит» работает только в
таргетинг-компоновщике (pro), не в основной генерации.

### 2.4. Компенсация дневника — только день 0
`diaryAdaptation`/rolling-компенсация применяется к первому дню; дни 1–6 строятся без учёта факта.
«План→факт→коррекция» должен быть скользящим по всей неделе/месяцу.

### 2.5. Нет «дня ног/кардио» как таргета углеводов
`heavyTrainDay` есть в Context, но не связан с целями дня (G1).

### 2.6. Женский цикл — ручной ввод, нет календаря
Календарный расчёт (средняя длина + лог) не реализован (G6). Для проф-диетологии (RED-S, железо,
энерго-доступность) — обязателен.

## Часть 3. ПЛАН доработки

Порядок: **эпики 1–3** (настройки) → **4–6** (диетология в генерацию) → **7–9** (проф-фичи).
Каждый эпик — с приёмкой и тестами. База: 527/527 зелёные, tsc 0.

### Эпик 1 — Единая «Периодизация углеводов» (P0, убрать 4→1)

**Цель**: один источник истины, ноль ветвлений по старым полям.

- **1а.** Ядро читает ТОЛЬКО `carbPeriodization` (8 опций). Снести ветки `cyclingMode`
  (`Context:2657–2684` и отображение `1177`/`2556`), `dietPauseMode` (`2670–2684`),
  `periodizationEnabled` (`2723`, `3001`). Миграция уже есть (`planner-storage.ts:86-96`).
- **1б.** Реализовать недостающую семантику в движке по `carbPeriodization`: `refeed` (×2.2 У,
  1 день), `carb_cycle` (±15%/30%), `butch` (3ВУ+1НУ), `flex_80_20`, `two_one`, `five_two`,
  `wave` — единой функцией `applyCarbPeriodization(dayBase, dayOffset, mode, trainDay)` (сейчас
  реальны только carb_cycle/butch).
- **1в.** Убрать из UI отображение `cyclingMode`, оставить только карточку «Периодизация
  углеводов»; подписи train/rest-ккал пересчитать от `carbPeriodization`.
- **Приёмка**: тест «каждый из 8 режимов меняет день детерминированно, по одному входу»;
  grep-гейт «в генерации нет чтения `cyclingMode`/`dietPauseMode`/`periodizationEnabled`». tsc 0.

### Эпик 2 — Разводка «цель» и «фаза» (P0)

- **2а.** `goal` = намерение (10 значений); `phase` = фарма-контекст (курс/мост/ПКТ/восстановление).
  Убрать из `PHASES` дубли-цели (cutting/maintenance/recomp/fat_loss/post_cut).
- **2б.** `PHASE_MULT` (`planner-targets.ts:181`) переписать: фаза **только** модифицирует белок/
  жир-гейты фарма-контекста, ккал-направление задаёт `goal`. Конфликт «goal=mass + phase=pct» →
  явное предупреждение, не молчаливое перемножение.
- **2в.** `autoGoal` перестать выводить из `phase`; убрать подсказку «фаза → рекомендованная цель»
  (`Settings:704-708`).
- **Приёмка**: инвариант-тест «один вход → одна цель, фарма-фаза не меняет направление ккал,
  только гейты»; 9 целей × 4 фаз = 36 ячеек без противоречий.

### Эпик 3 — Единые «уровни качества» (P1)

- **3а.** Удалить `nutrLevel`/`NUTRITION_LEVELS` полностью (подсказку `1173–1176`, импорты,
  Context-state).
- **3б.** Свести к двум ортогональным осям: **белок** = `proteinPreset` (1.6–2.6 г/кг), **качество
  продуктов** = `budget` (low/medium/max). Убрать 4-й уровень `enhanced` из `BUDGET_LEVELS`.
  `proteinPreset` «max» переименовать (например «Макс белка 2.6»).
- **3в.** `planType` → свести к `dietPrefs` («Стиль питания»): `keto` = низкоуглеводный профиль,
  `vegetarian` = вегетарианство, `mediterranean` = вкусовой паттерн; удалить `pMult/fMult/cMult`-
  декоративность, заменить на реальные макро-профили через `buildDayTargets` (кето → У ≤6% ккал,
  веган → растительные белки через пул). Выровнять с `dietPrefs` и аллергенами в один гейт.
- **Приёмка**: дифф-тест каждой оси (белок-пресет меняет только г/кг; budget меняет пул; стиль
  питания меняет профиль).

### Эпик 4 — Единый контур V2-скоринга в генерацию (P0/P1)

- **4а.** `product-usefulness-v2` — единственный `health-score` дня. `planner-reports.buildQualityReport`
  делегирует в v2 (E3). Убрать tier-скоринг как отдельный источник.
- **4б.** Микро-дефициты дня → prefer-пулы СЛЕДУЮЩЕГО приёма (не только пост-фактум D-23).
  Профильные микро-таргеты (женщина→Fe/Ca, курс→Mg/K, prep→…) подключить дефициты
  `analyzeDailyDiet` к выбору в `pickWeighted` (мягкий буст, не хард-фильтр).
- **4в.** DIAAS дня: при «слабом звене» приёма (лимитирующая аминокислота) — мягкий приоритет
  продуктам с полным аминопрофилем на следующем шаге сборки.
- **Приёмка**: `planner-usefulness-in-generation.test.ts` — при прочих равных дефицит цинка
  закрывается продуктом-источником (seeded); health-score дня = одно число, совпадает в карточках.

### Эпик 5 — Скользящая компенсация дневника (P1)

- **5а.** `diaryAdaptation` применяется к КАЖДОМУ дню недели по его дате (rolling), не только
  к offset 0. Прогнать `planner-diary-adaptation` по всем дням 3/7-дневной генерации.
- **5б.** Компенсация «факт вчера → сегодня» зациклить на месяце (переход между неделями без сброса).
- **Приёмка**: тест «перебор вчера → день 2 снижен, день 5 учитывает факт дня 4»; месяц без сброса
  компенсации между неделями.

### Эпик 6 — День-таргеты по типу дня (P1, ядро бодибилдинга)

- **6а.** `heavyTrainDay` + `trainingDays` → в `buildDayTargets`: день тяжёлых ног/высокого объёма →
  +20–30% углей (в пределах диетпотолка), день кардио-дефицита → −15%, день отдыха → базовое (G1).
- **6б.** Цели на приём: в шапке приёма «🎯» — задать Б/Ж/У слота (движок уже умеет target из
  формулы) (G2).
- **Приёмка**: инвариант «сумма целей приёмов = цель дня»; 7-дневная серия «Пн ноги / Сб отдых»
  даёт разные углеводы детерминированно.

### Эпик 7 — Женский модуль + календарь цикла (P1)

- **7а.** Календарный расчёт фазы цикла (средняя длина + последний лог), ручной оверрайд остаётся (G6).
- **7б.** Энергетическая доступность (`planner-ea.engine`) как сквозная карточка с кнопкой-действием
  («+250 ккал к цели»), пороги severe<20/risk<30/reduced<45 — единый источник (E4, дубль с
  `planner-female-cycle` убран).
- **Приёмка**: EA-порог у женщины-на-сушке даёт warning + действие; фаза цикла авто-синхронится
  с календарём, «ручной» перекрывает.

### Эпик 8 — Гигиена оставшихся настроек-сквозняков (P1)

- **8а.** `useRecipesInPlan` удалить → только `generationMode`.
- **8б.** `histamineSensitive` удалить/слить в `intolerances.lowHistamine` (один ключ, один гейт).
- **8в.** Легаси peak-week (`peakWeekEnabled` + селектор дня) удалить → только `bbPrepConfig`.
- **8г.** `specificity`, `lockedFoods`, `cookTime/batchCooking` в products-режиме — либо реальный
  эффект, либо удалить из UI.
- **Приёмка**: дифф-тест по каждой настройке «вкл/выкл меняет состав рациона»; grep-гейт «нет reads
  мёртвых ключей в генерации».

### Эпик 9 — Месячный план-редактор + полировка (P2)

- **9а.** Месячный план: карточка недели (ккал/объём, кнопка перегенерации недели без сброса) (G5).
- **9б.** Отчёт дня в печати (скор + флаги + покрытие).
- **9в.** Тренд качества 7/30 дней + бейдж «качество дня» (движки `daily-quality-score`/
  `day-score-trend` уже есть — остался бейдж в UI).
