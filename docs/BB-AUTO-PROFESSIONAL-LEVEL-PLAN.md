## Общая оценка

Кодовая база очень сильная: MEV/MAV/MRV, dose-aware PED, tradeoff-специализация, prep-движок
(по содержанию глубже PL: суммарный карб-бюджет Escalante, SGLT1, per-muscle taper), факт-фидбек,
safety-скор. **Главный системный разрыв:** несколько «про-функций» реализованы декоративно и не влияют
на фактическую загрузку плана + нехватка наглядности + незамкнутые обратные связи.

# ФАЗА 0 — НОВЫЙ ШАГ: фактическое внесение весов по всем используемым упражнениям

> **Мотивация (от пользователя):** текущий шаг «2 PED+Вес» позволяет вводить только рабочие максимумы
> по ~10 группам мышц (`bbWorkMax`: chest/back/quads/…). Движок выводит вес каждого упражнения формулой
> `weight = workMax[мышца] × BRZYCKI × intensityMult × поправка_оборудования` (жим наклон 0.85, машина 0.75,
> кабель 0.80 и т.п. — `weightForRepMax`, bb-builder:828). Для упражнений вне группы (машинные, изоляции,
> редкие) и для реальных отклонений от формульных множителей это **не отображает действительности**, и
> **тоннаж тренировки получается «кривой»**. Существующая per-exercise система (`workmax-exercises.ts`,
> `training.workMaxByExercise`, ~62 упражнения в 10 категориях) **не подключена к BbAutoConstructor**
> (он использует только `bbWorkMax` по мышцам).

## Цель шага

Дать пользователю ввести **фактические рабочие веса по каждому упражнению, реально присутствующему
в сгенерированном плане**, и пересчитать все сеты/тоннаж/нагрузку плана от этих реальных значений,
а не от формульной экстраполяции по группе мышц.

## Почему шаг должен идти ПОСЛЕ генерации плана

Чтобы перечислить упражнения, сначала нужен собранный план (`builtPlan.weeks[].sessions[].exercises[]`).
Это шаг **обратной калибровки весов**, поэтому он не может стоять до сборки (как «2 PED+Вес»).

## Точка вставки (обоснование)

**Между `plan` и `quality` — новый шаг `weights`.**

Текущий порядок: `params → ped → split → plan → quality → adjust → contest → annual → tools`.

- Шаг `quality` называется **«Тренировочная нагрузка плана»** и считает объём/тоннаж/прогрессию.
- Шаг `adjust` («Коррекция») применяет правки весов и перестраивает план.
- Если ввести фактические веса **до** `quality`, то нагрузка/тоннаж и всё, что их использует,
  будут считаться от **реальной** картины. А `adjust` будет оперировать уже откалиброванными весами.

Новая последовательность:
```
params → ped → split → plan → [weights] → quality → adjust → contest → annual → tools
```
`weights` — единственный шаг между «собран план» и «считаем нагрузку/качество».

## Дизайн шага `weights`

1. **Перечисление упражнений плана.** Собрать уникальные упражнения из всех недель/сессий
   (`Map<exerciseId, { name, muscle, role, plannedWeight, sets }>`). Показать группой по мышцам.
2. **Ввод.** Для каждого упражнения — поле «фактический рабочий вес» (кг, дефолт = текущий плановый вес).
   Рядом — подсказка «что вы реально жмёте на этот диапазон повторов/RIR» (например «Жим лёжа 6×RIR2 →
   ваш вес ___ кг»). Возможен выбор: ввести вес для **верхнего сета** упражнения — остальные сеты плана
   пересчитываются по фазовой прогрессии/процентам от него (масштабирование к реальному, как сейчас к workMax).
3. **Применение.** Новый движок-хелпер `recalibratePlanWeights(plan, actualByExercise)`:
   - для каждого упражнения берёт реальный вес;
   - пересчитывает все его сеты по неделям/фазам (масштабируя плановую кривую к фактическому базовому сету);
   - пересчитывает тоннаж/нагрузку/прогрессию для `quality`.
4. **Персистентность.** Сохранять в `training.workMaxByExercise` (уже существует), чтобы реальные веса
   переживали пересборку и использовались следующими мезо (подключить её в `buildBb` вместо `bbWorkMax`).
5. **Обратная связь.** После применения — баннер «веса откалиброваны: тоннаж N кг, средний по плану X».
   Кнопка «⏭ Пропустить (оставить формульные)» для тех, кто не хочет вводить.

## Критерий приёмки

- Пользователь вводит фактический вес хотя бы по части упражнений → тоннаж/нагрузка в `quality`,
  `adjust`, PDF/CSV-экспорте меняются от этих реальных значений.
- `training.workMaxByExercise` заполняется и используется при следующей сборке (или при «Перестроить план»).
- Шаги нумеруются сквозной (устраняется и дубль «3»/«4» из других разделов плана).

## Доработка Фазы 0 (Sep 2 2026): современный UI ввода весов

- **Группировка по группам мышц**: упражнения сгруппированы по `muscle`, каждая группа —
  карточка с заголовком-кнопкой (💪 + название мышцы на русском + счётчик заполнено/всего),

# ФАЗА 1 — Движки: самые дешёвые правки с максимальным приростом (P0)

1. **Rep-схемы реально применить к загрузке.** `bb-rep-schemes.engine` (12 схем: GVT/FST-7/myo/DC/BFR…)
   сейчас даёт только строку rationale. `schemeToLoading` импортирован в `bb-builder:55`, но **не вызывается**.
   Внедрить `schemeToLoading(scheme) → {reps, rir, restSec, tempo}` → перезаписать reps/rest/tempo целевых
   упражнений (тяж-primary для силовых схем, памп-accessory для pump/GVT/FST-7) с сохранением инварианта cap 5 сетов.
2. **Починить `factors.acwr` в `assessReadiness`.** `bb-auto-regulation.engine:51` инициализирует `acwr:'unknown'`,
   но никогда не присваивает — авторегуляция не учитывает ACWR. Подключить `calculateACWR`/per-muscle и дать вес в скоре.
3. **Микрозагрузка (plate-step).** Двойная прогрессия даёт скачок +5% (150 кг жим → +7.5 кг, нереально).
   Параметр `plateStep` (2.5 кг базово, 1.25 кг с микропластинами, 5 кг тяжёлые compound), округление `nextWeight`
   к нему; в `double_progression` снизить +5% → +2.5% или одна пластина.
4. **Топ-сет + back-off.** Все work-сеты упражнения сейчас идентичны. В `computeLoading`/`buildSession`
   дать вариацию: первый/последний сет тяжелее (RIR ниже), остальные −10–15% (back-off), reps соответствующие.
5. **Унифицировать RIR-дрейф.** `bbRir()` (floor(phaseWeek/2)) vs `rirDrift()` (floor((weekInPhase-1)/2))
   дают разный сдвиг. Один источник, `bbRir` делегирует в него.
