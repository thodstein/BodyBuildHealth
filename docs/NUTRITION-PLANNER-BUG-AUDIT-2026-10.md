### B1. Наполнитель тарелки добавляет аллергены без проверки исключений
`meal-plan-engine.ts:4787-4796`

```ts

for (const v of vegPoolDense) {
```

Единственная проверка — «этого продукта ещё нет в приёме». Нет проверки
`excludedIds`, `allergenTags`, `healthIssues`, `intolerances`, `categoryPref`.

**Что происходит:** у пользователя с аллергией на томаты / непереносимость

**Почему это P0:** это ровно тот класс дефекта, где приложение нарушает

продукт выглядит как обычная позиция в списке.

пул (`!excludedIds.has(id) && !allergenTags.has(id) && !healthIssueIds.has(id)`),
и не добивать приём, если после фильтра пул пуст. Лучше — брать кандидатов из
`pool.vegetable` (он уже отфильтрован), а не из хардкод-массива.

### B2. «Сохранить в профиль» обнуляет `daysPerWeek` и роняет TDEE на ~20%
`IndividualPlanContext.tsx:3159` → `IndividualPlanContext.tsx:999` → `planner-targets.ts:208,216` → `ultra-calculators`/`computePalFull`

```ts
// saveToProfile, строка 3159
next.training.daysPerWeek = [0,1,2,3,4,5,6]
  .filter(d => isTrainingDayFor(next.training.schedule, d)).length;
```

`isTrainingDayFor` при `enabled === false` возвращает `false` для всех дней
(`planner-training-schedule.ts:60`). То есть **если привязка к тренировкам
выключена — в профиль пишется `daysPerWeek = 0`**.

Дальше значение читается обратно как источник истины:

```ts
// IndividualPlanContext.tsx:999
workoutsPerWeek: (() => { const d = Number(s?.training?.daysPerWeek); return Number.isFinite(d) && d >= 0 ? d : 3; })()
```

и попадает в PAL: `palCoefficient = 1.2 + workoutsPerWeek * 0.075`.

**Что происходит:** пользователь жмёт «Сохранить в профиль» → его `daysPerWeek`
затирается нулём → TDEE падает с ~1.5 PAL до 1.2 (−20%) → цели по калориям
пересчитываются вниз. Причём это **глобальный профиль**: значение подхватывают
другие экраны (Support, V7-риски, нутриент-калькуляторы).

**Исправление:** писать `daysPerWeek` только если привязка включена; иначе —
не трогать поле вообще (или писать реальное число тренировок из профиля).
Плюс: `|| 0` в `planner-targets.ts:208` не должен трактовать 0 как валидное
«нет тренировок», если поле отсутствует/испорчено.

## 2. P1 — функция не работает или числа систематически неверны

### B4. Дни тренировок сдвинуты на текущий день недели
`planner-training-schedule.ts:74`

```ts
default: {
  const pos = ((offset % 7) + 7) % 7;
  return !!schedule.weeklyDays[pos];
}
```

Контракт модуля (строки 9, 20): «offset — день от начала планирования (0 = первый
день плана)», `weeklyDays` — индекс 0 = **Понедельник**.

Но фактический вызывающий код передаёт offset **от сегодняшнего дня**:

```ts
// IndividualPlanContext.tsx:3565
const _prepDate = isoAddDays(isoToday(), offset);
// IndividualPlanContext.tsx:892
const isTrainDay = (offset) => linkToTraining && isTrainingDayFor(schedule, offset);
```

Сравните с корректной реализацией в соседнем модуле:

```ts
// planner-work.ts:40-42
const dowBase = typeof opts.dowBase === 'number' ? opts.dowBase : (new Date().getDay() + 6) % 7;
const i = ((Math.trunc(index) % 7) + 7) % 7;
return !!opts.workDays[(dowBase + i) % 7];
```

**Что происходит:** `offset = 0` всегда читает `weeklyDays[0]`, то есть
«Понедельник», независимо от реальной даты. Сегодня понедельник — поэтому
дефект не виден; в любой другой день весь тренировочный график смещается на
`(new Date().getDay() + 6) % 7` дней.

**Область поражения:** `IndividualPlanContext.tsx:892, 3647, 3678`;
`IndividualPlanResults.tsx:636, 1923`; `NutritionProCards.tsx:52, 76`;
`index.tsx:693`; `trainSig` в `NutritionPeriodizationCard.tsx:109`.
То есть неверными становятся: `isTrainingDay` дня, peri-workout приёмы,
carb periodization (тяжёлый день), карточка периодизации, Pro-карточки.

**Исправление:** добавить в `isTrainingDayFor` необязательный `dowBase`
(по умолчанию — сегодняшний день, как в `planner-work.ts`) и применять
`(dowBase + offset) % 7`. Существующие тесты вызывают функцию с offset 0..6 как
«дни от начала плана» — их нужно переписать на явный `dowBase`, иначе они
зафиксируют неверное поведение.

### B7. «🏁 Применить тапер-план ББ» срабатывает только со второго нажатия
`PeakWeekTab.tsx:299-304` → `IndividualPlanContext.tsx:663-676`

### B8. Правки из компоновщика теряются при переключении дня
`MealComposer.tsx:339-346` vs `IndividualPlanContext.tsx:1941-1947, 2301-2351`

Переключатель дня в компоновщике:

```ts
const openDay = () => {
  setPlanDays(1); setSelectedDayIndex(idx);
  const weekDay = weekPlan?.days?.[idx];
  if (weekDay) { setDayPlan(JSON.parse(JSON.stringify(weekDay))); }
  else { generatePlan(1, undefined, idx); }

```

`weekEditDay` при этом **не выставляется** (в отличие от `openWeekDayForEdit`,
который делает `setWeekEditDay(di)`). А `updateMealTime` и `duplicateMeal`
синхронизируют в `weekPlan` только при `weekEditDay !== null`:

```ts
if (weekEditDay !== null && weekPlan?.days?.[weekEditDay]) { ... }
```

**Что происходит:** пользователь открывает день 4 в компоновщике, меняет время
приёма или дублирует приём — на экране всё меняется, но в `weekPlan` не попадает.
Возврат в недельный вид — правка исчезла. Остальные правки (замена продукта,
удаление, граммы) идут через `_resolvePlanDay(dayIdx)` и **сохраняются** — отсюда
ощущение «половина правок работает, половина нет».

**Исправление:** `openDay` должен вести себя как `openWeekDayForEdit` либо
`updateMealTime`/`duplicateMeal` должны принимать `dayIdx` и писать через
`_resolvePlanDay`, как это делают соседние хелперы.

### B10. Карточка периодизации в режиме препа считает даты от старта препа, а модификаторы — от сегодня
`NutritionPeriodizationCard.tsx:112` + `:123-131` + `:135`

### B11. Потолок углеводов (8–10 г/кг) не является потолком
`meal-plan-engine.ts:3793` vs `:6608-6611` и `:6745`

Потолок применяется только к стартовому бюджету:

```ts
const _carbCeiling = _capDisabled ? Infinity : Math.max(50, Math.round(input.weightKg * _capPerKg), ...);
let _baseCarbsTotal = ... Math.min(..., _carbCeiling);
```

А корректор и финальная добивка целятся в **сырую** цель:

```ts
const _norm = normalizeMacroTargets(input.goalKcal, input.goalProteinG, input.goalFatG, input.goalCarbsG);
// ...
const _devC = input.goalCarbsG - totals.c;
if (_devC > 10) { ... }
```

А `goalCarbsG` — это `baseGoalC * dayCarbMod` (`IndividualPlanContext.tsx:3672`),

и `baseGoalC = effectiveC`, куда BB-нутришн может добавить сверху.

**Что происходит:** на «волне» карб-периодизации день выходит за потолок 8–10 г/кг,
хотя вся защита от перебора (инсулин, HV) реализована именно в этом потолке.
Комментарий на строке 6742 прямо описывает это как намеренное поведение — но
тогда потолок не выполняет функцию, ради которой он написан.

**Исправление:** прокинуть `_carbCeiling` в `_correctDayToTargets` как жёсткий
`maxCarbsG` и в добивку тоже; либо явно разделить «клинический потолок» и
«потолок волны» и не называть первое потолком.

### B12. Доли жира по приёмам не суммируются в 100%

### B16. Отсутствующий % жира подставляется как реальная LBM

в UI («оценка по весу, укажите % жира для точности»), не выдавать статус

### B24. Печать и копирование сообщают об успехе при провале
`planner-day-print.ts:91-102, 217, 225`

```ts
export function printDayReport(html: string): void {
  try {
    const w = window.open('', '_blank', 'width=820,height=900');
    if (!w) return;          // ← блокировка попапа: тихий выход, void
    ...
  } catch { /* печать недоступна — игнорируем */ }
}
```

Функция возвращает `void`, а вызывающий код проверяет `if (!ok)`, поэтому

```ts
void printPlanHtml(...).then((ok: boolean) => { if (!ok) setErrorMsg('...'); });
```

Аналогично `shareOrCopyText`: `await navigator.clipboard?.writeText(text)` при
отсутствии `clipboard` даёт `await undefined` → `true`.

**Что происходит:** попап заблокирован браузером → пользователь видит «готово»,
файла нет. Копирование не сработало → «скопировано».

**Исправление:** возвращать `boolean`/`Promise<boolean>` честно; проверять
наличие `navigator.clipboard` до вызова и иметь fallback (`textarea` +
`document.execCommand('copy')`) с реальной проверкой результата.

| жен. масса 58 кг, 2345 ккал, 6 приёмов, тренировочный день | 4.19% → 4.15% |

**B35 (новое, не исправлено).** Узкое пересечение «малый вес (58 кг) + высокие углеводы
(5.5 г/кг) + 5–6 приёмов + peri-workout окна + белок 2 г/кг» не сходится в 3%:
полы приёмов по белку (MPS ~20 г × 8 слотов) физически больше дневной цели 120 г,
из-за чего белок перебирается на +4…7 г, а углеводы недобирают ~20 г. Это
**не регрессия правок** — то же самое в авто-режиме (8.97%), поведение было и раньше.
Движок сам честно пишет «⚠ «Не сошлось»: отклонение 6.3%», а корректор улучшает до 3.75%.
Требует отдельной настройки «полы приёмов при малом весе» (как B12 — менять полы,
капы и добор вместе), иначе ломаются выстроенные инварианты. Остальные профили — ≤3%.
