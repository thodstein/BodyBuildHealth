# Нативное приложение (APK) + Telegram Mini App из одного кода

Один репозиторий, один `src/`, два артефакта:

| Артефакт | Что это | Откуда берётся |
|---|---|---|
| Telegram Mini App | `dist/`, открытый внутри Telegram | `npm run build` → Vercel (как сейчас, без изменений) |
| APK | тот же `dist/` в нативном WebView | `npm run build:native` → Capacitor → `android/` → Gradle/CI |

Любая доработка в `src/` автоматически попадает **в обе версии** следующим билдом.
Различия версий — только через platform-слой (§3), форков кода нет.

## 1. Без Studio получится такое же приложение?

Да. Android Studio для сборки **не нужна**. Studio — это IDE (редактор + эмулятор
+ визуальный отладчик). Сама сборка — это Gradle (`./gradlew assembleDebug`),
он одинаково работает локально в терминале и в GitHub Actions. CI собирает
байт-в-байт такое же полноценное APK: те же 12 Capacitor-плагинов, тот же `dist/`.
Studio понадобится, только если захотите гонять эмулятор или копаться в нативном
слое руками.

## 2. Быстрый старт

```bash
npm ci
npm run build:native        # web-билд + npx cap sync android
```

APK без Studio — два пути:

**A. GitHub Actions (рекомендуется).**
Actions → `android-apk` → Run workflow (или push тега `v*`).
Артефакт `he-debug-apk` (`app-debug.apk`) — устанавливается на телефон напрямую
(разрешить «установку из неизвестных источников»). Ни JDK, ни SDK, ни Studio
на вашем ПК не нужны.

**B. Локально терминалом (без Studio).**
Нужны только JDK 21 + Android SDK command-line tools:

```bash
# разово: поставить platform-tools, platforms;android-35, build-tools;35.0.0
cd android && ./gradlew assembleDebug
# APK: android/app/build/outputs/apk/debug/app-debug.apk
```

## 3. Как устроены отличия версий (platform-слой)

Три файла ядра, всё остальное их потребляет:

- `src/core/app-platform.ts` — детекция `telegram | native | web`.
  Порядок: Capacitor → строгий Telegram (непустой `initData`/`user`, а не просто
  наличие скрипта) → web. Плюс `getSyncIdentity()` и `getOrCreateDeviceId()`.
- `src/core/app-config.ts` — параметры версий. Общее в `BASE_CONFIG`,
  отличия только в `PLATFORM_OVERRIDES`. Код читает итог через `getAppConfig()`.
- `src/core/native-bridge.ts` — единый фасад нативных возможностей.
  Каждый метод безопасен везде: native → Capacitor, telegram → Telegram API,
  web → Web API, иначе graceful no-op. Telegram-ветки поведения не меняют.

Три способа развести версии (по нарастанию инвазивности):

**3.1. Параметр** — добавить поле в `AppConfig` + значение в `PLATFORM_OVERRIDES`:

```ts
// app-config.ts
features: { ..., coachExportPdf: true }
PLATFORM_OVERRIDES = {
  telegram: { features: { coachExportPdf: false } }, // в Mini App скрыть
  native: {},
  web: {},
};
// в коде: if (getAppConfig().features.coachExportPdf) { ... }
```

**3.2. Файл** — `Foo.telegram.tsx` / `Foo.native.tsx` + выбор без if'ов:

```tsx
import { resolvePlatformModule } from '@/core/app-config';
import { FooTelegram } from './Foo.telegram';
import { FooNative } from './Foo.native';
export const Foo = resolvePlatformModule({
  telegram: FooTelegram, native: FooNative, default: FooTelegram,
});
```

**3.3. Дизайн** — CSS под класс платформы (`applyPlatformAttributes()` ставит
`html.app-telegram / .app-native / .app-web`):

```css
html.app-native .my-block { /* только APK: расширенный PRO-дизайн */ }
html.app-telegram .my-block { /* только Mini App */ }
```

Готовый PRO-пресет APK уже задан в `src/styles.css` (`html.app-native`:
тёмно-синяя палитра, увеличенный nav). Telegram Mini App стилями не затронут.

## 4. Расширенный функционал APK (что уже встроено)

Все методы — `src/core/native-bridge.ts`:

| Возможность | APK (native) | Telegram / web |
|---|---|---|
| Хаптика `haptics()` | Capacitor Haptics | Telegram HapticFeedback → `navigator.vibrate` |
| Локальные уведомления `notifyLocal()` | LocalNotifications | ServiceWorker (`push-manager`) |
| Push с токеном `initNativePush(onToken)` | PushNotifications (FCM) | no-op (свои механики) |
| Шаринг `shareText()` | Capacitor Share | `navigator.share` → clipboard |
| Файлы `saveTextFile()` | Filesystem (Documents) + Share | скачивание `<a download>` |
| Фото `pickPhoto()` | камера/галерея (системный диалог) | `<input type=file>` |
| Устройство `getDeviceInfo()` | Device-плагин | userAgent-fallback |
| Кнопка «назад» | `setupNativeBackButton()` (подключена в `App.tsx`) | Telegram BackButton как раньше |
| Статус-бар/сплэш | `initNativeChrome()` (вызван в `main.tsx`) | no-op |
| Биометрия `authenticateWithBiometrics()` | WebAuthn platform authenticator | там же, где доступен |

Что сознательно отключено в APK (`main.tsx`): PWA-баннер и ServiceWorker —
в Capacitor WebView за сплэш/статус/пуши отвечают нативные плагины, SW там
ненадёжен. На Telegram-ветку это не влияет.

Офлайн: движки уже локальные (IndexedDB/localStorage), `watchOnline()`/`isOnline()`
из моста + очередь `sync-queue`/`processQueue()` продолжают работать; в APK к ним
добавляется нативный Network-статус при необходимости.

## 5. Auth и синк в APK

- Входа через Telegram в APK нет (неоткуда взять `initData`) — работает
  существующий fallback `auth-module.ts`: локальный профиль в IndexedDB.
- `getSyncIdentity()` отдаёт `tg_<id>` в Mini App и стабильный `dev_<uuid>`
  (`he_device_id_v1`) в APK.
- `cloud-kv.initKvSync()` включается **при каждом входе** для любой identity:
  `tg_*` → токен `tk_<sha256(VITE_CRYPTO_KEY + ':' + tgId)>`, `dev_*` → токен
  от id устройства (своё облачное пространство). Явный токен привязки
  (`saveLinkedTgToken`) главнее — устройство становится вторым экраном
  Telegram-аккаунта. RLS в `user_kv` сверяет `id` с заголовком `x-user-token`,
  поэтому device-токены работают без серверных изменений.
- Выгрузка: при сворачивании/закрытии (`appStateChange` Capacitor,
  `pagehide`/`beforeunload`), при уходе в фон (`visibilitychange`), при
  возврате/фокусе — сначала pull, потом flush; плюс интервал 30 с.
- Вручную: «🔄 Синхронизировать сейчас» в Профиль → Настройки → Синхронизация
  (`SyncLinkSection`) и иконка 🔄 в шапке (`KvSyncButton`) — flush + pull.

### 5.1 Если облако «не настроено» / таблиц нет

1. Секреты репозитория (Settings → Secrets → Actions): `VITE_SUPABASE_URL`,
   `VITE_SUPABASE_ANON_KEY` (можно publishable `sb_publishable_…`),
   `VITE_CRYPTO_KEY`. Без них шаг **Guard cloud secrets** роняет сборку —
   специально, чтобы не выпустить APK без облака.
2. Схема: выполнить `supabase/bootstrap.sql` в Supabase → SQL Editor
   (идемпотентно; создаёт `user_kv` + `link_codes` с RLS).
3. Проверка: `GET /rest/v1/user_kv?select=key&limit=1` с заголовками
   `apikey` и `x-user-token` должен вернуть `200 []` (а не `PGRST205`).
4. Пауза бесплатного проекта: Supabase усыпляет проект после простоя —
   Cloudflare отдаёт `521`, DNS может пропасть (NXDOMAIN). Лечится кнопкой
   Restore в дашборде; данные и таблицы сохраняются.

## 6. Push (FCM) — что доделать для рассылок

Уже готово: запрос прав, регистрация, `onToken` в `initNativePush()`.
Осталось (только когда понадобятся серверные рассылки):

1. Firebase-проект → `google-services.json` положить в `android/app/`
   (в git не коммитить, для CI — секрет; сборка без него работает, пуши просто
   не инициализируются — в `build.gradle` уже есть guard).
2. Сохранять токен из `onToken` на своём бэкенде.
3. Отправлять через FCM HTTP v1. Локальные напоминания (`notifyLocal`)
   работают уже сейчас без всего этого.

## 7. Подпись release и публикация

Debug-APK из CI ставится на устройство сразу. Для RuStore/Google Play нужен
подписанный release:

```bash
# разово: создать keystore (хранить ВНЕ репозитория!)
keytool -genkeypair -v -keystore he-release.keystore -alias he -keyalg RSA -keysize 2048 -validity 10000
```

Секреты репозитория (Settings → Secrets → Actions):
`ANDROID_KEYSTORE_BASE64` (base64 файла), `ANDROID_KEYSTORE_PASSWORD`,
`ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. Release-шаги уже в workflow
(`android-apk.yml` job `release`: keystore из секретов → `keystore.properties`
→ `bundleRelease` + `assembleRelease`, артефакты `he-release-aab`/`he-release-apk`;
без секретов job пропускается, debug не страдает; приёмная сторона:
`android/app/build.gradle` читает `android/keystore.properties`, которого нет
в git).

Версии: `package.json` (3.0.0) и `android/app/build.gradle`
(`versionCode 2` / `versionName "3.0.0"`) сведены; дальше поднимать парой.
PRO-палитра натива: `android/.../res/values/colors.xml` 1-в-1 с токенами
`styles-native.css` + `capacitor.config.ts` (#0a1628/#050b16).

Перед публикацией: поднять `versionCode`/`versionName` в `android/app/build.gradle`,
проверить `applicationId` (`com.healthengine.app`), иконку (`android/app/src/main/res`),
разрешения (камера/уведомления уже задекларированы плагинами), privacy policy.

## 10. Виджеты рабочего стола (только APK)

В Telegram Mini App виджетов нет и быть не может (ограничение Telegram).
В APK — 12 нативных провайдеров (`android/app/src/main/java/com/healthengine/app/widgets/`):
9 в карточке «Виджеты на рабочий стол» + «HE Быстрый сет» и алиасы
«HE Сегодня» / «HE Неделя» (те же данные календаря, фиксированный режим
день/неделя).

| Виджет | Что показывает | Работает без открытия приложения |
|---|---|---|
| HE · Проведение | упражнения назначенной тренировки (живой сессии или плана дня), прогресс подходов и тоннаж | **да** («＋» в строке — подход с весом/повторами/RIR/RPE/техникой/паузой/заметкой; «▶ Начать» / «✓ Завершить» — без открытия приложения) |
| HE · Тренировка | последняя сессия, тоннаж, счётчик недели | нет (тап открывает Тренинг) |
| HE · Таймер | таймер отдыха, пресеты 0:30/1:00/1:30/3:00 | **да** (старт/пауза/сброс, тики через AlarmManager) |
| HE · Комплаенс | % выполнения (БАДы 7д или тренировки недели) | нет (тап открывает раздел) |
| HE · Питание (3×5) | **аналитика КБЖУ кругами за день / неделю / месяц**: ккал крупно + Б/Ж/У, остаток Б/Ж/У в граммах, сводка периода, вода, **список позиций дня** | **да** (чипы «День / Неделя / Месяц»; «‹ ›» листают даты последней недели; «＋ Еда» — нативный редактор с порцией и поиском по базе продуктов; «↩» отменяет последнюю запись дня; «✕» в списке удаляет конкретную позицию; чипы недавних/избранного пишут блюдо в один тап; «−250», «+250», «+500» и «Свой» — вода; «Скан»/«Фото» открывают приложение сразу в нужном сценарии) |
| HE · Аналитика питания (двойной) | две независимые половины: своя метрика (ккал / белки / жиры / углеводы / вода) и свой период в каждой | **да** (тап по названию метрики листает её; чипы «Д · Н · М» меняют период каждой половины отдельно) |
| HE · Вода | прогресс воды дня (мл/цель, полоса) | **да** (+250 мл пишет в очередь и сразу обновляет снапшот) |
| HE · Календарь | **день / неделя / месяц**: тренировки по графику, приём БАД, фарма/инъекции и личные дела; цвет дня по главному событию | **да** (режимы, листание, фильтр типа события, отметка «сделано» у дел и «＋ Задача») |
| HE · Заметки | закреплённые/свежие заметки, прогресс чек-листов | **да** (кнопка «＋ Заметка» открывает компактный редактор) |

Как это устроено:

- WebView и виджеты не видят общий localStorage → обмен через
  SharedPreferences `he_widgets` (`WidgetStore.java`).
- JS-мост `src/core/widget-bridge.ts` (безопасен везде, вне native —
  localStorage-фолбэк): `syncTrainingWidget` / `syncWorkoutWidget` /
  `syncComplianceWidget` / `syncNutritionWidget` / `syncCalendarWidget` /
  `syncNotesWidget` / `queueWaterMl` / `queueTaskToggle` / `drainWidgetQueue` /
  `widgetTimerCommand` / `consumeWidgetLaunchTarget` / `requestPinWidget` /
  `widgetOpacity` / `setWidgetOpacity`.
- Сборка снапшотов и разбор очереди — `src/ui/native/widget-sync.ts`:
  тренировка из `workout-logger`, комплаенс из приверженности/недели,
  питание из `diary-storage-v2` + `he_water_log` (снапшот: ккал и Б/Ж/У
  факт/цель + вода + готовые агрегаты `periods` за день, неделю с Пн и месяц),
  календарь из `he_coach_planner` + график тренировок +
  БАДы + инъекции (задачи дня, диапазон `items` вокруг сегодняшнего дня для
  недели/месяца, просрочено), заметки из `he_coach_notes` (закреплённые сверху,
  прогресс чек-листа), «проведение» из живой сессии или плана дня
  (`resolveWorkoutPlan`); очередь применяется (`applyWidgetQueue`) при синке —
  вода, еда, отметки задач, `task_add`/`note_add`, `set_add`/`workout_start`/
  `workout_finish` из быстрых редакторов и кнопок виджета.
- **Цели КБЖУ на виджете = цели приложения**: `collectTargets` читает тот же
  мост плана, что дневник и hero (`readPlanTargets` → `he_plan_kbju_targets`:
  ручное КБЖУ / цель / фаза / профицит / ББ-заметка), и только без
  опубликованного плана падает на профильный `calcNutrition`. Вода планом не
  задаётся — её цель остаётся профильной. Иначе виджет писал «из 2 500 ккал»
  там, где дневник жил по целям плана (например 2 100).
- **Свежесть цифр**: правка дневника (`onDiaryChangeV2`) и публикация целей
  плана (`PLAN_TARGETS_EVENT`) пере-пушивают снапшоты с дебаунсом
  (`watchNutritionForWidgets`), а уход приложения в фон — сразу
  (`visibilitychange` → hidden). Без этого стол показывал КБЖУ прошлого синка,
  пока приложение не откроют снова.
- **План дня для «Проведения»**: `he_pl_runtime` не хранит дат, поэтому день
  выбирается по графику из `settings.training.schedule` (`weekly` / `eod` /
  `pattern`), иначе по конвенции `daysPerWeek` (3 → Пн/Ср/Пт); если графика нет —
  ротация по числу сессий ISO-недели. Подход с виджета (`set_add`) сам создаёт
  живую сессию из плана, `logSet` считает RPE = 10 − RIR, `saveActiveSession`
  пишет автосейв; «Завершить» сохраняет сессию в журнал и чистит живую.
- **Календарь подхватывает всё**: тренировки по графику и плану
  (`he_pl_runtime`), БАДы (`he_support_plan_result` + дневник
  `he_support_diary`), фарму (`he_injection_schedule` + `he_injection_diary`) и
  личные дела (`he_coach_planner`). Каждое событие несёт `kind`
  (`task|training|supp|pharma`): иконка и цвет в агенде, цвет числа в месячной
  сетке (фарма > тренировка > БАДы > дела), тап по не-делу открывает профильный
  раздел, тап по делу — переключает «сделано».
- Режим, опорная дата и фильтр календаря хранятся **per-widget**
  (`calendar_mode_<id>` / `calendar_anchor_<id>` / `calendar_filter_<id>`):
  переключение «День / Неделя / Месяц», листание, «Сегодня» и чипы
  «Всё / Дела / Трени / БАДы / Фарма» работают офлайн, без WebView.
- RemoteViews не поддерживает `EditText`, поэтому «＋ Задача», «＋ Заметка»,
  «＋ Еда» и «＋» в строке упражнения открывают `WidgetQuickAddActivity` —
  диалог поверх лаунчера. Сохранение сразу пишет элемент в очередь и
  оптимистично обновляет снапшот (без запуска основного интерфейса). Еда уходит
  как `type=food` с приёмом пищи (Завтрак/Обед/Ужин/Перекус); `applyWidgetQueue`
  приводит английские ключи (`breakfast`…`snack`) к подписям дневника, иначе
  блюдо попадало в невидимую секцию. Подход уходит как `type=set_add` с весом,
  повторами, RIR/RPE, техникой 3/4/5, паузой и заметкой — тем же набором
  параметров, что и в проведении тренировки.
- Питание на виджете — `ProgressBar` с кольцевым `layer-list`
  (`widget_ring_kcal/protein/fat/carbs.xml`): процент внутри круга задаётся
  `setProgressBar`, цвет зашит в drawable (RemoteViews не умеет тонировать).
- **Периоды питания считает JS, а не виджет**: `collectNutrition()` отдаёт в
  снапшот `periods { day, week, month }` — суммы ккал/Б/Ж/У/воды и число дней
  с записями (`days`, `waterDays`). Неделя — с понедельника, месяц — с 1-го
  числа; среднее в день делится на число дней **с записями**, чтобы пустые дни
  не занижали результат. Период виджета 3×5 хранится per-widget
  (`nutrition_period_<id>`), у двойного — по половине
  (`nutrition_panel_period_<id>_<part>`, `nutrition_panel_metric_<id>_<part>`),
  переключение идёт broadcast-действиями провайдера без WebView.
  В неделе и месяце кольца и проценты показывают **среднее в день** (сумма за
  30 дней с дневной целью несравнима), а подпись — сумму и число дней.
- «＋ Еда» в быстром редакторе — тот же набор полей, что в дневнике: название,
  ккал, Б/Ж/У на порцию, **порция в граммах** и приём пищи; пустая порция = 100 г,
  плюс поиск по базе продуктов. Очередь нормализует порцию так же: пустое или
  битое `qty` — 100 г, больше 5000 — обрезается (как поле «Порция»); раньше
  `Math.max(1, 0)` давал запись «1 г».
- **Приёмы пищи — те же, что в дневнике**: `collectNutrition()` кладёт в снапшот
  `meals` (пресеты `MEAL_PRESETS` плюс свои из `he_custom_meals`), и редактор
  еды строит из них прокручиваемый ряд чипов. Раньше было четыре кнопки, и
  «Полдник», «До тренировки» или свой приём записать с виджета было нельзя —
  блюдо уезжало в «Перекус». Приём по умолчанию (`mealForNow`) считается по тем
  же границам, что в дневнике (5–11 завтрак, 11–16 обед, 16–22 ужин, иначе
  перекус): прежние 11/15/18/23 отправляли еду в 17:00 в «Перекус», а в два
  часа ночи — в «Завтрак». Копии списка в Java (`MEAL_ORDER` в провайдере,
  `DEFAULT_MEALS` в редакторе) сверяет тест №49: единый источник всё равно TS.
- **Список дня, даты и быстрые чипы**: `collectNutrition()` кладёт в снапшот
  `days` — семь последних дней с итогами и плоским списком позиций; у каждой
  записи есть адрес `meal` + `index`, поэтому «✕» удаляет именно эту строку
  (`type=food_remove` с `date`/`meal`/`index`), а не «последнюю вообще». Сам
  список — `ListView` через `NutritionItemsWidgetService`
  (`BIND_REMOTEVIEWS`), обычный RemoteViews прокрутку не умеет. Стрелки «‹ ›»
  меняют `nutrition_dayoffset_<id>` (0…−6): в прошлом дне показываются итоги и
  удаление, а кнопки добавления скрыты — иначе запись молча ушла бы в сегодня.
  Если адрес «✕» не сошёлся с дневником (запись уже убрали в приложении),
  не удаляется ничего: «последнюю вообще» снимает только «↩» без адреса.
  Чипы `quick` (избранное → недавние блюда) пишут `type=food` в один тап; на
  виджете показываются первые три из шести — больше в строку не влезает.
  В `PendingIntent` чипа лежит **сам продукт** (JSON), а `index` остался только
  для обратной совместимости: тап по устаревшей картинке раньше читал
  `quick[index]` из свежего снапшота и записывал не то блюдо, что нарисовано.
  Чип несёт `foodId` (избранное хранит id, недавние берут его из записи
  дневника), поэтому добавленное с виджета блюдо дневник узнаёт как тот же
  продукт.
- **Каталог продуктов для поиска** пишется отдельным ключом
  (`WidgetStore.KEY_FOODS`, мост `syncNutritionFoods`) один раз на версию
  `FOOD_DB` — ~700 позиций через мост на каждую правку дневника гонять незачем.
  В редакторе еды поиск подставляет КБЖУ на 100 г, а при смене порции значения
  пересчитываются пропорционально (`catalogPer100`); уже введённая порция при
  выборе продукта сохраняется (200 г остаются 200 г, а не превращаются в 100),
  а ручная правка любого из четырёх чисел пересчёт отключает — дальше цифры
  считаются своими. Каталог несёт `id` продукта: выбранный продукт уходит в
  очередь `food` с `foodId`, и дневник узнаёт его как тот же продукт из
  `FOOD_DB` (избранное, состав, «полезность»); переписанное руками название id
  сбрасывает — это уже не тот продукт. Версия каталога получила префикс `v2`:
  каталог, записанный без id, пересылается один раз.
- **Отмена с виджета** (ошибочная порция): нативный редактор кладёт запись в
  `lastFood` снапшота вместе с адресом (день + приём + индекс), по ней рисуется
  «↩» → очередь `type=food_remove` с этим адресом. `applyWidgetQueue` снимает
  ровно адресованную запись, а не «последнюю вообще»: иначе при добавлении в
  «Завтрак» после «Ужина» отмена снесла бы чужую еду. Круги уменьшаются сразу
  (`optimisticRemoveItem`). Старый снапшот без адреса — прежний путь: последний
  элемент последнего непустого приёма (порядок приёмов общий — как в дневнике,
  `MEAL_PRESETS`). «−250» — очередь `type=water_remove`:
  `removeWater` не уходит ниже нуля и снимает день из `waterDays`, если вода
  обнулилась. «Свой» открывает тот же нативный редактор с полем «Объём, мл» и
  пишет `type=water`.
- **Агрегаты между синками остаются согласованными**: добавление еды сразу
  поднимает КБЖУ, а первая запись дня добавляет день в счётчики `days` всех
  периодов (`shiftPeriodDays`); снятие последней записи дня убирает его оттуда
  же. Вода — так же: `waterDays` недели и месяца меняются, когда вода дня
  обнулилась или появилась впервые. Без этого среднее за неделю/месяц делилось
  бы на прежнее число дней, пока приложение не откроют.
- **Виджеты и разметка**: в `widget_nutrition_panel.xml` нельзя ставить обычный
  `<View>` — лаунчер инфлейтит только `@RemoteViews.RemoteView`-классы, и
  `android.view.View` роняет весь виджет в «Не удалось загрузить». Разделитель
  половин — `ImageView` с фоном-линией.
- «Скан» и «Фото» требуют WebView-движков (база штрихкодов, OCR этикетки),
  поэтому виджет ставит one-shot target `nutrition_scan` / `nutrition_photo`:
  JS ведёт в «Питание», кладёт флаг в `sessionStorage` (`he:nut-open`) и
  диспатчит `he-nutrition-open`; экран открывает сканер или камеру
  распознавания (`useLabelScan`), даже если смонтировался позже.
- **Прозрачность фона** — одна настройка на все виджеты (100 / 85 / 70 / 50 %)
  в карточке «Виджеты на рабочий стол». Хранится в `WidgetStore` (`widget_opacity`),
  подставляется при сборке `RemoteViews` через `WidgetStyle.apply()` готовым
  drawable (`widget_bg_a85/a70/a50`), потому что альфу у drawable в виджете
  не поменять. Кнопки `setWidgetOpacity` / `getWidgetOpacity` в плагине
  перерисовывают все провайдеры сразу.
- Тап по виджету открывает `MainActivity` с `WIDGET_OPEN`-intent →
  one-shot target в `WidgetStore` → JS забирает через `getLaunchTarget()`
  на уровне `App` (не только Главной, чтобы возврат на последнюю вкладку не
  «съедал» диплинк) и ведёт в раздел (`DashboardScreen.native`).
- Синк виджетов запускается не только при монтировании Главной, но и на
  `visibilitychange`/`focus` APK (`App.tsx`): данные не ждут открытия
  конкретной вкладки.
- Таймер полностью автономный: состояние + `endAt` в `WidgetStore`,
  тики каждую секунду через `AlarmManager` (`setExactAndAllowWhileIdle`,
  permission `SCHEDULE_EXACT_ALARM`; без гранта тикает неточно, но
  самокорректируется по `endAt`).

Как установить (для пользователя):

1. Главная → «Телефон · APK» → «Виджеты» → «📌 На стол»
   (системный диалог закрепления, Android 8+). Если лаунчер не поддерживает —
2. вручную: долгое нажатие по пустому месту стола → «Виджеты» →
   «Health Engine» → перетащить нужный.
3. Данные подтягиваются при каждом открытии Главной; кнопка
   «🔄 Обновить данные виджетов» — принудительно.
4. Прозрачность фона — в той же карточке: 100 / 85 / 70 / 50 %, применяется
   ко всем виджетам сразу.

## 11. Биометрия и другие функции (как включить)

Всё включается из APK: Главная → «Телефон · APK». В Telegram эти карточки
не отображаются.

**Биометрия** (`BiometrySetupCard`, механика `native-bridge.ts`,
без новых native-зависимостей — WebAuthn platform authenticator):

1. Сначала в самом Android: Настройки → Безопасность → Блокировка экрана
   (PIN/пароль) → добавить отпечаток или лицо.
2. В приложении: «🔐 Биометрия» → «Включить вход по биометрии» →
   подтвердить отпечатком (первый вызов регистрирует ключ
   `he_webauthn_cred_v1`, дальше — проверка им).
3. Опционально: «🔒 Блок входа» — приложение показывает экран
   разблокировки при запуске и при возврате из фона (`App.tsx`,
   только native; если биометрия стала недоступна — вход не блокируется).
4. «Проверить» — тест без изменения настроек; «Выключить» — удаляет ключ.

**Остальное** (`NativeFeaturesCard`, все методы уже были в `native-bridge.ts`):

- Уведомления: кнопка «Проверить» шлёт тестовое через `notifyLocal()`
  (там же запрашивается разрешение). Нет пуша — Настройки Android →
  Приложения → Health Engine → Уведомления. Серверные FCM-рассылки —
  по §6 (нужен `google-services.json` + бэкенд).
- Камера/галерея: кнопка «Проверить» открывает системный диалог
  `pickPhoto()` (камера/галерея). Используется в дневниках (фото тела,
  чеков, анализов).
- Шаринг: кнопка «Проверить» открывает системный диалог `shareText()`;
  файлы (`saveTextFile`) уходят через Filesystem + Share.

**Напоминания** (`RemindersCard`, `core/reminders.ts`, id 42000+):

- Взвешивание утром — ежедневный повтор в выбранное время.
- Приёмы пищи — завтрак/обед/ужин, три своих времени.
- Тренировка — выбранные дни недели + время (недельный повтор).
- Всё локально через `scheduleDailyReminders`/`scheduleWeeklyReminders`
  (`@capacitor/local-notifications`), без Firebase и без интернета.
  Напоминания курса живут отдельно (id 41000+, `PharmaCourseScreen`).

**Проверка обновлений** (`UpdateCheckCard`): кнопка «Проверить» в §4.4
диспатчит `he:check-updates`; сам поток (фид GitHub → скачивание →
установщик) остаётся в `AppUpdateBanner`, поэтому ручная проверка
игнорирует суточное окно и честно сообщает «последняя версия»/«доступна X».

**Статус облака** (APK + TG): «☁️ Синхронизировано в 21:40» в профиле,
иконка в шапке показывает ⟳ (идёт обмен) / ⚠️ (нет связи), полоса
`KvErrorBanner` появляется после 15 c непрерывной ошибки, «⬆️ Выгрузить всё
заново» перезаписывает облако локальной версией (лечит рассинхрон).

**Быстрый ввод в дневнике**: «↩ Как вчера» / «↩ Повторить вчерашний день»
переносит приёмы предыдущего дня аддитивно; дубликаты по имени и количеству
пропускаются (`diary-quick-repeat.ts`).

Что НЕ требует включения: хаптика, статус-бар/сплэш, кнопка «назад»,
офлайн-режим — работают из коробки в APK.

## 12. Самообновление APK без сторов

APK запекает `dist/` в момент сборки, поэтому сам ничего не подтягивает.
Лента обновлений — GitHub Releases, проверка — при каждом запуске APK:

1. `AppUpdateBanner` (только native, в TG/web — null) читает установленную
   версию через `App.getInfo()` и спрашивает фид `fetchLatestRelease()`
   (по умолчанию `.../releases/latest`, оверрайд — `VITE_APP_UPDATE_URL`).
2. Версия новее + не пропущена → баннер «⬇ Обновить» (проверка не чаще
   раза в сутки, пропуск версии запоминается в `he_app_update_v1`).
   Неудачная проверка суточное окно НЕ съедает: нет сети/лимит GitHub —
   повторим при следующем запуске (раньше одна осечка откладывала авто-
   обновление на сутки).
3. Скачивание — `DownloadManager` в приватный external-files
   (плагин `AppUpdater`, `MainActivity`), установка — системный установщик
   через FileProvider. Разрешение `REQUEST_INSTALL_PACKAGES` в манифесте;
   без гранта «неизвестные источники» баннер ведёт в настройки.
4. CI публикует APK в Release по тегу `v*` **и по ручному запуску**
   workflow `android-apk` (job `publish`): подписанный `app-release.apk`
   приоритетом, иначе debug. Движок предпочитает подписанный ассет
   (`pickApkAssetUrl`).

Критично — единая подпись: Android ставит обновление поверх только при
совпадении подписи. CI подписывает ВСЕ сборки одним ключом
(`build.gradle`: debug тоже берёт `signingConfigs.release`, когда есть
`keystore.properties`; без него локально — обычный debug-ключ). Разовый
переезд debug→подписанная сборка = переустановка с переносом данных,
дальше обновления встают поверх молча.

`versionCode` считается из версии (`major*1e6 + minor*1e3 + patch`,
`scripts/apk-version.mjs` → 3.0.15 = 3000015). Раньше он брался из
`build.gradle` (+1 для ручного запуска), но `apply` пишет файл только в
рабочую копию CI и не коммитит его → все ручные релизы выходили с одним и
тем же code, а тег-пуш собирал code ниже установленного, и Android
отклонял установку как downgrade.

## 12.1. Быстрое обновление без переустановки (OTA, как в TG)

Полный APK нужен только при смене нативного слоя (плагины/Java/манифест).
Обычные правки `src/` подтягиваются файлами внутрь установленного APK
(плагин `@capawesome/capacitor-live-update@8`, self-hosted, без облаков):

1. CI кладёт в каждый тег-релиз `web-bundle-<tag>.zip` (zip `dist/`,
   корень = index.html) рядом с APK.
2. Баннер при совместимом мажоре (JS 3.x на нативе 3.x) предлагает
   «⚡ Быстрое обновление»: `downloadBundle → setNextBundle` → «🔄 Перезапустить».
   Мажор разошёлся или .zip нет — остаётся только полный APK.
3. `readyTimeout: 10000` + `markAppReady()` в `main.tsx`: не стартовал за 10с —
   авто-откат на встроенный dist. Данные (IndexedDB/localStorage) общие,
   бандл меняет только код.
4. Откат вручную: `resetToBuiltInBundle()` из `src/core/live-update.ts`.
5. Бандл в данных переживает установку APK, поэтому на старте решается по
   версиям (`shouldResetOtaBundle`): бандл новее APK — это и есть обновление,
   не трогаем; равен/старше — устарел, `resetStaleOtaBundle()` возвращает
   встроенный dist и перезагружает WebView (не больше одного раза на версию
   APK). По метке сборки `__APP_BUILD__` так делать нельзя: она меняется и у
   самого OTA-бандла — каждый применённый бандл сбрасывался при первом же
   перезапуске, «быстрое обновление» откатывалось само.

```bash
npm run release:apk                 # 3.0.0 -> 3.0.1: версии, коммит, тег v3.0.1, push
npm run release:apk -- --version 3.1.0   # конкретная версия
npm run release:apk -- --dry-run    # только показать план
npm run release:apk -- --no-push    # версии и тег локально, push вручную
```

Скрипт `scripts/release-apk.mjs` поднимает `versionCode` (+1) и `versionName`
в `android/app/build.gradle`, версию в `package.json`, коммитит **только эти
два файла** (посторонний WIP в дереве не попадает), ставит аннотированный тег
`vX.Y.Z` и пушит ветку с тегом. Дальше CI (`android-apk.yml`, триггер
`push: tags: v*`) собирает и публикует GitHub Release: `app-release.apk`
(или `app-debug.apk`) + `web-bundle-<tag>.zip` для OTA. Телефон сам покажет
баннер обновления.

### Ручная сборка на GitHub (Actions → android-apk → Run workflow)

Ручной запуск тоже публикует Release — job `publish` больше не привязан
только к тегам (раньше `workflow_dispatch` шёл с `refs/heads/main`, и
публикация молча пропускалась).

- Поле **version** можно оставить пустым: CI возьмёт **+1 патч** от более
  свежего из `package.json`, последнего GitHub Release и тегов на `origin`
  (v3.0.5 → v3.0.6), пропишет его в `versionName` перед сборкой и создаст
  тег/релиз сам. Явная версия должна быть **выше** последнего релиза —
  иначе телефон не увидит обновление (`App.getInfo()` сравнивается с `tag_name`).
- Поле **publish** = `false` — собрать APK только как артефакт, релиз не трогать.
  Публикация ручного запуска разрешена только с `main` (с ветки — только
  `publish: false`, чтобы WIP-код не стал «последним релизом» для всех).
- `versionCode` ручной сборки = текущий в `build.gradle` + 1; тег создаётся
  на коммите запуска (`gh release create --target`), а не на «default branch».
- `package.json` в репозитории CI не меняет. Поэтому `release:apk` считает
  следующую версию от максимального тега на `origin` — занятый ручной
  сборкой номер он не возьмёт.

### Без ключа сборка не запускается

`build`-джоба тоже требует стабильный ключ: если `ANDROID_KEYSTORE_BASE64`
не задан, она падает с понятной ошибкой, а не собирает APK с одноразовой
debug-подписью раннера (такой APK нельзя обновить поверх — подпись у каждого
запуска новая). Четыре секрета — §7.

### Почему keystore не кладём в проект и не «берём из секретов»

Секреты Actions в GitHub **write-only**: их значение нельзя прочитать ни
через API, ни через `gh`, ни из репозитория — только перезаписать. Поэтому
«вытащить `ANDROID_KEYSTORE_BASE64` в локальную папку» технически невозможно,
и это правильно: ключ должен жить в одном месте — в секрете.

Локальная копия нужна ровно в одном случае — если вы собираете APK на своей
машине и хотите, чтобы он вставал поверх CI-сборок. Тогда положите файл
самостоятельно (он в `.gitignore`):

```bash
# android/app/he-release.keystore — тот же файл, что лежит в секрете
# android/keystore.properties:
storeFile=he-release.keystore
storePassword=<пароль>
keyAlias=<алиас>
keyPassword=<пароль>
```

После этого `assembleDebug` локально тоже подписывается release-ключом, и
локальные сборки взаимозаменяемы с CI.

### Разовая миграция, если APK собран локально без keystore

CI подписывает всё release-ключом, локальная сборка без `keystore.properties`
— debug-ключом (`CN=Android Debug`). Android не ставит обновление поверх
другой подписи (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`), при этом старая версия
остаётся на месте — снаружи это выглядит как «правок нет». Проверить подпись
установленного APK:

```bash
# Windows: build-tools из SDK
apksigner.bat verify --print-certs <путь к apk>
```

Переезд делается один раз: удалить приложение (или установить APK той же
подписью — например, собранный локально), дальше все обновления из GitHub
встают поверх молча, а обычные правки `src/` вообще не требуют переустановки
(§12.1).
