# ББ-диагностика — полный аудит и план исправлений (2026-11)

> **Статус:** план на утверждение. Код **не менялся** — аудит сделан только чтением.
> **Объём:** 37 подтверждённых дефектов (6 P0 / 16 P1 / 15 P2) + 8 продуктовых пробелов.
> **Baseline (до правок):** `npm run type-check` — 0 ошибок; кластер тестов диагностики — **219 passed**
> (`bb-diagnostics-honesty` 49, `bb-diagnostics-pro3` 31, `bb-diagnostics-max-pro` 94, `bb-diagnostics-hub` 45).
> Вывод: все найденные дефекты лежат в **непокрытых** кейсах — тесты зелёные и «разрешают» их.

## 0. TL;DR — что реально сломано

1. **Хаб врёт «всё хорошо» на пустых данных.** Готовность возвращает «🟢 Зелёный: можно по плану, включая добивки» на совершенно пустом скрининге, симметрия показывает «100 / пропорции в норме» без единого замера, стимул — «сбалансирован» без плана. Причина у готовности — `Number(null) === 0` внутри `num()`, при том что в шапке файла прямо написано «нет данных больше не выдаётся за зелёный».
2. **Мост «диагностика → ББ-авто» в ряде сценариев молча выбрасывает payload, но рапортует «✓ Применено».** Два подтверждённых пути: (а) `planner-bridge` подставляет чужой `targetCycleId`, конструктор делает `return`, а `clearPlannerApply()` уже сработал; (б) орто-скрин шлёт payload без `groups/weakPoints` — гейт приёмника его отбрасывает и вдобавок снимает ранее навешенные орто-гарды.
3. **Инъекция коррекций в план обходит save-guard и затирает несохранённые правки конструктора.** Пишет `he_bb_plan_saved` напрямую, шлёт `new Event('he-bb-plan-saved')` без `detail`, конструктор на это событие **безусловно** заменяет `builtPlan` из хранилища.
4. **Треть отчёта не считается.** `verification` структурно ≤ 0.70 (хаб всегда отдаёт `hasVbt: false`), а ACWR-пол и ACWR-штраф мертвы, потому что в скоринг уходит `perMuscleAcwr: null` при том, что ACWR посчитан строкой выше.
5. **Ключи аудита плана не совпадают с ключами хаба.** `planAudit.byMuscle` — канонические мышцы, а хаб ищет по гранулярным зонам (`chest_upper`, `delt_mid`, `back_width`) → lengthened / singleAngle / missingStrict / avgSfr для приоритетных зон **всегда пусты**.

## 2. P0 — дефекты честности (числа врут пользователю)

### BB-D-01 · P0 · «Зелёный: можно включая добивки» на пустом экране
- **Где:** `src/engines/bb/bb-readiness.engine.ts:33-45`; хаб: `BBDiagnosticsHub.tsx:508-509`, `:573`, `:930`, `:1200`.
- **Что:** `num()` = `Number(v)`, а `Number(null) === 0` и `Number('') === 0`. Поэтому `pain = 0`, `loss = 0`, `danger = 0` — и `tested` становится `true` (`pain >= 0`). Дальше score 0 → `green` с текстом «включая добивки». Хаб при этом **всегда** шлёт `pain010: null, vbtLossPct: null` (4 разных места вызова).
- **Эффект:** свежий пользователь открывает хаб и получает разрешение на добивки без единой метрики. Прямое противоречие аудиту Oct 11 2026 в шапке того же файла.
- **Фикс:** `num()` → возвращать `null` для `null | undefined | '' | '—'`; `tested` считать по «явно введённым» значениям; в хаб прокинуть реальную боль (`painMon`) и реальный VBT-loss вместо хардкод-`null`.
- **Тест:** `bb-diagnostics-honesty` + кейсы: пустой ввод → `level:'yellow', noData:true`; только `pain010:0` → `tested:true` (это данные); только `pain:null` → `tested:false`.

### BB-D-02 · P0 · «Симметрия 100 · пропорции в норме» без единого замера
- **Где:** `src/engines/bb/bb-symmetry.engine.ts:152-153` (+ хедер хаба).
- **Что:** `score = 100 - min(60, penalty)`; при отсутствии замеров `penalty = 0`, `issues = []` → 100/100 и «в норме».
- **Эффект:** ложное подтверждение нормы пропорций; пользователь не идёт мерить обхваты.
- **Фикс:** ввести `tested: boolean` (есть хотя бы 2 обхвата/рост/запястье), при `!tested` не рисовать score и выдавать «не измерено» вместо «в норме»; сохранить обратную совместимость для вызывающих.
- **Тест:** пустой `meas` → `tested:false`, `score:null`; один обхват → `tested:false` с подсказкой; полный набор → прежние числа (регресс на существующие 94 max-pro теста).

### BB-D-03 · P0 · «Стимул сбалансирован» без плана
- **Где:** `src/engines/bb/bb-stimulus.engine.ts:16-19` (и `catch` на `:24`).
- **Что:** при отсутствии плана возвращается `issues: []`, `scorePenalty: 0` — UI не отличает «идеально» от «нечего анализировать».
- **Эффект:** таб «Стимул» зелёный на пустом профиле.
- **Фикс:** добавить `tested:false` (или `noPlan:true`) в результат; UI — нейтральный серый чип «нет плана» вместо зелёного вердикта.
- **Тест:** `analyzeBBStimulus(null)` → `noPlan:true`, issues не пустой по смыслу (текст «собери план»).

### BB-D-04 · P0 · Ручные слабые зоны получают выдуманные «−15%»
- **Где:** `src/engines/bb/bb-diagnostics-hub.engine.ts:59-65`; рендер `BBDiagnosticsHub.tsx:1885`.
- **Что:** для ручного выбора подставляется `deltaPct: -15, source: 'volume'`, как будто это измеренный дефицит объёма. UI печатает «Авто-кандидаты: грудь −15%».
- **Эффект:** пользователь видит «измеренный» дефицит, которого не считали.
- **Фикс:** `deltaPct: null` + `source: 'manual'`; UI: `source==='manual'` → «выбрано вручную» без процента; авто-кандидаты считать отдельным списком.
- **Тест:** `manualWeak:['chest_upper']` без дневника → кандидат есть, `deltaPct === null`, `source === 'manual'`; сортировка по |delta| не падает на null.

### BB-D-05 · P0 · `verification` структурно ≤ 70%, ACWR-пол мёртв
- **Где:** `bb-scoring.engine.ts:87` (0.35 дневник + 0.35 замеры + 0.30 VBT); хаб `BBDiagnosticsHub.tsx:571` (`perMuscleAcwr: null`), `:576` (`hasVbt: false`).
- **Что:** VBT никогда не передаётся → максимум 0.70 и «пров. 70%» навсегда. `perMuscleAcwr` посчитан (`:444-445`) и используется в чипах, но в скоринг уходит `null` → `acwrDanger` всегда 0 → пол `≤59` и штраф `penACWR` не срабатывают никогда.
- **Эффект:** пользователь видит заниженную «проверяемость» без объяснения; опасный ACWR не влияет на балл.
- **Фикс:** передавать `perMuscleAcwr` в скоринг; `hasVbt` вычислять из реальных данных LVP/VBT (движок `bb-lvp` уже есть), а при их отсутствии **перевешивать веса** на доступные каналы и явно писать в UI «VBT не замерялся — вес исключён».
- **Тест:** только дневник → verification 1.0 при перевесе (и `channels` в результате); ACWR dangerous → пол ≤59 и `floors` содержит ACWR.

### BB-D-06 · P0 · План-аудит и хаб говорят на разных языках мышц
- **Где:** `bb-plan-exercise-audit.engine.ts:38-41,68` (ключи из `ex.muscle`/каталога = канонические группы) против `BBDiagnosticsHub.tsx:1211-1214`, `:1443`, `:1487-1489` (поиск по гранулярным зонам).
- **Что:** `aud = audit.byMuscle[z]` для `z ∈ {chest_upper, delt_mid, back_width, ...}` не находит ключ → `lengthened:false`, `missingStrict:false`, `avgSfr:null`, `missingAngles:[]`. То есть пробелы стимула по приоритетным зонам **не диагностируются**.
- **Эффект:** таб «Упражнения» показывает «нет проблем» для зоны, у которой в плане один угол и нет lengthened.
- **Фикс:** в движке отдавать **оба** индекса (`byMuscle` канонический + `byZone` гранулярный, собираемый из `granular`-полей упражнений), либо резолвить зону → канон в хабе через уже существующий `canonicalMuscle`/`granularToCanonical`.
- **Тест:** план из 3 упражнений на грудь, зона `chest_upper` → `avgSfr != null`, `angleCoverage.covered === 1`, `missing.length > 0`.

## 7. Вопросы на утверждение (продуктовые решения)

1. **Порог боли.** Сейчас `pain ≥ 7` — красный, `≥ 4` — жёлтый (`bb-readiness.engine.ts:51-54`). Оставляем, или `≥ 5` = красный (консервативнее и совпадает с типичными клин. шкалами)?
2. **Вес VBT в `verification`.** Исключать VBT-канал при отсутствии данных (перевес на дневник/замеры) или оставить 0.30 как «стимул сходить на VBT»? Рекомендую перевес + явную пометку.
3. **Спец-блок: 4–12 или 3–6 недель.** Кто главный — хаб или конструктор? Рекомендую 3–12 с предупреждением в конструкторе, но без молчаливого урезания.
4. **Ступень 1 возврата.** «Только техника» = `sets: 0` (упражнение остаётся с пометкой) или `sets: 1` без отказа? Рекомендую 0 сетов + отдельная пометка, иначе это не ступень 1.
5. **Красный флаг блокирует «→ В ББ-авто»?** Сейчас — нет. Рекомендую блокировать с явным подтверждением «понимаю риск», а гипотезу — нет.
6. **Орто-payload.** Чинить на стороне `OrthoScreenCard` (добавить группы) или ослабить гейт приёмника? Рекомендую первое: гейт должен остаться строгим.
7. **`verification` при отсутствии замеров вообще.** Показывать «0%» или «—»? Рекомендую «—» (0% читается как «всё плохо», а не «не измерено»).
8. **Объём волны 4.** Делать `BB-G-05` (live-поза/видео) в этом цикле или вынести отдельным планом? Рекомендую вынести — это единственный L-пункт.

4. **Ступень 1 возврата** — 1 подход с явной подписью «техника (не силовой объём)»;
   `volumeMult === 0` в хабе = «только техника» без силовых вставок. `sets: 0` не внедрён:
   билдер/исполнитель трактуют 0 как «упражнение удалено», это изменило бы смысл плана.
5. **Красный флаг не блокирует «→ В ББ-авто»** — остаётся предупреждением (гипотеза и
   возврат в работу не должны быть недоступны), но инъекция в план проходит через
   SafetyScore-гейт.
6. **Орто-payload** — гейт ослаблен только для BB-only полей (`hasBbOnlyInfo`), строгость
   по группам сохранена; ранее выставленные гарды снимаются **только** если payload явно
   принёс орто-секцию (`orthoPayloadPresent`), поэтому обычная диагностика их больше не
   стирает. Группы мышц из орто-скрининга **намеренно не отправляются** (специализация на
   больном суставе = +объём туда); вместо них — прехаб-строки и секция в отчёте, см. §10.11.
7. **`verification` без данных** — в UI «—», а не «0%» (0 читается как «всё плохо»).
8. **`BB-G-05` (live-поза/видео)** — вынесено отдельным планом.

Решения и границы знания:

1. **Действие только из данных.** «Снять N подходов» появляется лишь при
   `over > 0` в строках панели объёма; «добрать данные» — только когда канал
   реально пуст. Нет данных — нет совета, `note` объясняет почему.
2. **Проверка данных приходит из одного места.** `verification`/`verificationMissing`
   (BB-D-05) — вход движка, а не отдельный пересчёт: два разных «процента
   доверия» на одном экране были бы ровно тем дефектом, который закрывала волна 0.
3. **Скрининг — отдельный канал.** В `verification` его нет, но без него мобилити
   и драйвер движения — «нет данных», поэтому `screenTouched === false` поднимает
   шаг «добрать данные» с адресом в таб «Скрининг». VBT/LVP в этот шаг не входит:
   там данные есть, просто часть цифр не подтверждена — это не действие, а строка
   «проверка данных N%».
4. **Два шага — два места.** Второй шаг с тем же адресом (экран **или** вкладка
   хаба) отбрасывается: красный флаг и боль оба ведут в Ортопедию — остаётся флаг,
   вторым идёт объём; «готовность» и «эффект вставки» оба ведут в таб
   «Объём · Recovery» — остаётся готовность. Иначе карточка выглядела бы как две
   копии одной ссылки.
5. **«Собрать план» — не deep-link.** ББ-авто не входит в белый список экранов
   тренировочного блока; шаг рисуется как текст без перехода (кнопка «→» в шапке
   хаба рядом), чтобы не открывать произвольную вкладку.
6. **`planPresent` только `false`.** `undefined` = неизвестно → шаг не выводится:
   «нет плана» — утверждение, и оно требует проверки хранилища.
7. **Имя кнопки шага = сам шаг,** а не название раздела: визуальный чип места
   скрыт от скринридера (`aria-hidden`). Иначе на экране появлялись два «Скрининга»
   и ломались существующие `getByRole({name:/Скрининг/})`-контракты.
8. **Экспорт-паритет (BB-D-33).** Те же 1–2 шага уходят в HTML (первой секцией
   после балла) и в CSV; пусто — секций нет (не рисуем пустую инструкцию).

### 10.8 Хвост BB-D-33: «Рабочий вес (ориентир)» доезжает до отчёта

Движок умел печатать секцию, мета слала `workingRange: null` — значит секция не
рисовалась ни разу, а рационал конструктора «рабочий вес-ориентир» не появлялся.
Причина не в мете: в хабе не было источника e1RM — сохранённый LVP-профиль не
поднимался из хранилища, «жил» только в сессии калибровки.

| Что сделано | Файлы |
|---|---|
| `bbWorkingRangeNote()` — подпись коридора «Присед: 65–80 кг (65–80% от e1RM 100 кг) · индивид. LVP»; проценты считаются от коридора, а не хардкодятся | `bb-spec-ics.engine.ts` |
| Сохранённый LVP-профиль поднимается при выборе движения и даёт коридор; в карточке — строка `data-bb="working-range"` | `BBDiagnosticsHub.tsx` |
| Мета отдаёт тот же текст: HTML-секция «Рабочий вес (ориентир)» + CSV `working_range` | `bb-hub-export.ts` (поле уже было), `bb-diagnostics-export.engine.ts` |

Решения и границы знания:

1. **Источник — только индивидуальный e1RM из LVP** (r²≥0.85, движок уже режет
   шумный профиль). Популяционные таблицы дали бы «вес из воздуха», а прогресс
   e1RM в дневнике — это проценты, а не килограммы. Нет профиля — нет коридора,
   секция в отчёте не рисуется.
2. **«Показано = выгружено» работает в обе стороны:** строка в хабе и строка
   в отчёте — один и тот же текст из одного форматтера.
3. **В мост плана не идёт.** `workingRange` в payload остаётся запрещённым
   (jsdom-лок `'workingRange' in payload.data === false`): это ориентир для
   человека, а не назначение весов в сборку.
4. **Проценты не дублируются:** сила и масса — разные коридоры (80–90% / 65–80%),
   подпись берёт числа из `bbWorkingRange`, иначе правка процентов разошлась бы
   с отчётом (та же болезнь, что закрывал BB-D-33).
5. **Профиль после перезагрузки виден.** Раньше счётчик «сохранено профилей: N»
   показывал профили, которых нельзя было увидеть — это тоже было враньём,
   просто незаметным.

пустое не печатается), `bb-hub-working-range.test.tsx` (4 — нет профиля → нет

### 10.9 Декомпозиция 2 + «нет данных» + честная граница видео

#### 10.9.1 Пустой хаб больше не показывает `100 · ОК`

Композит из дефолтов — арифметика, а не измерение: новый пользователь открывал хаб
и читал «100 · ОК», хотя не ввёл ни одного числа. Теперь состояние `no_data`
считается один раз в хабе и печатается в двух местах одинаково.

| Где | Было | Стало |
|---|---|---|
| Кольцо в шапке | `100`, зелёное, `ОК` | `—`, серое (`data-state="nodata"`), `НЕТ ДАННЫХ · пров. —` |
| Хвост-футер | `оценка 100` | `оценка —` |
| HTML-отчёт | `Score 100/100 ok` | `Оценка: нет данных` + серый бейдж, «проверка данных —» |
| CSV | `score,100` / `level,ok` / `verification,0%` | `score,нет данных` / `level,нет данных` / `verification,—` |

Что считается «данными» (граница одна, а не эвристика по баллу):

1. скрининг тронут (`screenTouched`), дневник не пуст, выбрано упражнение разбора
   или вручную отмечена слабая зона;
2. введён хотя бы один замер, **отличный от предзаполненных 175/80** — это
   подсказка для долей, а не измерение (иначе пустой хаб никогда не был бы пустым);
3. есть сохранённый план ББ: его хаб реально аудирует (баланс/стимул/объём),
   поэтому балл по плану — не «число из воздуха».

Обратная совместимость: у отчёта появился только опциональный `scoreState`;
без флага печатается прежний `Score N/100`.

### 10.10 BB-G-05 в полном виде: видео-разбор позы (АПК-первый)

**Что сделано.** В «Скрининге» под карточкой лопатки/видео появилась рабочая
карточка `data-bb="pose-capture"`: съёмка → покадровый разбор BlazePose → метрики
ракурса → «→ В скрининг». Никакого «примера»: модель либо считает, либо карточка
говорит, почему нет.

**Почему не «свой ML».** В проекте уже есть контур позы: `@mediapipe/tasks-vision`,
`src/engines/cv/pose-engine.ts`, локальные ассеты `public/mediapipe/`
(`pose_landmarker_lite.task` + WASM). Второй экземпляр модели тянул бы память и
время старта, поэтому `getLandmarker` стал экспортом `getPoseLandmarker` (поведение
не менялось) и ББ-диагностика использует **тот же** загрузчик.

| Файл | Роль |
|---|---|
| `src/engines/bb/bb-pose-metrics.engine.ts` | чистая математика: лендмарки → сводка, пороги, вердикты, строки отчёта, патч OHS |
| `src/engines/bb/bb-pose-capture.engine.ts` | DOM-пайплайн: семплы кадров ≈3/с (8–32), DI-детектор, гиды съёмки, сообщения состояний |
| `src/ui/screens/TrainingScreen_parts/bb-hub-pose-card.tsx` | карточка: камера/галерея/живая камера, полноэкранный просмотр, прогресс, результат, применение |

**АПК-путь (как в мастере движений, `VideoCaptureCard`).** В WebView
`getUserMedia` часто недоступен, поэтому основная съёмка — системная камера
телефона через `<input type="file" capture="environment">`; видео сразу открывается
на весь экран (портал в `body`, `safe-area`), там же кнопка «Разобрать».
Галерея — второй путь; живая камера с индикатором «кадров с позой» показывается
только вне натива и только если `getUserMedia` есть. Блокировка прокрутки фона,
44px-кнопки, `aria-label` — как в остальных APK-карточках.

**Честность 2D (главное продуктовое решение).** Каждый показатель считается
только в своём ракурсе, в чужом — `null`, а не ноль:

| Ракурс | Считается | Не считается (объяснено в UI и отчёте) |
|---|---|---|
| Фронтально | вальгус (колено внутрь от линии таз–стопа), сдвиг таза, перекос таза | глубина приседа, наклон корпуса |
| Сбоку | глубина (угол в колене), наклон корпуса к вертикали, подъём пятки | вальгус, сдвиг/перекос таза |
| Оба | кисти над серединой стопы | — |

Пороги (в `BB_POSE_THRESHOLDS`, печатаются в результате, чтобы «10.7°» было
читаемо): глубина ≤100° — «глубоко», ≤120° — «до параллели»; наклон корпуса
25°/45°; вальгус 5°/10°; сдвиг таза 6%/10%; перекос 4%/8%; пятка 15%/30%.
Агрегация честная и разная по смыслу: глубина/корпус/пятка — из **самой глубокой**
точки (там паттерн виден), нарушения — **максимумом** по кадрам (колено, которое
уехало один раз, уже риск; среднее это размывает).

**Качество и отказы — три разных сообщения:**
- модель/ассеты недоступны → «Модель позы не загрузилась… работает ручной
  OHS-скрининг и гониометр» (разбора нет, `null`);
- поза не распознана (`quality: 'none'`) → «нужен весь силуэт от кистей до стоп,
  ровный свет, чистый ракурс»;
- мало кадров (<4 или <30% семплов, `quality: 'low'`) → «результат черновой,
  переснимите 5 повторов». Цифры при этом печатаются с пометкой «черновой».

**«→ В скрининг» переносит только измеренное** (`bbPoseScreeningPatch`):
фронт — `ohsKneeValgus`, бок — `ohsHipBelowParallel` / `ohsTrunkUpright` /
`ohsHeelsFlat`, оба — `ohsArmsOverMidfoot`. Нейтраль поясницы и «подворот таза» по
2D-видео не определяются и галочек не ставят. Кнопка недоступна, если патч пуст.

**Ракурсы независимы.** Фронт и бок измеряют разные признаки, поэтому результаты
хранятся и печатаются по ракурсу (`poseResults.front/side`, `poseApplied` — свой
флаг на каждый): снял спереди, потом сбоку — первый замер не исчезает ни из
карточки (строка «Сбоку/Спереди: разобрано · N из M кадров» + «Открыть»), ни из
отчёта (две секции HTML, две сводные строки CSV). «→ В скрининг» работает по
текущему ракурсу, поэтому патчи не конфликтуют; «руки над стопой» есть в обоих —
при двух видео применяется значение из применённого последним, и это сказано в
подписи карточки. Старый снимок с одиночным `poseResult` мигрирует в свой ракурс.

**Состояние и отчёт.** `poseView` / `poseResults{front,side}` /
`poseApplied{front,side}` живут в `BBState` (переключение табов замер не теряет),
старый снимок без `poseView` мигрирует в `'front'`, одиночный `poseResult` —
в свой ракурс. Разбор считается «данными» для `noDataAtAll` — балл по замеру, а не
по дефолтам. В мету добавлено **новое** поле `poseVideos` (legacy `pose` с ручными
углами не трогали): HTML — секция «Видео-разбор позы (ракурс)» на каждый ракурс с
качеством, кадрами, признаком переноса и строками `bbPoseLines`; CSV — `pose_video`
(сводка по ракурсу) + `pose_video_line` на каждый показатель. Нет разбора — секций
нет (вывод прежних вызовов не меняется); одиночный `poseVideo` в мете ещё
принимается — старые данные не ломаются.

Тесты: `bb-pose-metrics.test.ts` (30 — углы/пороги/агрегация/ракурс-фильтрация/
качество/патч/строки на синтетических лендмарках), `bb-pose-capture.test.ts` (5 —
семплирование, пустые кадры, готовые кадры без DOM, видео без длительности),

### 10.11 BB-D-19 (хвост): орто-скрининг → ББ-диагностика (без «слабых» суставов)

**Решение против буквы аудита.** Аудит предлагал добавить в `orthoBridgePayload`
канонические группы мышц. В ББ-авто `groups`/`weakPoints` — это слабые зоны, а они
включают **спец-блок** (`setSpecBlocks`) и добавляют объём именно этим мышцам.
Орто-флаг означает обратное — «сустав болит/нестабилен». Слабая зона из больного
сустава дала бы больше нагрузки на проблемную область, поэтому группы **не
отправляются** и в коде это записано как контракт (`bb-ortho-prehab.engine.ts`).

**Что сделано вместо этого.** Орто-скрининг хаба «Суставы и ортопедия» теперь
читается ББ-диагностикой из общего хранилища `he_ortho_screen_v1` (второй ввод не
заводится) и попадает в три места:

1. **Карточка «Скрининг»**: `🦴 Орто-скрининг (хаб Ортопедия)` — сводка флагов
   (`флагов N · 🔴/🟡/⚪`), кнопка «Открыть ортопедию», прехаб-строки
   (`сустав: колено (прехаб) → Копенгаген… : 2×10–12 RIR2`). `urgent` не прячется:
   «⛔ тренировка на паузе до врача — прехаб не предлагаем». Нет флагов — прямо
   сказано «орто-ограничения в план не попадут».
2. **Отчёт** (HTML/CSV): секция «Орто-скрининг (хаб Ортопедия)» — таблица флагов с
   уровнем (🔴 стоп / 🟡 врач / ⚪ наблюдение) и таблица прехаба; CSV —
   `ortho_flag` + `ortho_prehab`. Печать идёт тем же отчётом.
3. **Мост в ББ-авто**: прехаб-строки едут в `correctiveDetail` (существующий канал
   приёмника: тост + persist). Ограничения по-прежнему едут **только** `orthoGuards`,
   которые выставляет орто-экран; `orthoFlags` в payload намеренно не шлём — иначе
   сработал бы `orthoPayloadPresent` и снёс ранее выставленные гарды.

**Правила прехаба** (`bbOrthoPrehabRows`): любой `urgent` → `[]`; `doctor` → строка
с «после допуска врача»; `general` (Beighton / жёлтые / teen) → `[]` (это режим, он
уже в гардах); дедуп по `exerciseId`; кап 3; упражнения/доза/кью — из библиотеки
`bb-corrective.engine.ts` (id не выдуманы, каталог проверяется lock-тестом).

**Тесты**: `bb-ortho-prehab.test.ts` (10 — зона «сустав», каталог, urgent, doctor,
general, дедуп, кап, мусор, сводка), `bb-hub-ortho.test.tsx` (6 — пусто/наблюдение/

## 11. Остаток: что осознанно НЕ сделано

  через `input capture`; живая камера включается там, где API есть.
