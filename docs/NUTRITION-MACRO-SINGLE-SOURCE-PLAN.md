## Зачем
`meal-plan-engine.ts` (10 535 строк) собирает день ~27 проходами. Один и тот же макрос
независимо пересчитывается 4–7 последовательными проходами, у каждого свои пороги →
осцилляции add→cut, «заметка ≠ факт», противоречивые «было→стало». Это класс дефектов,
не один баг.

## Корневые точки (проверено чтением)
1. **Белок — 5 проходов**: P4-резка (≈5042–5076), `fixM` 8 итераций (≈5161–5235),
   `preciseAdjust` 3 прохода (≈5244–5375), P4b (≈5768–5834), P6 MPS-потолок (≈8932–8983).
   Полы цельного белка: 90/60 (fixM), ~80/60 (`realisticFloorG`), ×0.8 (preciseAdjust),
   80/50 (P4b), `max(40, вес×0.5)` (P6), 75/55/50/40 (reconciler ≈9455) — семь разных.
2. **Жир — 2 прохода**: kcal-догон жиром кап ×1.10 (≈4998) и fat-дефицит кап ×1.08 (≈5128)
   срабатывают на одном дне, затем P4c (≈5836) режет к ×1.10.
3. **Клетчатка — 5 капов**: `max(25,min(50,ккал/1000×14))`, hard 85, 115/65/50 по углеводам,
   `max(50,…)` без верха, снова hard 85.
4. **Pre-sleep минимум белка — 3 значения**: 20 / 18 / 25.
5. **`_pickCtx._locked`** только warn, не abort (reentrancy не защищена).
6. **`microSummary.coverage`/`diversity`** — уже исправлено (пересчёт в конце, коммит `15d68d6f`).

## Целевая архитектура
Ввести `ResolvedDayTargets` (P/F/C/kcal + provenance + journal строк). Все коррекции —
чистые функции `(meals, targets) => { meals, targets', log }`, применяемые из ОДНОГО
оркестратора. Единые именованные константы:
- `PROTEIN_FLOOR_MAIN_G` / `PROTEIN_FLOOR_SNACK_G` — один пол на роль.
- `FIBER_CAP_G(kcal)` — одна функция (не 5 литералов).
- `PRESLEEP_PROTEIN_MIN_G` — одно значение.
- `FAT_CAP_MULT` — один множитель (не 1.10 vs 1.08).
Журнал проходов → карточка «Почему день не сошёлся» (`planner-day-explain.ts`).

## Порядок работ (по одному шагу = один коммит pathspec)
1. Вынести константы в модуль `planner-day-limits.ts` и заменить ЛИТЕРАЛЫ на ссылки
   (поведение байт-в-байт, где значения совпадают; расхождения задокументировать).
2. Слить два жировых прохода в один (guard: второй не запускается, если первый сработал).

   убрать дублирующие `fixM`/`preciseAdjust` (или сделать их подшагами одного).

6. `_pickCtx._locked` → реальный abort или вынести контекст в параметры (нет reentrancy).
7. Журнал проходов в `planner-day-explain`.
