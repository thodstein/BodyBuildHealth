# UI-перф 2026-11: запуск без торможения (разбор + замеры)

Цель: приложение (включая АПК) должно открываться и переключать экраны без
заметных подвисаний. Девиз итерации — «сначала измерить, потом менять»: каждое
число ниже снято на реальном Chrome (headless, CDP), `vite preview` на
127.0.0.1:4174, эмуляция 4× CPU (медленный телефон), один и тот же сценарий.

## Что было не так (главное)

Экраны были переведены на `React.lazy`, но стартовый бандл всё равно тянул
3.7 МБ gzip / ~15.7 МБ распакованного JS. Причина оказалась не в ленивости, а в
`manualChunks` в `vite.config.ts`:

* экраны группировались по папкам правилами `id.includes('SupportScreen')`,
  `id.includes('IndividualPlan')` и т.п.;
* rollup, встретив «ничей» общий модуль (React, `core/*`, `engines/*`,
  `ui/components/*`), приклеивал его к ближайшей ручной группе — например,
  `react`, `react-dom`, `scheduler`, `core/master-db`, `ui/components/InfoErrorBoundary`
  попадали внутрь чанка `support-ui` (3.4 МБ);
* старт приложения импортировал всего пару таких общих модулей и через них
  подтягивал **целые** чанки каталога БАДов, планировщика питания и т.д.

Итог: `index.html` предзагружал 14 файлов, включая `support-ui`, `nutrition-plan`,
`support-db`, `recipe-db`, `training-data`, `labs-ui`, `fertility`.

## Что сделано

1. **Убраны ручные группы экранов** (`SupportScreen`, `IndividualPlan`,
   `NutritionScreen`, `LabsScreen`, `FertilityPCTScreen`). Экраны и так грузятся
   динамическим `import()` — rollup сам даёт им отдельные чанки, а общие модули
   кладёт в стартовый чанк, а не в чужой экранный. Правила для тяжёлых
   данных (`support-db`, `nutrition-db`, `recipe-db`, `pharma-db`, `chart-js`,
   `usda-foods`, `training-data`, `diary-storage`) оставлены.
2. **`TrainingScreen` разбит на секции через `React.lazy`** (26 компонентов):
   авто-конструкторы ПЛ/ББ/кардио/арм/сильный/бой, редактор программ, дневник,
   библиотека, все диагностические хабы. Раньше первый вход во вкладку
   разбирал 8.2 МБ JS (780 модулей, ~14 МБ исходников), из которых нужна была
   одна секция. Граница `Suspense` — **внутри** экрана, чтобы при подгрузке не
   терялись страница/зона/вкладка.
3. **Предзагрузка авто-конструкторов**: пока пользователь выбирает трек на
   экране «Планировщик», чанки ПЛ/ББ прогреваются (120 мс задержки).
4. **Быстрые поиски по продуктам**: `findFoodById` / `findFoodByName` /
   `findFoodByIdOrName` / `filterFoodsByName` в `core/nutrition-database.ts`
   (индексы-`Map`), заменены линейные `FOOD_DB.find/filter` в горячих местах
   дневника, конструктора питания и калькуляторов.
5. **`InfoErrorBoundary`** вынесен из `SupportScreen_parts/SupportScreenData.tsx`
   (файл тянет весь каталог БАДов) в `ui/components/InfoErrorBoundary.tsx`.
6. **АПК: префетч в простое** не трогает самые тяжёлые чанки (БАДы 2.7 МБ,
   питание 2.5 МБ) — иначе на слабом телефоне рывок посреди чужой вкладки.
   «Тренинг» после сплита — 106 КБ, его греем.
7. **`SupportScreen` разбит на разделы через `React.lazy`** (15 компонентов:
   каталог, избранное, дневник, стеки, протоколы, калькуляторы, исследования,
   пептиды, авто-калькулятор, ручной подбор). Раньше весь раздел «БАДы» —
   один чанк 2.7 МБ; теперь оболочка **724 КБ**, а тяжёлые части (протоколы
   947 КБ, авто-калькулятор 431 КБ и т.д.) грузятся при открытии конкретного
   подраздела. `Suspense` внутри экрана — состояние навигации не теряется.

получили свою цену при **первом** открытии (раньше их код грузился на старте
за счёт всех). Повторные открытия — 25–75 мс.

## Осталось (не сделано в этой итерации)

* **Повторная отрисовка экрана «БАДы» ~200–260 мс (4×)** — самая дорогая
  «тёплая» перерисовка; нужно точечное мемоизирование тяжёлых вью
  (`SupportCatalogView`, `SupportDiaryView`, `SupportInteractionsView`) и
  вынос расчётов в `useMemo`.
* **`IndividualPlanContext`** монолитен: любое изменение плана перерисовывает
  весь конструктор питания; разбиение на контексты даст эффект только вместе с
  `React.memo` на вью.
* **`bb-build` в воркере** уже вынесен; второй воркер под prep-движок
  обсуждался, но выигрыш под вопросом — не делали.
* **Профиль (1.5 МБ), `PeakWeekProCard` (1.9 МБ)** — кандидаты на такой же
  сплит по требованию, если появится жалоба на первый вход.

* Тесты: `TrainingScreen_parts` + `ui/__tests__` + `SRCBBScreen_parts` +

# Итерация 2 (2026-11-07): старт 4.1 МБ → 0.9 МБ

## Что нашли

Причина «предзагрузки на старте» оказалась ровно та, что описана выше как
гипотеза, но не в `registry.init()`: `core/master-db.ts` импортировал базовые
таблицы из **барреля** `data/support-database.ts`, а баррель — это
`import "./support-catalog-init"` + `export *` всех модулей каталога. Плюс сам
баррель и все шарды лежали в ручной группе `support-db`, поэтому старт тянул
2.5 МБ каталога БАДов целиком.

Отдельная находка: `ui/native/widget-sync.ts` (стартует вместе с дашбордом в
APK) импортировал из `core/data-link` **одну** функцию `derivePAL`, а `data-link`
тянет движки рисков, БАДов, лабораторий и питания — ещё ~2 МБ.

## Что сделано

1. `core/master-db.ts` берёт `EFFECTS_DB / MECHANISMS_DB / RISKS_DB /
   RECOMMENDATIONS_DB` из `data/support-category-data.ts`, а `INTERACTIONS_DB`
   — из `data/support-interactions-db.ts` (листовые модули, без сайд-эффектов).
   Каталог на старте больше не инициализируется; это делает тот, кто его
   реально открывает (БАДы / риски / калькулятор).
2. `derivePAL` и `deriveTrainingLoad` вынесены в `core/energy-pal.ts`;
   `data-link` их реэкспортирует (API не поменялся), `widget-sync` импортирует
   из листа. `data-link` целиком ушёл из стартового графа (140 → 91 модуль).
3. Ручная группа `support-db` **удалена**: с любой ручной группой rollup
   добавлял статический `import` этого чанка в стартовый, если хоть один
   модуль группы был нужен старту. Без группы данные попадают в общий
   on-demand чанк (`data-link`), а не в preload.
4. `nutrition-db`: из правила убран `nutrition-v2-data` (его читает
   `nutrition-v2.engine` на старте) — FOOD_DB осталась отдельным чанком 476 КБ,
   но старт его больше не тянет.

## Замеры (4× CPU, тот же сценарий)

| Метрика | До | После |
|---|---|---|
| стартовый JS | 4158 КБ / 7 файлов | **897 КБ / 4 файла** |
| `preload` в `index.html` | entry + chart-js + support-db + nutrition-db + pharma-db + diary-storage | entry + chart-js + diary-storage |
| DOMContentLoaded | 1460–1891 мс | **185–378 мс** |
| long task на старте | до 1118 мс | до ~250 мс (суммарно меньше) |
| «тёплый» повторный вход | 27–287 мс | 16–43 мс (БАДы 219) |

Цена: первый вход в тяжёлую вкладку разбирает общий чанк `data-link` (2.1 МБ:
движки рисков/БАДов + каталог) — это те же байты, что раньше разбирались на
старте. Первое открытие: тренинг 259 → ~1330 мс, питание 347 → ~600 мс,
БАДы 777–973 → ~770 мс, лаборатория 92–162 → ~100 мс, риски 161–395 → ~165 мс,
фарма 95–115 → ~105 мс (всё при 4× CPU; на нормальном устройстве — в ~4 раза
быстрее). Суммарно за сессию работы меньше, но платится она одним куском при
первом входе, а не при запуске.

## Осталось

* **Каталог БАДов внутри `data-link`** (≈1.3 МБ из 2.1) — он попадает туда,
  потому что `engines/support.engine.ts` использует `SUPPORT_CATALOG_DATA` как
  фолбэк покрытия. Отвязать без изменения чисел риска нельзя: если каталог не
  загружен, покрытие для веществ не из `SUPPORT_BASE_COVERAGE` станет нулевым.
  Вариант — реестр каталога (`registerSupportCatalog` + пересчёт `useDataLink`
  после подгрузки), но это меняет момент, когда числа риска «дозревают».
  Проверено экспериментом: одного `calculateSupport` мало — движок ещё берёт из
  барреля `findSubstancesByOrgan/ALL_SUBSTANCES/…`, поэтому «убрать один
  импорт» не сокращает чанк.
* `NutritionScreen` (2.5 МБ), `PeakWeekProCard` (1.9 МБ) — по-прежнему грузятся
  целиком при первом входе. Для «Питания» ленивые вкладки мало что дают:
  вкладка по умолчанию — сам планировщик, а `meal-plan-engine` в нём 712 КБ.
* Тест `src/engines/__tests__/diary-mmc-checkin-integration.test.tsx` падает
  на строке «2 сетов» — это устаревшее ожидание после итерации «согласование
  числительных» (`8aeb72252`), к перфу отношения не имеет.

# Итерация 3 (2026-11-07): «Профиль» — вкладки по требованию

## Что сделано

`ProfileScreen_v2.tsx` держал все 8 вкладок статически, хотя первый вход
показывает только hero-плитки (`tab === null`). Все 8 переведены на
`React.lazy`, граница `Suspense` — вокруг тела вкладки (шапка с «Назад» и
поднавигация остаются на месте, состояние `tab` не теряется).

| Чанк | До | После |
|---|---|---|
| `ProfileScreen_v2` | 1484 КБ | **26 КБ** |
| `ProfileDiariesTab` (6 дневников + движки) | внутри экрана | 1118 КБ по требованию |
| `ProfileCoachTab` / `ProfileUserTab` / остальные | внутри экрана | 20–122 КБ по требованию |

Замер (4× CPU): открытие «Профиля» до hero-плиток — ~260 мс, вход в
«Дневники» — ~1.5 с (первый и единственный раз, чанк 302 КБ gzip).

Тесты профиля, которые кликают в вкладки, переведены на `waitFor`
(`profile-coach-wiring.test.tsx`): в jsdom ленивый чанк грузится 2–3 с.

## Проверка

* `tsc --noEmit` — 0; `npm run build` — ок.
* `ProfileScreen_v2/__tests__` + профильные тесты `ui/__tests__` —
  38 файлов / 506 тестов зелёные.
