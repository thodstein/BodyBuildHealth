## §0. Резюме для решения (TL;DR)

**Что уже хорошо и не трогаем:** 7-шаговый визард, в котором **все 40 собираемых входов реально доходят до `buildCombatPlan`** (no-op контролов в визарде нет — проверено резолвом каждого идентификатора); ISSN-16 позиция по весогонке; безопасность подростков/сотрясений/спарринга; 240-кейсная матрица сборки; блокировка экспорта при errors; 8 форматов выдачи; честный EWMA-ACWR с `lowBase`; ATR 5/3/2 + год с таперами под каждый бой.

**Главный вывод аудита — три класса проблем, в порядке цены:**

| Класс | Суть | Цена |
|---|---|---|
| **1. Ложные числа в отчёте/выдаче** | 2 дефекта, из-за которых план показывает и печатает **неверные объёмы** (§1.1–1.2) | Тихая потеря доверия к цифрам |
| **2. Движок богаче, чем UI** | **~25 экспортов движка вычисляются и никогда не показываются** (§4) — половина ISSN-протокола сгонки просто не на экране | Пользователь не видит то, что уже посчитано |
| **3. Категорий нет вообще** | Ежедневный взвешиватель/траектория сгона, журнал спарринга, батарея тестов (динамометр), RED-S/LEA-скрининг, чек-лист недели боя на экране, графики, what-if (§5) | Это то, что отличает «генератор» от «инструмента тренера» |

**Плюс структурный долг:** мёртвый `combat-day-types.ts`, осиротевшие 25 экспортов, задвоенный годовой блок в двух файлах, APK-CSS-правила, написанные на несуществующий DOM (7 пилюль шагов ~30px в АПК — **дефект, который `verify:apk-design` физически не может увидеть**), BJJ/дзюдо/самбо оплачены таблицами весов, но недостижимы через тип.

**Предлагаю 8 эпиков E1–E8.** E1–E3 — «не врёт» (правка чисел и дефектов), E4–E6 — «показывает» (поверхности поверх готового движка), E7–E8 — «новое» (содержание, которого нет ни в движке, ни в UI). Оценка: E1–E3 — 1 сессия, E4–E6 — 2–3 сессии, E7–E8 — 2 сессии.

## §1. Дефекты, которые врут цифрами (P0 — делать первыми)

### 1.1 `totalSets`/`totalTonnage` не пересчитываются на деload/тапер-неделях

`combat-finalize.engine.ts:41-42` пропускает **всю** неделю при `wk.deload`, и пересчёт агрегатов живёт внутри этого блока:

```ts
41:  for (const wk of plan.weeksData) {
42:    if (wk.deload) continue;
...
85:    wk.totalSets = wk.sessions.reduce((s, sess) => s + sess.exercises.reduce((a,e)=>a+e.sets,0),0);
86:    (wk as any).totalTonnage = ...
```

Но срез per-exercise cap идёт в **предыдущем** цикле, где гварда деload нет (`:22-25`):

```ts
22:        if (ex.sets > lim.perExerciseCap) {
24:          ex.sets = lim.perExerciseCap;
25:          ex.workSets = ex.workSets.slice(0, lim.perExerciseCap);
```

**Последствие:** на деload-неделе `ex.sets` урезается, а `wk.totalSets` остаётся до-резачным. Потребители, которые читают `wk.totalSets` — `combat-print.engine.ts:27`, `combat-xlsx.engine.ts:26`, `combat-annual.ts:200`, `CombatPlanView.tsx:170-174` (чипы «сетов» в шапке) — показывают **завышенное** число. Тот же гвард заодно молча пропускает для деload-недель: MRV-трим, MEV-предупреждения, проверку шеи по 4 плоскостям, core-anti, авто-инъекцию прехаба и баланс push/pull.

**Фикс:** вынести пересчёт агрегатов (`:85-86`) выше `continue`; отдельно решить, должны ли проверки шеи/core/баланса пропускаться на деload (да — деload понижает объём намеренно, но агрегироваться он должен честно).

### 1.2 `plyo` и `unilateral` раздувают объём без потолка

`combat-specialization.ts:12,21` выдают акценты `plyo` и `unilateral`:

```ts
if (d==='boxing')   return { ..., plyo: 1.1 };
if (d==='wrestling')return { ..., unilateral: 1.2 };
if (style==='striker') return { ..., plyo: 1.15, ... };
```

`COMBAT_LANDMARKS` (`combat-volume.ts:9-42`) содержит **только** `neck / grip / rotational / legs / push / pull`. `getCombat(level,'plyo')` → `null` (`:52-54`). Все гейты финализатора завязаны на `neck/grip/rotational` — grep по `plyo|unilateral` в `combat-finalize.engine.ts` даёт **0 совпадений**.

**Последствие:** у боксёра плиометрия ×1.1–1.15, у борца унилатераль ×1.2, у кикбоксёра ×1.1–1.15 — **без MRV-потолка, без MEV-пола и без авто-трима**. Объём может уйти в потолок бесконечно; при этом ни MEV, ни «перегруз» никогда не сработают, потому что сравнивать не с чем.

**Фикс:** добавить `plyo` и `unilateral` в `COMBAT_LANDMARKS` (4 уровня) + включить в ключи финализатора. Значения — из §2.5 (плиометрика/ударная) с явной пометкой источника, как у таблиц весовых категорий.

### 1.3 Валидатор — passthrough, а не валидатор

```ts
// combat-builder.engine.ts:950
export function validateCombatPlan(plan: CombatPlan) {
  return plan.validation || { ok: true, warnings: [], errors: [] };
}
```

Ничего не пересчитывает — отдаёт то, что сохранил билдер. Прод-консьюмеров **ноль**; импортируют только 3 теста. Функция с именем `validate*`, не способная поймать мутированный план, — ловушка для следующего потребителя.

**Фикс:** либо переназначить на `revalidateCombatPlan` (реально пересчитывает поверх мутаций) и использовать в финализаторе, либо удалить. Молчаливый no-op под именем «валидатор» — хуже отсутствия функции.

### 1.4 Идентичность плана недетерминирована

```ts
// combat-builder.engine.ts:934
id: `cb_${Date.now()}_${Math.random().toString(36).slice(2, 6)}`,
```

Одинаковый вход → разный `id` при каждом вызове. Планы нельзя диффать, дедуплицировать в хранилище или дедуплицировать в годовом плане. Тесты это фиксируют («determinism fightDate без startDate»), а не чинят. Тот же класс — `combat-annual.ts:123` (`Date.now()` как фолбэк старта) и `combat-print.engine.ts:121` (`Date.now()` в хеше фолбэка).

**Фикс:** `id` = хеш значимых входов (дисциплина/цель/уровень/недели/дни/fightDate/сплит/…). Тест-лок: «одинаковый вход → одинаковый id; смена fightDate → новый id».

### 1.5 Дубли предупреждений попадают и в rationale, и в отчёт

Финализатор сам пишет про сессионный бюджет, потом `validateSyncCombat` (`combat-limits.ts:23`) возвращает **посимвольно те же** строки. `plan.validation.warnings` дедуплится, а `rationale` — нет:

```ts
174:  plan.validation = { ok: errors.length === 0, warnings: [...new Set(warnings)], errors };
175:  plan.rationale = [...plan.rationale, ...warnings.map(w => `• ${w}`)];   // ← не-дедупленное
```

`buildCombatReport` (`:199-200`) читает **и** `plan.rationale`, **и** `plan.validation.warnings` → каждое нарушение видно дважды.

**Фикс:** `rationale` строить из `new Set(warnings)`.

### 1.6 Бюджет сессии: одно упражнение режется, сессия — только предупреждается

```ts
22:  if (ex.sets > lim.perExerciseCap) { ...trim... }     // enforced
34:  if (totalSets > lim.maxSets) warnings.push(...);      // warned only
35:  if (sess.exercises.length > lim.maxExercises) warnings.push(...);   // warned only
```

Ничто в финализаторе не удаляет упражнения, чтобы влезть в `maxSets`/`maxExercises`. Всё держится на builder-проходе (`combat-builder.engine.ts:718-751`), где бюджет содержит собственные магические числа без источника: `0.08` (кондиция→сеты), `12` (пол), `*3` (кратность прохода), `100` (предохранитель), и жёсткий пол `if (cur.ex.sets > 2)` — несанкционированно, без предупреждения. Тест-файл, который **должен** это зафиксировать (`combat-balance-limits.test.ts`, 28 строк) проверяет только 5 несвязанных вещей. **Ни один тест не проверяет, что сессия сверх `maxSets` реально урезана.**

**Фикс:** единый `enforceSessionBudget` в финализаторе (удаление необязательных упражнений по тому же порядку, что и в ББ-авто), константы в именованный экспорт, лок-тест на перегруз.

### 1.7 `trimToMRV` режет сквозь сессии и упирается в пол

```ts
// combat-finalize.engine.ts:56-65
const groupExs = wk.sessions.flatMap(s => s.exercises.filter(filterFn)).sort(...)
while (total > mrv && idx < groupExs.length*4) {
  if (ex.sets > 2) { ex.sets -= 1; ... }
  if (idx > 120) break;
```

Три проблемы: (а) `flatMap` по всем сессиям недели — сет может быть срезан у сессии, уже стоящей на своём `maxSets`; (б) пол `>2` означает, что группа, где все упражнения по 2 сета, **не поддаётся триму вообще** — код проваливается в warning-ветку; (в) `*4` и `120` — необъяснимые магические границы.

## §2. Новые исследования 2024–2026 (интернет-синтез)

Источники: PubMed E-utilities + Crossref (провайдер websearch вернул 403 — обход через первичные API). Ниже только то, что **можно закодировать**.

### 2.1 Энергетика: главное окно, которого нет в планировщике

| Находка | Число | Источник |
|---|---|---|
| Аэробный вклад растёт **>4 мин** | **>70 %** окислительный при длительности схватки >4 мин; алатические/гликолитические — всплески | ISSN position stand 2025, п. 2 (PMID 40059405) |
| Дзюдо, симуляция 1–5 мин | окислительный **70 %**, АТФ-ФК **21 %**, гликолитический **8 %** (все длительности); окислительный растёт **50 %→81 %** по ходу схватки | PMID 27736247, IJSPP 2017 |
| Бокс, бой 3×3 мин | ЧСС **>93 % HRmax** в 1–2 раундах, **>97 %** в финальном; лактат **>15 ммоль/л** (12–18) | PMID 35415997, JSMF 2023 |
| Muay Thai, симуляция | **10.75 ккал/мин**, **9.39 MET**, ЧСС и VO₂ **всегда выше анаэробного порога**; всплеск CO₂ex в 1-м раунде | PMID 19370044, AJP-NM 2009 |
| MMA официальный vs симулированный | лактат **16.9 vs 16.8 ммоль/л** — различий нет; **гликоген до боя выше только в официальных** | PMID 27625756, JSCR 2017 |
| Кто сильнее — удар vs борьба | Борьба: сдвиг всей кривой сила–скорость вверх (макс. сила). Удар: небольшой рост макс. силы + заметный рост лёгких быстрых действий. Анаэробные: у борцов — **длинные** усилия, у ударников — **короткие** | PMID 26993133, IJSPP 2017 (систематический обзор) |
| Весовая категория | У лёгких MMA **больше оф. касаний**, физиологическая нагрузка **растёт по ходу** схватки; у тяжёлых — после 1-го раунда ЧСС выше, но без разницы по лактату | PMID 37181273, 2023 |

**Что из этого не закодировано:** в планировщике нет модели «раунд → газ». `combat-conditioning.engine.ts` возвращает `{ durationMin }` блоки, а билдер сводит их к `*0.08` сетов. Нет понятия «длительность схватки», нет разделения алатического/гликолитического/окислительного, нет правила «спринт-доминантный vs аэробно-доминантный режим по длительности боя».

**Фича (E7):** профиль боя `{ длительность_боя_мин, раунды, пауза_раунда_мин }` → распределение кондиционирования по модальностям:
- **≤2 мин (BJJ/доджитсу)** → алатический доминант: 5–8 с повторов, пауза 20–30 с
- **2–4 мин (бокс 3×3)** → смешанный: и ал-спринт, и пороговая аэробика
- **≥5 мин (MMA 3×5, Muay Thai)** → **аэробное доминирование >70 %**: приоритет Zone2/threshold над HIIT
- Устоявшийся факт: **гликолитическая доступность растёт только от официальных боёв** → симуляции не дают «гликогеновую» адаптацию, а тренировочные раунды её не заменяют. Это должно быть в UI честно, а не продаваться как «спарринг = бой».

### 2.3 Шея: консенсус BJSM 2025 — данные есть, программирования нет

PMID 40345809 (BJSM 2025): систематический обзор (21 работа) + Delphi-консенсус 18 экспертов, **57 утверждений в 5 категориях**: контекстные факторы (17), **периодизация тренировки шеи (12)**, адаптации (10), содержание (15), приверженность (3). Сейчас в коде — 11 упражнений, 4 плоскости, 4 уровня объёма (проверено, что они совпадают), но **нет ни одного из 12 утверждений о периодизации**.

Плюс: бойцы имеют **меньший объём движения шейного отдела при большей изометрической силе и выносливости**, чем контроль (PMID 35763910, MSK Pract 2022) — то есть ROM-компонент тренируется меньше, и это дефицит, а не норма.

**Фича (E7):** периодизация шеи по плоскостям (сбалансированная неделя → акцентная неделя, длинная/короткая), изометрика как дозовая единица (секунды удержания × интенсивность), `collinsNoteForLevel` (экспорт существует, UI-нет), жёсткая изометрия-только для подростков (уже есть — сохранить).

**Фича (E8):** слой «нейромышцачные когнитивные» — реакция/решения/зрение как протокол в лагерной фазе, измеримый (тест на реакцию до/после), с честной пометкой уровня доказательности (уровень C по нейробиофид-данным, уровень B по сну).

### 2.5 Плиометрика / ударная — числа нужны, чтобы закрыть §1.2

| Что известно | Источник |

### 2.6 Тепловая адаптация — одна строка текста вместо протокола

`combat-taper.engine.ts:58` содержит только `'Heat acclimation: сауна 15-20′×3/нед в тапер (опционально)'`. Данные:

- **5-дневная краткосрочная тепловая адаптация (STHA)** дала эффект у элитных любительских боксёров (PMID 35510889, JSCR 2022) — тренировка в жару улучшает и жаркую, и нейтральную среду
- 12 сессий пассивной адаптации по 1.5 ч при 45 °C / 38 % RH; изотермическая адаптация с целью Tgi ≥38.5 °C (10 сессий) (PMID 31094260, IJSPP 2020; PMID 35787594, MSSE 2022)
- **Критично:** пассивная тепловая адаптация **использует дефицит жидкости как часть процесса** — 12 сессий без питья vs ad libitum дали разные результаты. Для бойца, который через 2 недели сушится, это прямое противоречие.

**Фича (E8):** тепловой протокол с гейтом «не в сгоне и не в неделе боя», прогрессией 5 → 10 → 12 сессий, явной связкой с гидратацией/электролитами, и предупреждением о конфликте с планом сгона.

### 2.7 Нагрузка: session-RPE подтверждён, отраслевые нюансы не закодированы

- В **MMA RPE выше**, чем в BJJ и кикбоксе; в соревновательный период выше, чем в предсоревновательный — «длительность схваток и доля соревновательных действий объясняют» (PMID 28933715, JSCR 2017)
- Время замера session-RPE **10 vs 30 мин не влияет** на боксёров (PMID 24570606, JSSM 2014) → «замерить сразу» — не ложь
- Judo: TQR + session-RPE + Hooper мониторятся каждую сессию, включая **усиленный период и тапер** (PMID 33050671; PMID 40525688, 2025) → референс для нашего тапера
- Женские боксёры: показатели нагрузки и **состояние восстановления различаются в фазах менструального цикла** (PMID 40391112, Front Psychol 2025) → у нас есть `lutealPhase` как флаг, но не как фактор мониторинга

**Фича (E7):** отраслевой множитель RPE в карточке мониторинга (вид спорта × тип сессии), а не единый коэффициент.

### 2.8 Кость — нет вообще

Ударные виды = высокоимпактная нагрузка + сгон массы = идеальная комбинация для стрессовых переломов. Женские бойцы: низкий site-specific BMD у 67 % (PMID 35622478). Стресс-переломы — крупная проблема в военной/спортивной среде (5.9 % в IDF, PMID 32817239; предикторы у молодых женщин, PMID 18849871). В коде нет: костного тренинга, низкоимпактного гейта, отслеживания импакт-нагрузки, кальция/вит D в контексте кости (у нас есть только женские ноты «кальций» в `combat-female-travel.engine.ts`).

**Фича (E8):** импакт-бюджет недели + низкоимпактный режим при RED-S/сгон/подросток + витаминно-минеральный блок (Ca/D3/K2) как реальный вход, а не текстовая нота.

### 2.9 Программные ожидания (что хочет тренер)

Сверенные с рынком (CoachAbout, Myzone, Vald, EasiNote) и с практикой клубов/сборных:

1. Ежедневный журнал веса + **траектория** к категории (не «слайдер сгона»)
2. Журнал спарринга: раунды, тип, интенсивность, RPE → **кумулятивный ACWR от спарринга отдельно от зала**
3. Батарея тестов с **реальными опубликованными нормами** и историей
4. Вход/возврат: красные флаги, сотрясение, **градуированный RTP до спарринга**
5. Календарь лагеря: обратный отсчёт до боя, неделя боя по дням, автосборка из боевой даты
6. Сравнение вариантов (A/B) без потери текущего
7. Экспорт тренеру/бойцу + ICS
8. Честность: если норма не опубликована — писать «ориентир», а не выдавать за норму

Из этого реализовано 5–8 (экспорт, ICS, календарь-частично, честность-частично). Отсутствует 1–4 и 6.
