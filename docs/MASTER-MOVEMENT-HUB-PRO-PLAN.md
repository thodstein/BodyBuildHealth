## 1. Назначение и рамки

Мастер движений — единый lift-first экран диагностики одного силового движения (12 лифтов: жим лёжа/наклонный/стоя, присед, классика/сумо, тяга в наклоне, блок, бицепс, трицепс, икры, шраги). Он объединяет 10 блоков: безопасность/зачёт, слабые мышцы, слабые точки, мёртвые точки, траектория штанги, геометрия техники, VBT, видео+Kinovea, дневник-срывы, RIR/мезо-коррекция, остальные лимитеры.

Цель плана — довести его до уровня профессионального инструмента диагностики движения (сравнимо с GymAware/FLEX/Metric/Qwik VBT + Kinovea) без потери текущей интеграции с ПЛ-авто и дневником.

Ограничения:
- Не ломать существующие API моста `applyToPlanner` / `planner-bridge`.
- Сохранить APK-маркеры (`data-lift`, `data-vc`) и тесты.
- Не использовать устаревшие планы как источник истины; выводы сделаны по коду и свежему исследованию.

## 3. Интернет-исследование: профессиональный стандарт 2024–2026

Источники: GymAware, FLEX, Enode, Metric/Qwik VBT, WL Analysis, VALD ForceDecks, SimpliFaster, Frontiers/BMJ (bar-path/VBT), Kinovea.

Ключевые возможности профессиональных инструментов:
1. **Bar path analytics**: цветовое кодирование по скорости/ускорению/силе (heatmapping), горизонтальное смещение в мм, target-zone (идеальная траектория), overlay первого/последнего повтора и разминки/рабочего подхода, сравнение сессий.
2. **VBT**: индивидуальный LVP (линейная регрессия, r²), e1RM по скорости первого повтора (±1–2%), velocity-loss пороги (10/20/25/40%), различение mean vs peak velocity, MVT, метрики паузы (мс), RFD.
3. **Асимметрия**: двухсенсорный трекинг (левая/правая втулка), наклон штанги в реальном времени, интеграция с force plates (динамическая асимметрия по фазам), 3D-захват суставов.
4. **Видео/CV**: автоматическое распознавание упражнения, экспорт видео с оверлеем, контроль ракурса (90°, дистанция, высота камеры), качество съёмки (Shah 2026).
5. **Kinovea**: t/x/y (см/мм), углы, xLoop (SRD 4/6 см), vertical displacement, duration, turnover.
6. **Методология**: MVT-специфичность по движению, velocity-loss как критерий окончания сета, L/R-пороги Bishop/Parkinson (10/15%).

Вывод: наш движок уже покрывает ~60% «мозга» (фазы, углы, VBT-пороги, MVT, Kinovea xLoop, асимметрия L/R, экспорт). Основные пробелы — **визуализация/сбор данных** (heatmapping, overlay, target-zone, pause duration, dual-sensor, LVP-калибровка в UI) и **честность реализации видео** (мок вместо CV).

## 4. Разрывы (Gap analysis)

### P0 — блокеры корректности (исправить в первую очередь)
1. Персист `lift` не сохраняется при смене движения (`useEffect` deps без `lift`).
2. `groupsForPhase` вызывается с пустой фазой в `applyAll` → потенциальный сбой/мусорные группы.
3. `diaryHint` жёстко фильтрует «жим»/«bench» → не работает для других лифтов.
4. `anthroHint` не реактивен (deps `[]`), сохранение антропометрии делает `location.reload()`.
5. Видео помечено «BlazePose», но фактически `mockAnalyze` → ложное обещание; VBT-значения из мока попадают в план.
6. `weakMuscleSubs` → `diagnosticExerciseMap` блок в `applyAll` — мёртвый код (void cands/key), создаёт впечатление интеграции, которой нет.

### P1 — профессиональные функции (недостающие)
7. LVP-калибровка в UI (движок есть, экрана нет): ввод 3–4 точек вес/скорость, r², персональный e1RM по скорости.
8. Velocity-loss порог как явный ввод (сейчас только цель strength/speed/mass), отображение «стоп сета при −X%».
9. Mean vs peak velocity + коррекция ×0.9 для peak (движок `adjustVelocityForMetric` есть, UI не использует).
10. Pause duration (мс) для жима/приседа — метрика соревновательного стандарта.
11. Bar path: горизонтальное смещение (мм), target-zone, heatmapping по скорости, overlay повторов/подходов.
12. Asymmetry: наклон штанги (tilt) из Kinovea/видео, dual-sensor L/R, фазовая асимметрия.
13. Видео: реальный CV или честный «ручной/мок-режим» + контроль качества съёмки.
14. Экспорт: добавить асимметрию, LVP, pause duration, heatmapping-сводку; сейчас только xLoop/VBT.

> **Статус после волны 4 (см. §15–§16):** №11 закрыт полностью (overlay повторов + склейка серии из нескольких CSV), №13 закрыт (реальный CV + «оценка ≠ замер» + контроль качества съёмки), №14 закрыт (22 метрики в CSV/HTML + SVG-траектория ключевого кадра). Остальные пункты P0/P1 закрыты волнами 1–3.

> **Уточнение после волны 5 (§17):** №11 — heatmapping по скорости доведён (инлайн-график и SVG), overlay дополнен сравнением с прошлой сессией (персист серии); №14 — добавлены PNG-кадр и видео-анимация траектории; №16 — «Быстрый старт» для пустого хаба; №18 — VBT-метрика и качество съёмки в отчётах по-русски, без id (`mcv`/`ok`).

### P2 — UX и качество
15. Коллапс-состояние не персистится; длинный экран (10 блоков) без поиска/навигации.
16. Нет «пустого состояния»/онбординга для новых пользователей.
17. Доступность: часть кнопок <44px (например, выбор дней «Д1»), контраст белого текста на тёмном.
18. Локализация строк: смесь русского/английского в идентификаторах (косметика).
19. `location.reload()` в антропометрии — плохой UX.

## 19. Волна 7 (31.10.2026): калибровка видео — линия по грифу, mp4 при поддержке

**Проблема волны 6:** траектория поверх видео рисовалась панелью в углу, потому что неизвестно,
где штанга в кадре. Это ограничение снято калибровкой «см трека → пиксель видео».

**Калибровка (движок `trajectory-overlay.engine.ts`):**
- `VideoCalibration` = якорь (пиксель кадра + координаты трека в этой точке), `pxPerCm` и флаг зеркала X.
- `calibrationFromTaps`: масштаб из двух тапов известного отрезка (`pxPerCm = distPx / refCm`), `null` при нулевом отрезке.
- `isCalibrationSane`: 0.05…200 px/см — отсекает опечатки («45 см» вместо «4.5») и битые данные из localStorage.
- `mapTrackToVideo`: перевод точек трека в пиксели (y трека растёт вверх, в кадре — вниз; `mirrorX` для съёмки с другой стороны).
- `grabVideoFrame(file, {timeSec})`: кадр видео в `data:URL` + натуральные размеры — по нему пользователь тыкает точки.

**UI хаба (`video-calib`):**
- «📷 Кадр из видео» → превью, тапы: якорь (штанга на 0 с трека) → точка A → точка B эталона; поле «Эталон, см» (по умолчанию 45 — диаметр блина), тумблер «⇄ зеркало X», «↺ Сбросить точки».
- Живой расчёт масштаба до сохранения, кнопка «💾 Сохранить калибровку» пишет её в `MasterState.videoCalib` (per-lift), «🗑 Удалить калибровку» убирает.
- Статус блока честно говорит, что будет на выходе: «✓ откалибровано · N px/см» или «линия будет панелью». Без точек трека калибровка недоступна и это написано.
- Тапы по превью пересчитываются в пиксели исходного видео (превью масштабируется по ширине).

**Запись видео:**
- `recordVideoWithOverlay(..., {calibration})`: с калибровкой траектория рисуется **линией по кадру** (xPixel × scale), панель не рисуется; подпись «линия по калибровке кадра». Без калибровки — прежняя панель.

- Анимация траектории по-прежнему webm (это не запись подхода).

**Честные ограничения (в UI и здесь):**
- Калибровка линейная и по одному кадру: перспективные искажения не корректируются, при сильном ракурсе линия уйдёт.
- Якорь привязан к первой точке трека и к 0 с видео; если трек начинается позже, нужен `offsetSec` (параметр движка есть, поля в UI пока нет).

## 24. Волна 12 (01.11.2026): перспективная калибровка по 4 кадрам

**Задача:** камера стоит сбоку под углом — тогда масштаб «px на см» сверху и снизу кадра разный,
и прежняя калибровка одним коэффициентом (§19) кладёт линию по грифу только в одном месте.

**Честная модель (движок `trajectory-overlay.engine.ts`):**
- Полная гомография по 4 точкам **не применяется**: точки штанги почти коллинеарны (движение
  вертикальное), такая задача вырождена. Взята осевая модель pinhole-камеры с наклоном:
  `Y = (vA·y + vB) / (vC·y + 1)`, масштаб — её производная `|vA − vC·vB| / (vC·y + 1)²`,
  горизонталь масштабируется **локально** (изотропно) на этой высоте.
- `perspectiveFromAnchors(anchors, points, {mirrorX})`: привязка = время трека + пиксель штанги
  в кадре; точка трека берётся на это время (`pointIndexAtTime`), поэтому координаты трека
  не выдумываются.
- Подгонка — нормальные уравнения в **нормированных** координатах: без нормировки матрица
  плохо обусловлена (y·Y ≈ 1e4) и точное решение отбрасывалось как вырожденное (поймано тестом).

**Почему минимум 4 кадра, а не 3:** три точки дают точное решение (3 неизвестных, 3 уравнения),
и промах в тапе ничем не обнаружить. Четвёртая точка включает двойную проверку:
остаток подгонки и **leave-one-out** — каждая точка предсказывается по остальным. Тест показывает,
что промах на 30/60/120 px теперь даёт `null`, а не «кривую, но красивую» линию.
- Допуск — 3 см хода штанги (`fitPx` переводится в см через медианный локальный масштаб).
- Привязки обязаны покрывать ход штанги: разброс высот ≥ max(10 см, половина хода), иначе
  `null` (экстраполяция перспективы с 5 см на 50 см — выдумка).
- `isPerspectiveSane`: 4+ привязки, конечные числа, локальный масштаб 0.05…200 px/см,
  знаменатель без полюса. `perspectiveSkewPct` показывает разброс масштаба по высоте.

**UI (`video-persp`, секция 8):** выбор видео, четыре строки «время в видео → 📷 кадр → тап по
штанге» (время подставляется как 5/35/65/95% трека), зеркало X, сброс, удаление.
До сохранения показано: масштаб снизу → сверху, разброс % и невязка в px; если разброс >60% —
предупреждение. Без разбора CSV модель честно недоступна («Нужны точки трека»), при неполных
точках — счётчик «заполнено N из 4».

**Приоритет и запись:** `recordVideoWithOverlay({perspective})` точнее единого масштаба, поэтому
перспектива имеет приоритет над `calibration`; footer честно пишет «линия по перспективе
(4 точки)», а при попадании в кадр <60% — «линия вне кадра». Персист — `MasterState.videoPersp`

## 27. Волна 15 (01.11.2026): ракурс по замеру — без угадывания подписи

**Задача из плана:** «авто-детект ракурса» (раньше ракурс вводился только вручную в метаданных).

**Что честно проверяемо, а что нет.** По одной 2D-траектории видны два измеримых сигнала:
разброс масштаба «сантиметров» по высоте кадра (если перспектива откалибрована) и горизонтальный
ход штанги относительно вертикального. А вот «спереди или сбоку» — нет: для этого в кадре нужен
эталон (линейка, блин, стойка известной длины). Подставлять догадку в метаданные съёмки значило бы
выдавать оценку за замер, поэтому ракурс остаётся ручным полем, а авто-часть говорит только то,
что видно по цифрам.

**Движок (`strength-sport-video.engine.ts`):** `cameraAngleCheck(points, { skewPct, driftLimitPct,
skewLimitPct })` → `CameraAngleCheck`:
- `driftPct` — горизонтальный ход штанги, % вертикального хода (`(max x − min x) / (max y − min y)`);
- `skewPct` — разброс масштаба по высоте, % (передаётся из перспективной калибровки; без неё `null`,
  а не `0` — «не проверено» ≠ «проверено и ровно»);

## 28. Волна 16 (01.11.2026): доводка до качества — слабости своих же волн

Ревью кода волн 14–15 нашло четыре реальные слабости; ниже что именно и почему.

**1. Замер ракурса ломался на одном глюке трекера.** `cameraAngleCheck` брал размах
`Math.max(...x) − Math.min(...x)`: одна «улетевшая» точка давала ложный вывод «штанга уходит
на 50% хода → камера не перпендикулярна», а выброс по вертикали наоборот занижал уход и давал
фальшивый «ok». Теперь `dropSpikes` выкидывает точки, резко расходящиеся с ходом **соседей**
(порог = медиана локального излома × 4, но не меньше 0.5 см) — плавный уход штанги сохраняется,
потому что там соседи уходят вместе с точкой, а одиночный глюк режется. Плюс `spanOf` вместо
`Math.max(...arr)`: спред в аргументы роняет стек на длинной серии (проверено на 20 000 точек).

**2. Горизонталь трактовалась одинаково для любого ракурса.** Сбоку горизонталь в кадре —
направление движения плюс возможный наклон камеры; **спереди** это уход штанги вбок по телу, то есть
чистый сигнал техники, и совет «переснимите строго сбоку, чтобы отделить» там просто неверен.
Добавлено `basis: 'side' | 'front' | 'unknown'` (из `capture.side`): фронт → «боковой уход — сигнал
техники, а не наклона камеры»; сбоку → две версии причины; ракурс не указан → цифра есть, трактовки
нет: «непонятно, это вбок по телу или путь уходит вглубь кадра». В блоке появился `angle-basis`.

**3. Захват кадра был скопирован дважды и мог висеть 8 с.** Кнопки `📷` и `⤓` дублировали логику
(рассинхронизация сообщений, разное округление времени). Обе теперь идут через
`capturePerspFrame(i, timeSec)`; добавлен `perspBusyRef` — второй клик во время захвата
игнорируется, иначе два seek подряд показывают в плеере не тот момент. Сессия кадров открывается
только при `readyState >= 2`: раньше на не декодированном видео каждый клик ждал `loadeddata`
до 8 секунд, прежде чем честно падать на разовый `grabVideoFrame`.

**4. Мини-плеер не показывал введённое время.** Правка поля «время в видео» теперь сразу
переставляет плеер на это время (в `try`, потому что до загрузки метаданных WebView бросает), —
пользователь видит кадр, который возьмёт, а не вводит время вслепую. Заодно поправлено
форматирование `cleanCapture` (две инструкции в одной строке).

## 33. Волна 21 (02.11.2026): эталон в кадре — ракурс стал измеряемым, а не угаданным

**Что было не так.** С §27 вердикт честно оставлял две версии («либо техника, либо камера не под 90°»),
потому что по одной 2D-траектории азимут камеры не восстановить. Пользователю предлагалось
«переснять строго сбоку» — совет верный, но без обратной связи: соответствовала ли новая съёмка
этому совету, он не знал.

**Физика замера.** Эталон — отрезок известной длины, лежащий **поперёк** движения штанги (гриф между
насечками ≈ 131 см, ширина стойки/скамьи). Камера в плоскости движения видит его в истинную длину,
повёрнутая на угол φ — укороченным примерно в `cos φ` раз. Значит
`cos φ = наблюдаемая длина / (реальная длина × масштаб кадра)`, и угол считается.
Диск для этого **не** годится: он круглый, и его видимая ширина почти не зависит от азимута
(для масштаба он годится).

**Движок (`trajectory-overlay.engine.ts`):**
- `referenceAngleCheck(span, { pxPerCm })` → `{ observedCm, expectedCm, ratio, azimuthDeg, flag, pxPerCm, reason }`.
  `azimuthDeg` — угол к плоскости движения (0…90°), а не «слева/справа»: знак по одному кадру не
  определяется, и это сказано в каждом `ok`-вердикте.
- Честные отказы вместо красивых цифр: нет масштаба кадра → `unknown` («сначала калибровка или
  перспектива»); отрезок < 24 px → `unknown` («ошибка тапа съедает >4°»); отрезок виден > чем на 12%
  длиннее ожидаемого → `unknown` (эталон ближе к камере, чем калибровочная плоскость, либо не та длина);
  `lengthCm` 0/минус/>5 м и нечисловые точки → `null`.
- Вердикт по углу: ≤15° — камера в плоскости (`xLoop` сравним), ≤40° — отклонена на N°, горизонталь
  укорочена примерно на `(1 − cos φ)`%, >40° — почти спереди (`xLoop` и скорости по пути несравнимы).
- `perspectiveTrackYForVideoY(c, videoY)` — обратная вертикальная связь перспективы
  `y = (vB − Y)/(Y·vC − vA)`: без неё локальный масштаб брался бы не на той высоте, где лежит эталон.

**Движок (`strength-sport-video.engine.ts`):** `cameraAngleCheck(..., { azimuthDeg })`:
- `azimuthKnown: boolean` + `azimuthDeg: number | null` (было жёстко `false`); неправдоподобный угол
  (−5, 120, NaN, ∞) игнорируется;
- измеренный угол перекрывает метаданные: `basis` выводится из него (`> 60°` → `front`, иначе `side`);
- в `drift`-ветке при измеренном боковом ракурсе «либо техника, либо камера» снимается: это техника,
  камера в плоскости движения; при `front` — боковой уход штанги, как и раньше;
- `cameraAngleShortLine` добавляет `камера N°` первой частью строки и знает про измеренный ракурс.

**Hub:** подблок `ref-block` в «Ракурс по замеру» — поле длины эталона (`ref-length`, персист
`refLengthCm`), кнопка `ref-grab` (кадр из того же мини-плеера перспективы, чтобы пиксели совпали
с калибровкой), кадр `ref-frame` с двумя тапами (третий тап начинает заново), `ref-result` с черновым
замером и причиной отказа, `ref-save` («Применить к ракурсу»), `ref-saved` (что именно применено и по
какому кадру), `ref-clear`, `ref-msg`. Масштаб берётся локальный из перспективы на высоте эталона,
иначе — единый `pxPerCm` калибровки; нет ни того, ни другого — честный отказ.
Сохранённый замер идёт в `angleCheck`, в `angle-azimuth`/`angle-basis` («(измерено)») и в подписи
картинок. Персист `MasterState.refAngle` чистится от мусора (угол 0…90, длина 1…500 см, конечный `atSec`).

**Отчёт:** CSV-строки «Угол камеры по эталону, °» и «Эталон в кадре, см» (36 → 38 метрик), HTML-строка
«Угол камеры по эталону» с оговоркой «от плоскости движения»; без замера — «—», а не 0°.

**Тесты волны 21:** `reference-angle.test.ts` (12: мусор → `null`, нет масштаба, короткий отрезок,
0°/25°/60°, эталон ближе камеры, наклонный отрезок, неправдоподобный масштаб, round-trip обратной связи

## 36. Волна 24 (02.11.2026): ось эталона — половина формулы, а не подпись

**Найденная ошибка геометрии (важнее любой косметики).** Волны 21–23 рекомендовали в UI «гриф между
насечками ≈ 131 см, ширина стойки» как эталон и считали угол по `acos(ratio)`. Но это разные оси:
- отрезок **в плоскости движения** (длина скамьи, глубина стойки, метки на полу) при камере сбоку
  виден полностью и сжимается как **cos φ**;
- отрезок **вдоль штанги** (гриф между насечками, ширина стойки) при камере сбоку направлен в
  объектив, виден почти в ноль и растёт как **sin φ**.

`acos` верен только для первого. На втором получался угол **90° − φ**: на 30° от плоскости замер
показывал 60°, а на 60° — 30°, то есть «камера почти сбоку, xLoop сравним» при фактически фронтальной
съёмке, плюс поправка горизонтали по неверному множителю (+15% вместо «поправлять нечего»). Совпадало
это только на 45°, где cos = sin, — поэтому и не бросалось в глаза.

**Движок (`trajectory-overlay.engine.ts`):** `ReferenceAxis = 'across' | 'along'` в `ReferenceSpan`
(по умолчанию `across`), и в результате появились `axis`, `cosPhi` и `cosPhiRelErrPct`:
- `across` → `cosPhi = ratio`, угол = `acos(ratio)`;
- `along` → `cosPhi = √(1 − ratio²)`, угол = `acos(cosPhi)` (то же, что `asin(ratio)`);
- точность считается по режиму: `across` — `√2·tap/spanPx`, `along` — та же ошибка, усиленная
  множителем `ratio/(1 − ratio²)`, то есть у фронта честно растёт;
- в `reason` формула названа словами («видимая длина = реальная × cos φ» / «× sin φ»), иначе число
  из отчёта не воспроизвести;
- `ratio > 1.12` по-прежнему `unknown`, но текст разный: для `along` это «концы ткнуты не по грифу».

**Поправка горизонтали:** входом стал `cosPhi` (с `ratio` только как запасной путь для замеров волны 22,
где ось была неявно `across`). Иначе ось «вдоль штанги» давала бы поправку +100% вместо +15.5%.
`cos φ = 0` теперь `refused` с прямым текстом («под прямым углом — горизонталь не наблюдается»), а не
`unknown`: это измеримый, но бесполезный ракурс.

**Hub:** переключатель `ref-axis-across` / `ref-axis-along` (`aria-pressed`, ≥44 px) и подсказка
`ref-axis-hint`, которая прямо говорит, что брать в каждом режиме; выбор оси персистится
(`MasterState.refAxis`). Плейсхолдер длины подсказывает 120 см для скамьи и 131 см для грифа.
`ref-saved` называет ось применённого замера. В сохранённом замере теперь лежат `cosPhi`,
`cosPhiRelErrPct` и `axis`, поэтому поправка после перезагрузки не деградирует.

**Отчёт:** строка «Эталон: ось» («поперёк движения» / «вдоль штанги») — 42-я метрика; в HTML ось идёт

**Что по-прежнему честно не делается:** направление «слева/справа» не измеряется (эталон даёт только
угол к плоскости), а перепутанную пользователем ось код не детектирует — поэтому ось спрашивается

## 38. Волна 26 (02.11.2026): сравнение сессий знает, под каким углом они сняты

**Зачем.** Весь смысл замера ракурса был в сравнимости `xLoop` между сессиями, но само сравнение
сессий (`compareBarSessions`) про ракурс не знало: оно брало `xLoop` как есть. Две сессии под 8° и 25°
дают ΔxLoop ≈ −0.2 см «просто потому, что камера стояла иначе», и это читалось как изменение техники.
Рядом уже стоял правильный образец — `weightMismatch` («сравнение скорости честно только при равном
весе»); ракурс проверялся тем же способом, но его не было.

**Движок (`strength-sport-video.engine.ts`):**
- `BarRepSnapshot` получает `cosPhi` и `angleDeg`; `snapshotBarRep(rep, maxPoints, camera?)` пишет их,

  камеру, а **vmax сравнивать можно** (поворот вокруг вертикали вертикаль не искажает), и — если оба
  угла ≤ 40° — «с поправкой на ракурс ΔxLoop ≈ ±X см (оценка)». Дальше 40° поправка не предлагается:

## 40. Волна 28 (02.11.2026): направление ухода словами, сверка двух эталонов, модель поворота

**Три вопроса, на которые отчёт отвечал цифрой без слов.** «xLoop +0.5 см» — это плюс вправо **в кадре**,
а куда это по телу, не сказано; «угол 25°» — верно ли размечена ось, не сказано; «горизонталь занижена» —
насколько, видно только в процентах поправки. Все три вопроса решаются уже имеющимися данными, без новых
зависимостей и без единого выдуманного числа.

**1. Направление ухода (`barDriftDirection`, strength-sport-video).** Знак `x` переводится в тело по стороне
съёмки. Геометрия проверяется, а не запоминается: лежащий головой на север, камера на его **левом** боку
смотрит на восток, её собственное «право» указывает на юг — то есть камера слева даёт «изображение `+x` = к
ногам» (стоя — «назад»), камера справа — «к голове»/«вперёд». *(В первой редакции волны 28 знак был
перепутан; см. §41 — ошибка найдена при попытке измерить сторону и исправлена вместе с тестами.)*
Порог 0.3 см: меньше — это шум трекинга, а не направление (`level`). Нет стороны → `unknown` с причиной;
вид спереди → `unknown`, потому что «влево/вправо» в кадре не переводится в «к голове/вперёд» без того,
с какой стороны снимали. Направление **не измеряется**, а выводится из параметров, и подпись говорит это
прямо («по параметрам съёмки»), вместе с оговоркой про зеркальную запись: селфи-камера переворачивает кадр.
В хабе — строка `drift-dir`, в отчёте — строка «Направление ухода».

**2. Сверка двух эталонов (`referenceAngleCrossCheck`).** Поперечный эталон даёт cos φ, продольный — sin φ,
и вместе они обязаны дать единицу. Если `cos² + sin²` уходит от 1 больше допуска (неопределённость тапов
плюс 4 % на допущение «отрезок в плоскости движения»), замер **не применяется**: лучше перемерить, чем
поправить горизонталь по неверной оси. Это закрывает ровно тот класс ошибки, из-за которого в волне 24
было 60° вместо 30°: теперь разметка проверяется измерением, а не доверием. Подтверждённый угол считается
как `atan2(sin, cos)` — по обеим осям сразу, а не по одной.

В хабе: тумблер `ref-cross-toggle`, второй отрезок всегда на противоположной оси (`ref-alt-length`,
`ref-alt-tap-*`), результат — `ref-cross` с тремя состояниями («пройдена», «не сошлась», «неполная»).
Сохранённый замер несёт `checked: 'both'` и `crossDevPct`; без них он честно подписан «ось не проверена».

**3. Модель поворота.** Третьего измерения в данных нет, поэтому «3D-ротация» честно реализована как
**модель**: тот же измеренный путь, у которого горизонталь растянута в `1/cos φ` — то есть как он выглядел бы
с камерой в плоскости движения. В SVG — пунктиром (`#4ade80`) с легендой «модель: камера в плоскости» и
подписью «пересчёт измеренного пути, а не второй замер»; в PNG/CSV/HTML — только подписью с числом
(«xLoop ≈ 3.1 см вместо 2.8»). В PNG вторая кривая намеренно не рисуется: рендер нормализует точки по своим
границам, и растянутая кривая легла бы в тот же прямоугольник — то есть показала бы противоположное правде.
Кнопка `export-model` без измеренного угла не включается и говорит, чего не хватает.

**Звук в видео с наложением, без muxer-а.** Перекодирование через canvas теряло звук подхода, и «видео с
траекторией» уходило немым. Отдельная библиотека для этого не нужна: аудиодорожка берётся из исходного
элемента (`sourceAudioTrack` → `video.captureStream()`), кладётся рядом с видеодорожкой канвы, и MediaRecorder

## 41. Волна 29 (02.11.2026): сторона камеры измерена по кадру — и знак в волне 28 исправлен

**Последний «неизмеряемый» пункт оказался измеримым.** В волнах 28–40 было записано: «направление
слева/справа по одному кадру принципиально не измеряется — любой отрезок даёт только |φ|». Это верно только
для **длины**. Но эталон — это ещё и **направление отрезка в кадре**: поперечный эталон лежит вдоль оси
«голова ↔ ноги» (жим) или «вперёд ↔ назад» (стоя), и камера с левого и с правого бока видит эту ось
направленной в противоположные стороны кадра. Порядок двух тапов — уже измерение, к нему нужен один
пользовательский бит (какой конец у головы) и один честный бит про запись (зеркальный кадр).

**Ошибка знака в волне 28, найденная этой проверкой.** Прежде чем писать сторону, геометрия была выведена
заново физикой: лежащий головой на север, камера на его левом (западном) боку смотрит на восток, её
собственное «право» указывает на юг, значит голова на изображении — слева, и `+x` в кадре идёт **к ногам**.
В волне 28 было наоборот (камера слева → `+x` = «к голове»). То есть `barDriftDirection` уверенно называл
противоположное направление — самый опасный вид ошибки: правдоподобный ответ вместо `unknown`.
Знак исправлен, тесты переписаны на физику, а не на прежнее ожидание; в §40 добавлена пометка.

**`referenceSideCheck` (trajectory-overlay.engine).** Вход: два конца эталона (какой из них «у головы»),
ось эталона, бит `mirrored`. Выход: `side: 'left' | 'right' | 'unknown'`, сдвиг `dxPx`, **сила сигнала**
`|dx| / длина отрезка` и готовая подпись. Правила отказа (а не догадки):
- ось `along` — сторону не даёт: при камере сбоку концы грифа проецируются в одну точку по горизонтали;

## 42. Волна 30 (02.11.2026): средняя скорость концентрической фазы — рядом с пиковой

**Проблема методики, а не картинки.** В хабе и отчёте единственная скорость из видео — `vmax`, пиковая. При
этом MVT и нагрузочно-скоростной профиль (LVP) в литературе считаются по **средней** скорости
концентрической фазы, и пик систематически выше её на 1.5–2 раза. Пока в отчёте стоит одно число с подписью
«vmax», его подставляют в MVT — и результат завышен на десятки процентов. Движок мог посчитать среднюю с
самого начала: амплитуда и длительность повтора уже измерены.

**`vMean` (strength-sport-video).** Для каждого повтора `vMean = amplitude / 100 / (durationMs / 1000)` м/с —
вертикальное смещение концентрической фазы (низ → верх) на её время. Это арифметика измеренных точек, без
модели: поворот камеры вокруг вертикали вертикаль не искажает, поэтому величина устойчива к ракурсу так же,
как `vmax`. Поле необязательное (`vMean?`) — старые сохранённые серии его не содержат, и задним числом
значение не выдумывается; `snapshotBarRep` переносит его как есть, `cleanSeries` принимает только
правдоподобное (0 < v < 20 м/с).

**`meanVelocitySummary` — сводка словами.** Средняя по повторам, пиковая по тем же повторам, во сколько раз
пик выше, и оговорка: «MVT и LVP считаются по средней скорости, а не по пиковой». Нет замеров средней —
`null`, а не средняя из пиковой. `barSetStats` добавляет `vMeanMean` (средняя по подходу считается только по
тем повторам, где она есть).

**Сравнение сессий.** ΔvMean едет рядом с Δvmax, но вердикт по-прежнему по `vmax`: сравнивать надо одну и ту
же величину, а средняя в старых сериях отсутствует. `prevVMean`/`curVMean`/`deltaVMeanPct` появляются только
когда её знают обе сессии — иначе поля нет, а не «0 %».

**Хаб.** Сообщение разбора CSV показывает `· средняя 0.42 м/с` рядом с `vmax`; в блоке серии — строка
`kinovea-vmean` со сводкой; у подхода — `ср. vMean`. Нет полного повтора (мало точек, только подъём без
цикла) — строки нет вовсе, а не «0 м/с».

**Отчёт.** Две новые строки CSV/HTML: «Средняя скорость (концентрическая), м/с» (число) и «Средняя или
пиковая» (оговорка: сколько повторов, какая пиковая, во сколько раз выше, и что MVT/LVP — по средней). Если
в видео есть только `vmax`, вторая строка прямо говорит: «в видео есть только пиковая скорость — это не
средняя; с MVT/LVP её не сравнивайте». Строк 50 → **52**.

**Честная граница метода.** Средняя считается по вертикальному смещению, а LPT-устройства меряют путь по
траектории. Разница — только горизонтальная петля: 3 см на 40 см вертикали дают +0.3 % пути, то есть в
пределах округления до 0.01 м/с. Это сказано здесь, а не выдано за «полное совпадение с GymAware».

## 43. Волна 31 (02.11.2026): пересчёт «пиковая → средняя» перестал быть молчаливым

**Что было не так.** Если пользователь выбирал метрику «Пиковая», `adjustVelocityForMetric` умножал число на
0.9 — и в интерфейсе об этом не было ни слова: зона MVT, e1RM и readiness считались по другому числу, чем
введено. Константа 0.9 (пик на 10–20 % выше средней) — **оценка**, зависящая от движения, веса и техники, а не
закон. Число, которое молча меняется, — это подгонка, а не расчёт.

**Что теперь.** `metricConversion(metric, measuredPeakToMean?)` возвращает `{ factor, basis, text }`, где
`basis` — `direct` (введена средняя, пересчёта нет), `measured` (по **своему** отношению пик/средняя из
видео-замера) или `estimate` (грубая константа). `adjustVelocityForMetric` принимает то же отношение третьим
аргументом, так что подпись и множитель всегда из одного источника. Неправдоподобное отношение (≤1.02, >5,
мусор) не применяется — остаётся честная оценка.

**Откуда своё отношение.** Ровно из замера волны 30: `meanVelocitySummary(...).peakToMean` по повторам
текущей серии этого движения. То есть чем больше пользователь снимает видео, тем меньше в его цифрах
остаётся констант.

**Хаб.** Под выбором метрики — строка `vbt-metric-note`: «✓ по вашим видео: пик выше средней в 1.8 раза» либо
«ℹ оценкой ×0.9 (пик обычно на 10–20 % выше средней)». И там же точная граница влияния: **на потерю скорости
пересчёт не влияет** (она — отношение, множитель сокращается), а на зону MVT и e1RM влияет. Без этой строки
пользователь не знает, какие из чисел он видит на самом деле.

**Отчёт.** Новая строка CSV/HTML «Пересчёт пиковой в среднюю» с тем же текстом и пометкой источника
(«по своим видео» / «оценка»). Строк 52 → **53**.
