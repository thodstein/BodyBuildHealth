## 1. P0 — порча данных / неверные даты (исправлять первыми)

### P0-1. Дата соревнования «съезжает» назад на ~6 дней за каждый календарный день работы приложения `[проверено] [layout]`

- `src/engines/lms/pl-meet-registry.engine.ts:137` — `weeksToStart: weeksToStartFromDate(date, todayIso)` (countdown в неделях: `floor(дни/7)+1`);
- `src/engines/lms/pl-meet-registry.engine.ts:200-201` — `syncCompetitionsFromMeets` **обратно** превращает countdown в дату: `const weeks = Math.round(meet.weeksToStart); const date = dateFromWeeksToStart(weeks, opts.todayIso)` → `today + (weeks-1)*7`, т.е. остаток дней внутри недели теряется;
- вызов на каждом монтировании: `src/ui/screens/SRCBBScreen.tsx:435-455` (`syncCompetitionsFromMeets`, затем `localStorage.setItem('he_pl_macro', next)`).

Численный прогон (старт заявлен на 2027-01-10, неделя 8, 10 дней подряд):

```
2026-11-22 -> 2027-01-10 (week 8)
2026-11-23 -> 2027-01-04 (week 7)
2026-11-24 -> 2026-12-29 (week 6)
2026-11-26 -> 2026-12-17 (week 4)
2026-11-29 -> 2026-11-29 (week 1)
```

**Последствие:** дата старта и неделя старта в годовом плане silently «приближаются» к сегодняшнему дню; через неделю пользователь видит «старт на этой неделе», хотя до него 7 недель. От этой же даты строятся пик-блок, тапер и `.ics`. Данные в `he_pl_macro` уже испорчены у всех, кто пользовался вкладкой.

**Причина по сути:** `date` объявлена источником истины, но на каждом синке перезаписывается из производной countdown-величины (и комментарий `:121-129`, обещающий «не пересчитывать от сегодня», относится только к `week` внутри `mergeMeetRegistry`, а `syncCompetitionsFromMeets` его обходит).

**✅ Решение пользователя:** при первом запуске после обновления **спросить**, какая дата верная (показать найденную и дать подтвердить/исправить).

**Фикс — две части:**

1. **Поведение:** в `syncCompetitionsFromMeets` не переписывать `date`, если у события уже есть валидная дата; из даты выводить только `week` (`weeksToStartFromDate`), а `date` синтезировать лишь когда её нет. Регресс-тест на **идемпотентность round-trip** `merge → sync` (сейчас `pl-post-meet-and-registry-2026-11.test.ts:84-92` проверяет только `merge`).
2. **Данные:** одноразовый флаг `he_pl_meet_date_prompt_v1`. Если он не выставлен и в `he_pl_macro.competitions` есть старты, показать модалку: «Дата старта «…» сейчас 2027-01-04 (неделя 7). Это верно?» → кнопки «Подтвердить» / «Исправить дату» (`<input type="date">`), запись через тот же канон, флаг выставляется в любом случае. Повторно не спрашивать.

### P0-2. Подставленные из прошлой сессии веса считаются «подход записан» → тренировка не сохраняется `[проверено]`

- `src/ui/screens/SRCBBScreen_parts/SessionPlayer.tsx:919-937` — `hydratePrevious()` кладёт во `actual` **все** подходы упражнений предыдущей сессии с `rpe: 0`; запись в сессию (`logSet`) при этом не происходит;
- «записанность» определяется фактом наличия ключа: `const logged = !!actual[k]` (`:3882`), `doneSets += ... !!actual[keyFor(ei, si)]` (`:1239`, см. также `:2989`), `firstUnlogged = ex.targetSets.findIndex(... !actual[...])` (`:3885`);
- следствие в UI: строка сворачивается в «✓ вес × повторы», ни один подход не открыт для ввода (`firstUnlogged === -1`), полоса прогресса = 100 %, появляется кнопка «Все подходы записаны» (`:3136-3143`) → `exitSession()`;
- `exitSession` сохраняет только если в сессии есть реальные подходы: `if (session && session.exercises.some(e => (e.sets || []).length > 0) && !savedRef.current) { finish(); }` (`:1071-1073`).

**Последствие:** вторая тренировка того же дня / следующий круг с тем же составом упражнений открывается как «всё выполнено»; нажатие «Все подходы записаны» закрывает сессию **без сохранения**, при этом UI уже подтвердил успех. Дополнительно — гонка: если нажать ✓ раньше, чем разрешится `getLastSession()` (`:900`), `setActual(prefilled)` затрёт введённые значения на `rpe: 0`.

**Важно:** кнопка «Все подходы записаны» и `mainProgress` — незакоммиченная правка в рабочем дереве (не моя, не откатывать). Дефект старше неё (строки выглядят записанными и до кнопки), но кнопка делает потерю данных одношаговой. Фикс должен идти в ту же сторону: предзаполнение — отдельная карта (`prefill`), а «записан» = подтверждённый подход (`rpe > 0` / явный флаг), а не наличие ключа.

**Фикс:** ввести отдельный `prefill`-слой (вес/повторы для подсказки) и считать `logged`/`doneSets`/`firstUnlogged` по `loggedRef` (или `rpe > 0`), а не по наличию записи в `actual`; `hydratePrevious` не должен перетирать уже введённое.

### P0-4. Авторегуляция применяется дважды: вес ×m², подходы ×m², RIR-сдвиг ×2 `[проверено] [layout]`

- `src/engines/lms/lms-builder.engine.ts:1433` (`sets × arVolMult`), `:1444` (`weight × arTopMult`), `:1448` (`RIR + arRirShift`) — применяются **и при `faithful: true`** (гейт `faithful` стоит только на объёмных множителях `:1416-1441`, не на авторегуляции);
- `src/ui/screens/SRCBBScreen.tsx:608` — `buildSrc` передаёт `autoReg: autoregPayload(autoRegResult)` в `buildLMSPlan`;
- `src/ui/screens/SRCBBScreen.tsx:986` — `effectiveSrc` передаёт **тот же** `autoRegResult` в `applyPLEffectiveOverlay`;
- `src/engines/lms/lms-effective-plan.ts:46-50` — `normalizeWorkSet` снова умножает `ws.sets × autoVol` и `ws.weight × autoTop`, RIR `+ rirShift`.

**Последствие:** в режиме «🤖 Авто» заявленный −10 % превращается в −19 %, подходы режутся дважды, RIR сдвигается на 2 вместо 1. Это тихий недогруз: цифры правдоподобны, поэтому в UI не бросается в глаза. `effectiveSrc` — источник и таблицы плана, и плеера, т.е. тренирует пользователь именно по дважды скорректированному плану.

**Важно перед фиксом:** путь «сезон» (`PLCompetitionTab.tsx:251-272`) берёт недели из уже скорректированного `builtSrc` и в билдер не ходит — там оверлей единственная точка применения. Поэтому «просто убрать `autoReg` из оверлея» сломает сезонный путь. Нужен признак в `LMSBuildOutput` («авторегуляция уже применена») и применение ровно один раз.

**✅ Решение пользователя:** авторегуляция применяется **по одной явной кнопке «применить»** и ровно один раз (не автоматически на каждой сборке). Реализация в духе `plDeloadCfg`:

1. убрать автоматическую передачу `autoReg` из `buildSrc` (`SRCBBScreen.tsx:608`) и из оверлея (`:986`);
2. кнопка пишет персистентный конфиг (`plAutoRegCfg`: множители, RIR-сдвиг, deload) в `he_pl_session`;
3. конфиг применяется в одной точке при сборке/оверлее и помечает план (`autoRegApplied`), чтобы повторная сборка не удваивала;
4. `autoRegMode === 'auto'` остаётся режимом диагностики/предпросмотра («что будет»), а не молчаливым автоприменением.

**Фикс:** регресс-тест «m=0.9 даёт ровно −10 %, а не −19 %»; тест «нажал один раз → применилось один раз, перезагрузка не меняет»; тест на сезонный путь.
