## Найденные проблемы

### P0 — Критические

**P0-1. Полный BB-год НЕ помещается в localStorage (потеря данных)**
- Скретч-тест: 52-нед BB-год (4 блока, 4 дн/нед) → план = **6561 КБ** (лимит ~5 МБ).
  Разбивка: bbPlan ~1105 КБ/блок, program ~729 КБ, weeks ~640 КБ.
- `saveAnnualTrainingPlan` молча ловит quota (`catch {}` без события) — блоки собраны в памяти,
  но НЕ сохранены; после перезагрузки план исчезает (или остаётся старая версия, и sync-эффект
  откатывает память к storage). Снапшоты (`he_annual_scenarios`, кап 6 × полный план) — тот же риск.
- Триггеры: «📦 Собрать весь год» (год >~30 нед), авто-синк при каждом изменении макро
  (useEffect в панели), снапшоты.
- **Фикс**: компактный формат (не хранить `result.bbPlan`/`result.program` целиком — либо только
  ссылки/хеши + недели, либо LZ-сжатие, либо IndexedDB); размер-предупреждение в UI;
  явная обработка quota с флешем; кап по числу собранных недель.

### P1 — Важные

**P1-1. `composeAnnualProgram`/`mergeBlockWeeks`: экспорт с несобранными блоками молча теряет недели**
- Собран блок 1 из 4 → программа «года»: `meta.weeks=20`, фактических `bb.weeks=8` (скретч
  подтвердил: MISMATCH). Несобранные блоки пропускаются, недели перенумеровываются — пользователь
  получает год, укороченный на 12 нед, без явного предупреждения (предупреждение есть только в
  `meta.notes`).
- **Фикс**: `composeAnnualProgram` — блокировать экспорт при неполной разметке (или заполнять
  пустые скелеты/помечать «НЕ СОБРАНО»), показывать список пропущенных блоков; либо синхронизировать
  `meta.weeks` с фактической длиной и флешить предупреждение.

**P1-2. Двойная резка финальной недели при пике + тапере (BB-блок)**
- Скретч: last-week сетов при peak-only = **63**, при peak+taper = **31** — generic taper
  (×0.45/RIR+2) накладывается ПОВЕРХ пик-протокола bb-contest-prep, который уже содержит свою
  taper-кривую. `buildBBBlock`: peak применяется, затем `applyBlockTaperToWeeks` режет ту же неделю.
- **Фикс**: при `peakApplied` пропускать generic taper на пик-неделе (или заменять пик-конфиг на
  taper + peak, и скрывать конфликтующие переключатели в UI).

**P1-3. `updateAnnualBlockWeeks`: молчаливая обрезка при ручном roundtrip**
- Скретч: блок 8 нед, из редактора возвращаются 12 недель → сохранено 8, 4 недели потеряны без
  предупреждения (`loopWeeksToLength` усекает).
- **Фикс**: не обрезать молча — либо расширять блок (проверить влияние на totalWeeks/раскладку),
  либо явный флеш «программа длиннее блока — обрезана до N нед» + диалог.

### P2 — Качество

- **P2-1. Дублирование логики**: `annualWeekForDate` (block-builders.engine) == `macroWeekForDate`
  (MacrocyclePanel) — идентичные формулы; `PHASE_CYCLE_PERIODS` (панель) == `phasePeriod`
  (`selectPLCycleForBlock`); `scenariosStorage`/`scenarioStorage` — похожие реализации.
- **P2-2. Мёртвый код**: `phaseOfBlockKind` (annual-training.types, не используется нигде);
  `migrateAnnualPlanFromMacroStorage` (только тесты); `annualCardioText` (только тесты);
  `removeAnnualTrainingPlan` (кто вызывает?).
- **P2-3. `bbKey`/`plKey` при `storageKey`**: при `isBB` оба ключа = `storageKey`
  (BbAutoConstructor передаёт `he_bb_macro`; ProgramEditorView — по dir) — макро-стэйт PL-ветки
  десериализует BB-формат (безвредно, но грязно); в изолированном контексте !isBB ветка читает
  ГЛОБАЛЬНЫЙ bbKey.
- **P2-4. ICS-экспорт**: `DTEND` = дата конца недели (exclusive → показывается 6 дней), для
  соревнований `DTSTART=DTEND` — 0-дневное событие; стандарт требует DTEND = начало + 1 день.
- **P2-5. Авто-создание плана года**: sync-эффект панели создаёт и сохраняет
  `he_annual_training_plan_v1` при каждом открытии/изменении макро — запись без явного действия
  пользователя + умножение quota-риска (см. P0-1).
- **P2-6. Семантика stale в UI**: блок помечается «изменился — пересоберите», но не показывается,
  ЧТО изменилось (layout/конфиг/цикл) — добавить diff-подсказку.
- **P2-7. Валидация storage**: `isAnnualTrainingPlanShape` не проверяет `ref.kind` (невалидный kind
  → блок уходит в 'error' при сборке), не проверяет сумму недель ≤ totalWeeks.
- **P2-8. `saveMacroEdit` (SRCBScreen)**: кламп недель ББ 4–24 vs ПЛ 1–∞ — рассинхрон границ;
  нельзя сохранить блок короче 4 недель через конструктор ББ.
- **P2-9. Кнопка «💾 Сохранить» в панели** — дублирует автосохранение (эффект уже пишет storage);
  мёртвое действие для пользователя.
- **P2-10. `selectPLCycleForBlock` хардкодит strength-direction** — для general/bb цели PL-блоки
  всё равно получают силовые СРЦ-циклы.

### P3 — Мелочи

- `escapeHtml` в MacrocyclePanel не экранирует `'`; `icsDate` через toISOString (UTC-сдвиг дня);
  `buildAnnualPlan` — результат `skipped` считается и для 'unbuilt' (семантика «готовых пропущено»);
  PL-программа блока: `meta.daysPerWeek` не ставится для скелетов без цикла.

## План доработок

### Этап 1 — P0: хранение и quota (самое важное)
1. **Компактная сериализация плана**: не хранить `result.bbPlan` и `result.program` в полном виде —
   достаточно `result.weeks` (UserWeek[] — это и есть «программа») + `program` для PL-блоков
   (маленький) + ссылку/хеш bbPlan; bbPlan восстанавливается только при передаче «В ББ-авто»
   (пересобрать нельзя — но можно хранить только на время передачи; при перезагрузке — повторная
   сборка). Проверить итоговый размер (< 1 МБ для 52 нед).
2. **Явная обработка quota** в `saveAnnualTrainingPlan`: try/catch → возврат `{saved:false}` +
   флеш «⚠ План не сохранён — слишком большой (N МБ)», не молчать.
3. **Размер-индикатор в UI** карточки сборки («🗄 План: N МБ / ~5 МБ») + предупреждение до сборки.
4. Снапшоты: хранить компактный вариант (без bbPlan/program) или сократить кап до 3.

### Этап 2 — P1: целостность данных
5. **P1-1**: `composeAnnualProgram` — блокировать/предупреждать экспорт при несобранных блоках
   (список «не собрано: нед X–Y»); `mergeBlockWeeks` не должен молча перенумеровывать.
6. **P1-2**: `buildBBBlock` — при `peakApplied` не применять generic taper к пик-неделе;
   UI: при включённом пике скрыть/отключить «📉 Taper внутри блока» (или связать через
   `taper.weeks=0`).
7. **P1-3**: `updateAnnualBlockWeeks` — при weeks > блока: расширение блока (с проверкой
   totalWeeks/раскладки) или явное предупреждение с сохранением; тест на оба пути.

### Этап 3 — P2: чистота и UX

## Критерии приёмки
- Полный BB-год (52 нед) сохраняется и переживает перезагрузку (размер < 1 МБ).
- Экспорт «В ручной режим» никогда не выдаёт программу короче totalWeeks без явного предупреждения.
- Пик-неделя ББ-блока не модифицируется generic-тапером.
- Все существующие тесты области (216) + новые зелёные; tsc 0.
