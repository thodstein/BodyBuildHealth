## 3. КЛАСС B — МЁРТВАЯ АРИФМЕТИКА (карточки, которые не могут быть правдой)

Три находки проверены личным чтением исходников.

### B1. `bcaa` получает окно кальция 🔴
`support-hub-evidence.engine.ts:328-342`:
```ts
const matchKey = (k: string): boolean => {
  const kl = k.toLowerCase();
  if (key.includes(kl) || kl.includes(key)) return true;   // ← строка 330
  ...
};
const directKey = Object.keys(therapeutic).find(matchKey); // ← строка 342, берёт ПЕРВОЕ
```
`THERAPEUTIC_WINDOWS` использует 2–3-буквенные ключи (`ca`, `mg`, `zn`, `fe`, `se`, `cr`, … — `SupportBioavailabilityData.tsx:181-237`). Для `id = 'bcaa'`: `'bcaa'.includes('ca')` → **true** ⇒ `bcaa` получает кальциевое окно (min 500 / opt 800 / max 1200 / UL 2500 мг). Тот же класс ложных срабатываний для любого id, содержащего короткий ключ как подстроку. **0 тестов упоминают `bcaa`.**

### B2. Карточка «суммарная нагрузка» считает не то 🔴
`UnifiedSynergyCalculator.tsx:483-508`:
```ts
loads[nutrLower].total += 1; // qualitative marker          // :504  ← СЧЁТ, не мг
...
return Object.entries(loads).map(([k,v]) => ({ nutrient:k, ...v, isOverUL: v.total > v.ul }))  // :508
```
`v.ul` — это **числовой UL в мг** (цинк 40, кальций 2500). Счёт 1–3 против 40/2500 ⇒ `isOverUL` **структурно всегда false**. При этом в движке есть **настоящий** дозовый аккумулятор `buildCumulativeLoad` (`support-plan/display.ts`), который хаб не использует. Карточка декоративна.

### B3. `calcATRange` возвращает `mid` в 2.5 раза ниже середины 🟠
`metabolic-hub.engine.ts:1280-1284`:
```ts
const low  = Math.round(input.tdee * 0.05);   // 5%
const high = Math.round(input.tdee * 0.15);   // 15%
const mid  = Math.max(base, Math.round((low + high) / 2 * 0.4));  // :1282 — это 4%, а не 10%
const persistent = (input.weeksInDeficit ?? 0) >= 12 ? Math.round(mid * 0.6) : 0;
return { low, mid: Math.min(high, mid), high, ... };
```
Середина диапазона 5–15% = 10% TDEE. Здесь `(low+high)/2*0.4` = 4% TDEE. Кламп `Math.min(high, mid)` прячет инверсию в UI, но **`mid` систематически занижен в 2.5 раза**, и `persistent = mid*0.6` compounds. Множитель `*0.4` без комментария и без источника. Тест проверяет только строку-подпись и полосу low–high, но **не порядок `mid`** — поэтому баг и жив.

### B4. Порог лейцина: 2.2 в гейте, 2.5 в поле и в тексте 🟠
`engine.ts:1257` отдаёт UI `leucThreshold = 2.5`; `:1261` гейтит по `leucinePerMeal >= 2.2`; `:1263` печатает «<2.5г». Пользователю показывают неверную планку. Тест (`metabolic-hub.test.ts:944-951`) проверяет только деление на приём и монотонность.

### B5. Недостижимая ветка `ulWarning` 🟠
`SupportEffectiveDose.tsx:231` читает `(win as any).ulWarning`, но тип `DoseWindow` (`support-hub-evidence.engine.ts:308-311`) такого поля не имеет и `doseWindowFor` его не ставит. Плюс фолбэк-путь жёстко кодирует `ul: 9999` (`:350`) ⇒ через него UL-предупреждение не срабатывает **никогда**.

### B6. `checkGuardrail` + `GuardrailContext` не вызываются нигде 🔴
`tz-bridge-mechanism.ts:291-334` определяет клинические гейты (обязательные «даже в manual режиме» по комментарию) и контекст (`e2Level`, `hemoglobin`, `hematocrit`, `hasHCG`, `hasAI`). **0 внешних потребителей, 0 тестов.** То есть хаб-калькулятор посчитает дозу и для вещества, противопоказанного при повышенном HCT или подавленном E2.

### B7. `same` — несуществующее вещество с грейдом A 🔴
`shared-constants.ts:20-156`: `SUB_ALIAS` мапит `s_adenosyl_methionine` и `heptral` → `'same'`; `canonId` возвращает это дословно (`:158-162`). Движок выдачи грейдит несуществующий `same` как **A по настроению и суставам** (`support-hub-evidence.engine.ts:166`).

### B8. `computeV7Matrix` раздувает каждую систему фантомными механизмами 🔴
`risk-engine-v7-matrix.ts:1097` перебирает `mechIdx = 1..9`, тогда как определено максимум 8, а веса уже суммируются в 1.00. Неопределённые слоты падают в `base = 0.02`, `w = 1/7` (`:1098`, `:1128`) ⇒ чистая инфляция: **+0.29 п.п. для 8-строчных систем, до +2.0 п.п. для `ins_axis` (2 строки → 7 фантомов)**, и это идёт в `overallRaw/overallNet` через геометрическое среднее. При этом `V7RiskDisplay.tsx:284` прячет невалидные механизмы от пользователя — итог **нельзя свести с разбивкой**.

### B9. `defaultM` — мёртвая таблица, разошедшаяся с живой 🟠
`tz-bridge-marker.ts:12,20-62`: 28 записей, **не читается нигде**. `getMiFromLab` использует свой `baseDefaults` (`:243`). Расхождение **по 10 из 28**: `cv2, cv4, liv1, cns1, cns2, rep1, rep2, rep3, rep5, hem1`. Кто «починит» `defaultM` — не изменит ничего; кто прочитает как документацию — будет введён в заблуждение.

### B10. Отображаемый `m_i` ≠ вычисляемый `m_i` 🟠
`tz-bridge-spec.ts:776` пересчитывает `m_i` для показа как `min(3, round(mechRaw/(w × U_i × C_mech)))` — обратная величина, впитавшая вес препарата, экспозицию и `U_i`. Внутри движка используется другой (`:728`, кламп 0–3 на `:252`). Колонка в UI — производный артефакт, поданный как член модели.

### B11. VolumeOptimizer читает ключи без писателей 🔴
`VolumeOptimizerTab.tsx:696` читает `he_workout_log_v1` и `he_training_log`. Поиск по всему `src` **не находит ни одного прод-писателя**. Живой дневник — `he_workout_log_v2` (пишут/читают `BBDiagnosticsHub.tsx:472`, `ArmDiagnosticsHub.tsx:590`, `DiaryToolsView.tsx:417`). Импорт «из дневника» в проде почти наверняка пуст.

### B12. Три источника PAL без кросс-проверки 🟡
`metabolic-hub.engine.ts:194` — литеральная копия `PAL_BASE_MAP`; `metabolic-constants.ts:197` — канон; `activity-catalog.ts:11-15` (`PROFESSION_PAL`) — третья таблица с теми же 1.40/1.55/1.75. Ни один тест не сверяет их.
