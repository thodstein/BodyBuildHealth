# Планировщик питания — HIGH-VOLUME план: инсулин+ААС, 1500У / 500Б, реальные порции (Sep 04 2026)

> Продолжение `NUTRITION-PROFESSIONAL-PLAN.md` и прошлого аудита «800У/400Б».
> Новое требование: **пользователи на инсулине + ААС ставят до 1500 г углеводов и 500 г белка**.
> Программа должна **изначально считать правильно** (типология завтрак/обед/ужин, train/rest,
> пери-окна, съедобные порции), а не «добивать бататом 5 порциями».
> Принцип рецептов: **масштабирование без ломки рецепта** (авторская пропорция × порции + сайд,
> а не раздувание специй/масла).

## 1. Аудит: что ломается на 1000–1500У / 400–500Б (факты из кода)

### 1.1. Инсулин: кап 120 г/приём не держит 1500У
- `meal-plan-engine.ts:3048–3059`: `carbG = clamp(dose*10, 30–120)` на один инжект-приём,
  только если рядом нет еды (`_hasMealNear`). При 1500У/сут (эквивалент ~100–150 ЕД суммарно
  с едой) один «инсулиновый» приём 120 г — капля. Остальные 1380 г падают в общий котёл
  и дальше режутся капами мейнов.
- `planner-targets.ts:114–117` + `planner-day-targets.ts:127`: `insulinFloor = units*10`,
  `fats = min(fats, weight*0.5)` — правильно (жиры душим под инсулином), но пол У
  `min(insulinFloor, ceilingAbs)` упирается в `ceilingAbs = weight*max(8, bulk→10)`.
  **1500У при 110 кг = 13.6 г/кг — выше любого ceilingAbs.** Цель честно посчитана,
  но движок ниже её режет.
- Нет связки «болюс ↔ конкретный приём»: болюс перед обедом должен раздувать **обед**,
  а не размазываться `CARB_W` по дню.

### 1.2. Intra: кап уже правильный — его надо защитить, а не «чинить»
- `meal-plan-engine.ts:2531`: `_intraCap = clamp(40 г/ч * duration/60, 30–90)`.
  Комментарий `2521–2528` прямо запрещает линейное масштабирование («300 г амилопектина»).
- Риск регрессии: любой «bulk-множитель ×1.5» поверх всего дня убьёт этот кап.
  **Требование пользователя «НЕ 300 г во время тренировки» = уже реализованный инвариант,
  фиксируем тестом и гейтом.**

### 1.3. Считает неверно изначально → добивка бататом
- Корень: `_carbForRaw` + `CARB_W (обед 1.7)` раздаёт доли **без учёта вместимости приёма**
  (`_mainCarbCap = grainCap*0.72`, `2500–2585`), потом `buildWholeMeal` упирается в
  `carbPortionCap`/`maxDry 170 г`, а хвост закрывают E5 (фрукт) → F1 (1 comfort) → строгая
  посадка → корректор. На 800У это ещё сходится, на 1200–1500У — «батат ×5».
- Второй гарнир внутри приёма **намеренно убран** (`1568–1571`: «гречка+рис — жалоба»),
  но замены не дано: избытку некуда деться кроме fruit/comfort с капами 150/40–110 г.

### 1.4. Завтрак ≠ обед (частично есть), обед = ужин (нет)
- E1 (`PLANNER-MEAL-LOGIC-PLAN.md`): `breakfastCarbPool` + `isBreakfastProtein` + запрет
  мясной ротации на завтрак (`1426–1446`) — **завтрак уже не «обеденный стол»**.
- Обед и ужин — один `buildWholeMeal` с тем же пулом. Разницы «обед = max У + мясо + овощи,
  ужин = белок + умеренные У, без тяжёлых бобовых» нет. На 1500У ужин получает столько же,
  сколько обед — несъедобно и нефизиологично (вечером чувствительность к инсулину ниже,
  кроме болюса под укол).

### 1.5. Добивка: только сухофрукты, пряника нет как класса
- `COMFORT_CARB_IDS (600)`: мёд/хлеб/изюм/финики/пряники/джем/зефир/пастила/сушки/печенье —
  список **есть**, но: один источник на приём (`1613–1619`), капы 35–110 г
  (`COMFORT_PORTION_LIMITS:310`), в посадке `portionCeiling 150 г (4347)`.
  Пряник 50 г = ~35 г У — им 500 г недобора не закрыть.
- Нет лестницы плотности: белый рис/рисовый крем/кукурузные хлопья/багель/сок/декстрин-напиток
  (0 клетчатки, 70–90 У/100) не выделены в отдельный тир «плотная добивка».

### 1.6. Рецепты: ряд ×0.5–×3 не держит 1500У
- `planner-recipe-mode.ts:199,1092`: `heavyScaleMax 2.2–3.0` (по весу, не по цели);
  капы масштаба `1.2×Б/1.2×У (202–204)` режут высокоуглеводный приём по белку;
  сайды max 2 × 200–250 г (~140 г У потолок).
- Раздувание ×5 сломает рецепт (специи/масло ×5) — нужен **компонентный скейл**.

### 1.7. Train/rest: разница есть, но слабая для фармы
- `planner-bb-nutrition.ts:42–50`: train `+30У/−13Ж`, rest `−25У/+11Ж`; `heavyTrainDay +25%У/+5%ккал`;
  `carbPeriodization` моды; peri-слоты только в train-day (`recipe-mode:1060–1062`).
- Для натурала ±30 г достаточно. Для инсулина разница train/rest — **500–800 г У**
  (1500 vs 700). Сейчас её надо выставлять руками через цели/периодизацию.

## 3. Архитектура решения: «считай правильно сразу»

### 3.1. Capacity-aware распределение (замена «раздай → добивай»)
Новая функция `distributeCarbsByCapacity(totalCarbs, meals, caps)`:
1. Каждому приёму считается **вместимость**: `гарнир_кап + comfort_кап + фрукт_кап + питьевые_кап`
   с учётом типологии (обед больше, ужин меньше, снек — по режиму, peri — фикс, presleep — 0 У).
2. `CARB_W` остаётся **приоритетом**, но доля ограничена `min(доля, вместимость)`.
3. Остаток — в приёмы с остаточной вместимостью, а не в «последний» (`vals[last] += diff`
   в `2500–2510` — текущий костыль, раздувающий ужин).
4. Добивка (E5/F1/посадка/корректор) — только остаток **<15%** цели приёма, иначе это
   ошибка распределения, а не «норма».

### 3.2. Типология приёмов (завтрак/обед/ужин — разные тарелки)
| Приём | Роль | Носители У | Белок | Комментарий |
|---|---|---|---|---|
| Завтрак | быстрый старт, low-GI + ягоды/банан | каши/хлопья/рисовый крем (уже E1) | яйца/творог/сыворотка (уже) | без мясной ротации (уже) |
| Обед | **главный У-приём дня** | рис/басмати/паста + **плотная добивка** (пряник/хлеб/сок) | мясо/рыба full | сюда идёт болюс-инсулин дневной |
| Ужин | белок + умеренные У | картофель/гречка/овощи, comfort только при high_carb | мясо/рыба/птица | без бобовых-тяжеловесов; при вечернем болюсе — +быстрые У в окно укола |
| Перекусы | слоты расширения | **carb-mode при high_carb** (крупа 80 г + фрукт + comfort), иначе белковые | порошок/творог | гейт: У в снек только если мейны в капе |
| Pre/post/intra | физиологические окна | prew ≤60 медленных, postw ≤75 быстрых, intra 40 г/ч кап 90 | pre 20–35 / post 25–50 / intra EAA 12 | **никогда не масштабируются от дневного бюджета** (инвариант) |
| Pre-sleep | казеин 32–40 г | 0 У, Mg 10 г + ягоды 50 г фикс (уже) | казеин/творог | closed для добивки (уже) |
| Инсулин-окно | болюс-приём | быстрые У `dose*10` кап 120 **на окно**, при нескольких болюсах — несколько окон | 0–20 г, жиры 0 | привязка к времени укола, не к CARB_W |

### 3.3. Лестница плотности добивки (не только сухофрукты)
Новый ранжированный тир `DENSE_CARB_LADDER` (У/100, fiber, GI, съедобная порция):
1. Напитки: декстрин/сок/морс/изотоник (10–25 У/100 мл, fiber 0) — top при недоборе >150 г.
2. Сахаристые: мёд/джем/мармелад/зефир (70–80 У/100, порция 35–50 г).
3. Выпечка: пряники/сушки/печенье/багель/белый хлеб (60–75 У/100, порция 50–110 г).
4. Сухофрукты: финики/изюм/курага (65–75 У/100, порция 60 г).
5. Крупы-плотные: белый рис/рисовый крем/кукурузные хлопья/манка (75–85 сух / 25–30 гот).
Порядок = fiber/У ascending + GI context (train-окно → высокий GI ок, вечер/отдых → низкий).
Капы COMFORT при `bulk/high_carb` ×1.5, разрешить **2 источника** вместо 1 при недоборе >100 г.

### 3.4. Съедобность (EDIBILITY_CAPS — по продуктам, не по категориям)
Поверх категорийных капов — таблица «сколько реально съесть за раз»:
- каша готовая 350–450 г (не 700), сухой рис 150–170 г (уже), хлеб 100–165 г,
  пряники 50–80 г, мёд 40–60 г, сок 200–400 мл, курица 250–300 г, творог 250 г,
  овощи 200–300 г, орехи 25–40 г/приём.
- Вес приёма: мейн 400–700 г, снек 200–400 г (уже частично `curWeight*... >650 skip` в `3131`).
- При превышении — не резать молча, а **сплитить в новый слот/следующий приём** или
  предлагать «＋ Приём».

### 3.5. Рецепты: компонентный скейл без ломки
- Разобрать ингредиенты на классы: `base (белок/крупа)` скейлится ×N; `fat (масло)` — max +50%;
  `seasoning (специи/соус)` — freeze на ×1–1.5; `veg` — max ×2.
- `PORTION_STEPS` продлить до ×4–×5 **только для base**, остальное по своим капам.
-Beyond ×3: не раздувать один рецепт, а **рецепт ×3 + сайд** (крупа/хлеб/напиток) — бейдж
  «🍳 ×3 + 🍚 гарнир». Пропорция автора цела, КБЖУ сходится.
- `heavyScaleMax` от **цели приёма**, не только от веса (приём 900+ ккал → 3.0+ независимо
  от веса атлета; безопасность держат капы 1.2–1.8× и гейты приёмки).
- Scale-капы при high_carb: `carb 1.2→1.8`, `protein 1.2→1.4` (белок доберётся топ-апом).

### 3.6. Train/rest как два разных дня
- `trainDay`: peri-окна + болюс-окна + обед max + снек carb-mode + напитки разрешены.
- `restDay`: peri нет вообще (бюджет в мейны), болюс только фоновый (если long — без У-окна),
  У-приоритет — завтрак/обед, ужин лёгкий, comfort урезан вдвое, напитки запрещены.
- Разница 500–800 г задаётся `dayCarbMod` + отсутствием peri + типологией, а не одним числом.

## 5. Критерии приёмки high-volume

1. **1500У train-day, 110 кг, инсулин, products**: dev ≤5%, peri-капы целы, fiber ≤50,
   приёмы ≤700 г, порции ≤ EDIBILITY_CAPS, посадка <15% У-приёма.
2. **1500У recipes**: dev ≤8%, рецепт ≤×3 + сайд/напиток, специи/масло не масштабированы.
3. **500Б**: best-effort + warning Morton, порции ≤300–350 г, порошок ≤3 при ≥320 г.
4. **Rest-day**: нет peri/intra, У на 400–700 ниже train, ужин лёгкий.
5. **Intra при любом бюджете**: ≤90 г, из декстрина/EAA, не из каши.
6. **Регрессия**: 641/641 планировщика + формула ≤3% зелёные, tsc 0, commit pathspec.

  доза инсулина — граммы УГЛЕВОДОВ с плотностной конверсией, не граммы продукта.
- Дотяжка (этот раунд, всё зелёно 56/688): мердж белка перебирает кандидатов (не break
  на первом 300 г) + fallback нового пункта (lean: белок/творог 0%) + fat-guard мерджа;
  потолок компенсации по goalFatG (не adjusted); белковый носитель вето >75% + GI-fallback;
  F1-fallback по плотности; перенос с kcal-комнатой и запретом в тяжёлые; выравнивание
  CARB_W на HV; legacy-fallback распределения; `planner-recipe-high-volume.test.ts` (11:
  assemble-800, products-1500/500, rest/train, снеки); маркер IGF/ГР окнам; mealPrepPlan
  в undo; G3-запрет через isPeriLikeMeal.
- Осознанно НЕ делаем: rest-режим ограничениями в движке (разница train/rest — дело целей:
  carbAutoCycle/dayCarbMod/BB-моды + отсутствие peri; резать comfort на отдыхе ради
  «режима» ломает сходимость без физиологической выгоды — гликоген восполняется и в отдых);
  поиск источника «овёс-45 в окне» закрыт гарант-проходом (детерминированно чисто).

## 6. Сырое vs готовое: единый режим веса (аудит Sep 04 2026)

### 6.1. Факт: сейчас смесь в одном дне и даже в одном рецепте
- `FOOD_DB` держит обе меры рядом: `oats` (варёный, ~71 ккал) и `oats_dry` (367 ккал),
  `rice_white` (готовая мера в рецептах 60–80 г) соседствует с топ-апами `TOPUP_CARB_IDS`
  (`day-target-corrector.ts:89`: `rice_white` + `oats_dry` в одном списке).
- Ремап `oats→oats_dry` есть только точечно: `recipe-db.ts:108–113` (≤150 г в рецептах),
  `IndividualPlanContext.tsx:1673` (portable-режим), тест `planner-recipe-gates.test.ts:36`.
  Системного правила нет: один приём может получить `гречка 250 г готовой` + `oats_dry 30 г сухой`,
  пользователь взвешивает и то и другое «как написано» — ошибка ×2.5–3 по крупам.
- `carbPortionCap` (`meal-plan-engine.ts:262–282`) различает сухое/готовое **по плотности**
  (`carbs≥55 → maxDry`, `<30 → maxGrain`), а не по флагу продукта — эвристика, а не единица измерения.
- Отображение: везде просто «г» (`MealListRender`), без «сух/гот». Закупки суммируют
  `amount` по `id` (`buildShoppingFromPlans:758–778`) — 100 г сухого риса и 100 г готового
  складываются как одно и то же.

### 6.2. Решение: глобальный `weightMode: 'raw' | 'cooked'` + конверсия
- NEW `planner-weight-mode.ts`: таблица `DRY_TO_COOKED` (рис 1→2.8, гречка 1→2.5,
  овсянка 1→3.0, паста 1→2.4, булгур 1→2.6, чечевица 1→2.3; мясо наоборот 1→0.65–0.75
  ужарка — для закупок, не для тарелки).
- Каждый `FOOD_DB`-продукт получает флаг `weightState: 'dry' | 'cooked' | 'fresh'`
  (крупы сухие в каталоге — dry; `rice_white/oats` готовые — cooked; мясо/овощи — fresh).
- Переключатель в Settings (персист `he_planner_weight_mode`, дефолт `cooked` — «как на тарелке»):
  движок считает в канонических per100 как сейчас, а **отображение + закупки + готовка**
  конвертят в выбранный режим. Внутри одного плана — один режим, бейдж
  «⚖️ вес готовый / сухой» в шапке дня и в печати.
- Рецепты: `portions` хранятся как авторские (с флагом), скейл не меняет смысл граммов,
  конверсия — только на рендере. Смесь в одном рецепте запрещена линтом
  (`planner-recipe-gates.test.ts`: все `ingredientIds` одного рецепта — один `weightState`
  для круп).
- Закупки: агрегировать в **сыром** весе всегда (покупаем сухую крупу), тарелка — в выбранном.
  Две колонки в списке: «купить» / «на тарелке».

### 6.3. Приёмка
- Матрица: один и тот же день в `raw` и `cooked` даёт одинаковые КБЖУ (±1%), граммовки
  отличаются на коэффициенты таблицы; нет приёма со смесью мер; закупки — сырой вес.

## 7. Нижние карточки: автоперестройка при любом изменении (аудит Sep 04 2026)

### 7.1. Факт: stale-карточки после ручных правок
- Рецептурные пути синкают закупки: `replaceMealWithRecipe` (2145), `pickRecipeOption` (1939, 1955),
  `removeMealRebalanced` (1840, 1855), `addSecondRecipeToMeal` (2285), `autoCorrectPlan` (3272).
- Ручные правки **не синкают ничего**: `addFoodToMeal` (1629), `replaceFoodItem` (1694),
  `updateItemAmount` (1719), `removeFoodItem` (1740), `moveFoodItem` (1458),
  `updateMealTime`/`duplicateMeal` (1864/1884) идут через `_applyDayPlanMealUpdate` (1621)
  / `updateMultiDayPlan` (1434), которые обновляют только `meals/totals`.
- `mealPrepPlan` — только по кнопке `generateMealPrep` (3280); открытая рецептурная карточка
  обновляется тихо (`refreshRecipeCookingCardIfActive`, 3299), generic-план — нет.
- `recommendations` — только по кнопке + один `useEffect` на `injections.length`
  (`planner-special-meal-state.ts:109`). Смена веса/цели/периодизации при готовом плане
  карточки не трогает. Отчёты/брифинг — производные рендера (ок), закупки/готовка/рекомендации — нет.

### 7.2. Решение: один реактивный синк вместо N ручных вызовов
- NEW `usePlannerDerivedSync`: `useEffect` с debounce ~400 мс на
  `[dayPlan, threeDayPlan, weekPlan, planDays, selectedDayIndex, mealPrepDays]`:
  1. `setShoppingList(buildShoppingFromPlans(visiblePlans))` — всегда из видимых дней
     (та же логика выбора, что в F-ветках `replaceMealWithRecipe`);
  2. если `recipeCookingActiveRef` — `refreshRecipeCookingCardIfActive(...)`, иначе
     инвалидировать `mealPrepPlan` (бейдж «устарело — нажмите 🍳», не молчаливый stale);
  3. `generateRecommendations()` — дешёвая, можно всегда; тяжёлые отчёты оставить по кнопке.
- Убрать разрозненные `setShoppingList` из 8 мест (оставить один вызов синка) — иначе гонки
  «ручной синк vs эффект» (порядок: эффект — единственный писатель).
- `weekEditDay`-синк уже есть в `_applyDayPlanMealUpdate` (1621–1626) — распространить тот же
  паттерн на синк закупок (сейчас часть путей синкает только `dayPlan`-копию).
- Индикатор «↻ карточки обновлены» + `undo` покрывает и производные (снапшот уже включает
  `shoppingList/recommendations`, `IndividualPlanContext.tsx:1401–1421` — проверить `mealPrepPlan`).

### 7.3. Приёмка
- Любая правка (граммы/замена/удаление/перетаскивание/второй рецепт/время/дубль) → закупки
  и готовка соответствуют плану без нажатия кнопок; тест: мутация → `buildShoppingFromPlans`
  от актуального состояния равен показанному `shoppingList`.

## 8. Второй рецепт в приёме рушит генерацию (аудит Sep 04 2026)

### 8.1. Факт: механика `addSecondRecipeToMeal` (2223–2288) + ребаланс
- Второй масштабируется к остатку: `_roomKcal = max(150, target − first)` (2251) —
  если первый уже закрыл/перебрал приём, второй **принудительно** +150 ккал минимум.
  Два сытных рецепта в приёме 700 ккал = гарантированный перебор.
- Слияние — конкатенация `[...items1, ...items2]` (2255), затем `rebalanceDayAfterRecipes`.
  Но резка перебора **скипает ядро обоих рецептов** (`planner-recipe-mode.ts:568–581`:
  `coreIds` = union `ingredientIds`, без ids — весь приём ядро). Резать нечего —
  остаются только сайды/соседние приёмы; при двух больших рецептах их не хватает.
- Финальная посадка ±10% (`700–742`) смотрит только `m.recipeApplied` (708) и масштабирует
  **весь приём целиком** — авторские пропорции обоих рецептов плывут вместе.
- Баги синка: закупки для three/week берутся из **старых** `threeDayPlan.days/weekPlan.days`
  (2285), а не из пропатченных `resMeals` — список врёт; `refreshRecipeCookingCardIfActive`
  не вызывается (есть в `replaceMealWithRecipe:2146`, нет здесь) — карточка готовки stale;
  печать/брифинг второй рецепт уже умеют (`planner-day-print.ts:102,119–120`,
  `planner-briefing.ts:69–71`), корректор тоже (`day-target-corrector.ts:74–80`) — узкое место
  именно в `addSecond + rebalance`, не в отображении.
- Совместимость `recipeCompatibility` (2237) — только гейт «можно/нельзя», без
  количественной проверки «влезут ли КБЖУ».

### 8.2. Решение: второй рецепт как «доля приёма», а не «плюс 150»
1. **Предварительный количественный гейт**: `доля2 = roomKcal/target`; если `<25%` —
   предупреждать «влезет только ≥×0.5 мини-порция, приём переберёт» и предлагать:
   (а) ужать первый до `target − min(room, secondMin)` кумулятивной посадкой ±10% **до**
   слияния, (б) мини-порцию второго ×0.5, (в) отмену. Никаких принудительных +150.
2. **Ядро второго — тоже ядро**: расширить финальную посадку (708) на `recipeApplied2`
   (`m.recipeApplied || m.recipeApplied2`), кумулятивный коридор ±10% считать **раздельно**
   на каждый рецепт (два счётчика `cumScale`), а не на приём целиком.
3. **Починить синк**: закупки из пропатченных дней (как в `replaceMealWithRecipe:2139–2145`),
   вызвать `refreshRecipeCookingCardIfActive`, разнообразие уже считается (2271) — ок.
4. **Замена второго вместо «только добавить»**: UI уже умеет («Заменить второй рецепт»,
   `MealListRender.tsx:314`) — движок должен при замене сначала **вычесть** items2 старого
   второго, а не конкатенировать третьим слоем.
5. **Лимит**: max 2 рецепта на приём (уже фактически), третий — только через замену;
   peri/presleep — запрет второго (одно окно = одно блюдо).

### 8.3. Приёмка
- Тесты: `первый 600 + второй 400 в цель 700` → либо ужатие первого + мини-второй с dev ≤5%,
  либо честный отказ с toast (не молчаливый перебор 1000/700); закупки = факт после операции;
  повторная замена второго не копит items (длина items не растёт); резка не трогает ядра обоих.
